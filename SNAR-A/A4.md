# SNAR-A4

## Skorpion Norms And Rules, A generation. Standard A4

This standard defines the **semantics** of the Skorpion programming language with the `*.sk` extension. It describes **what a syntactically valid program means**: which types are checked, which constraints are enforced, which operations are valid, and how async/Promise, unions, and error types behave.

The rules of this standard are normative. Informative notes are explicitly marked as such. Error codes match `midlevel/semantic.go` and are **informative**; the conditions are normative. §13 lists every known divergence between this standard and the reference implementation.

## 0. Common Rules

### R-C1. Rule of Input

The input to the semantic analyzer is the **AST** produced by the parser according to SNAR-A3.

A program that does not conform to SNAR-A3 is **not** analyzed; the semantic phase is not entered.

### R-C2. Rule of Analysis Order

The analyzer processes the program in the following order:

1. Register built-in types (§1.3).
2. Register the built-in `Error` type (§8.1).
3. Register user-declared error types (§8.2).
4. Register all top-level functions (§4.1).
5. Check the `main` function (§4.5).
6. Analyze each function body (§4.2–§4.4).

An error in an earlier step **may** prevent later steps from running. This is implementation-defined; the reference implementation stops at the first failing phase.

### R-C3. Rule of Scope

A **scope** is a mapping from identifier names to symbols.

There are three kinds of scope in a program:

| Scope | Created by |
|-------|------------|
| Global | Program start |
| Function | Each function body |
| Block | Each `{ … }` block |

A **global scope** contains: built-in types, built-in functions, the `Error` type, user error types, and top-level functions.

A **function scope** is a child of the global scope and contains the function's parameters.

A **block scope** is a child of the enclosing scope and contains variables declared in the block.

Name lookup starts from the current scope and walks up the chain to the global scope.

### R-C4. Rule of Symbol Kinds

Every symbol has a **kind**:

| Kind | Meaning |
|------|---------|
| `SYM_VARIABLE` | A variable or parameter |
| `SYM_FUNCTION` | A function |
| `SYM_CONST` | A constant or type name |

### R-C5. Rule of Errors vs Warnings

A **semantic error** is fatal: the program does **not** conform to this standard.

A **semantic warning** is non-fatal: the program still conforms, but the user is informed.

Errors are reported with codes `1xxx`, `06xx`, `15xx`; warnings with codes `2xxx`.

### R-C6. Rule of Case Sensitivity

All names are case-sensitive (SNAR-A2, R-C5).

### R-C7. Rule of Conformance

See §11.

## 1. Types

### 1.1. Rule of Type Names

The Skorpion type system has the following **type constructors**:

| Type | Constructor |
|------|-------------|
| `int` | primitive |
| `string` | primitive |
| `float` | primitive |
| `double` | primitive |
| `bool` | primitive |
| `char` | primitive |
| `void` | primitive (unit) |
| `any` | primitive (top) |
| `arr[T]` | array of `T` |
| `arr` | alias for `arr[any]` |
| `dict` | dictionary (keys: any string, values: heterogeneous) |
| `T<A, B, …>` | union |

### 1.2. Rule of Valid Types

A type string is **valid** if it is:
- one of `int`, `string`, `float`, `double`, `bool`, `char`, `void`, `any`, `dict`, `arr`;
- `arr[T]` where `T` is valid and `T ≠ void`;
- `T<A, B, …>` where each `A`, `B`, … is a valid non-union non-`any` type, and there are at least two members (or a single member, which normalizes).

An invalid type in a declaration produces error `1506`.

### 1.3. Rule of Built-in Types

The built-in types are always visible in every scope. A user function or error type may **not** share a name with a built-in type (`1500`).

### 1.4. Rule of `void`

`void` is the type of `null` and of functions that return no value.

`void` **cannot** be used as:
- a variable type (`1558`);
- a function parameter type (implementation-defined; SNAR-A3 §5.3 rejects it at parse time for `arr[void]`, but a bare `void x` parameter parses);
- an array element type (`1543`);
- a union member (`T<void, int>` is invalid, `0615`).

`void` **can** be used as:
- a function return type;
- the type of `null`.

### 1.5. Rule of `any`

`any` accepts any non-`void` value.

`any` **cannot** be:
- a union member (`0615`);
- the target of a `null` assignment (`1557`);
- a parameter that receives `null` (`1552`).

`any` is the **top type** for values, but it is **not** a valid type in `T<...>`.

### 1.6. Rule of Numeric Types

The **numeric types** are: `int`, `float`, `double`, `char`.

`char` is numeric for the purpose of arithmetic, comparisons, and `+=`/`-=`.

### 1.7. Rule of Implicit Conversions

Two implicit conversions are permitted:

| From | To | Context |
|------|----|---------|
| `char` | `int` | assignment, function argument, return value |
| `int` | `char` | assignment, function argument, return value |

All other conversions are **explicit**, using `to_*` built-ins (§9.2).

### 1.8. Rule of Type Equality

Two type strings are **equal** if they are byte-identical.

`T<int>` and `int` are **not equal** as strings, but are semantically equivalent: the parser normalizes `T<A>` to `A` (SNAR-A3 §2.4.1).

### 1.9. Rule of Union Types

A **union type** `T<A, B, …>` is valid if:
- it has at least one member;
- each member is a valid type (§1.2);
- no member is itself a union (`0611`);
- no member is `any` (`0615`);
- no member is `void` (`0615`).

A union variable has a **current type** — the type of its last assignment. Before the first assignment, the current type is **unknown**.

### 1.10. Rule of Array Types

`arr[T]` is an array of elements of type `T`.

`arr` is an alias for `arr[any]`.

`arr[void]` is **invalid** (`1543`).

`arr[arr[T]]` is a nested array — valid.

An array variable tracks its **element type** and, if initialized with an array literal, its **per-element types** (for indexing).

### 1.11. Rule of Dictionary Types

`dict` is a dictionary with string keys and heterogeneous values.

A `dict` variable may track its **key types** if initialized with a dict literal.

## 2. Variables

### 2.1. Rule of Variable Declaration

A variable declaration:

```
Type Name [ = Expr ]
```

is analyzed as follows:

1. If `Type` is invalid → `1506`.
2. If `Type` is `void` → `1558`.
3. If `Name` is already declared **in the current scope** → `1505`.
4. If `Expr` is present:
   1. Compute `Expr`'s type.
   2. If `Expr`'s type is `void` (null):
      - If `Type` is `any` → `1557`.
      - Otherwise → allow (null assignable to any non-`any` type).
   3. Check compatibility (§2.2).
5. Define `Name` in the current scope with `Type`.

### 2.2. Rule of Type Compatibility in Assignment

A value of type `Src` is assignable to a variable of type `Dst` if one of:

| Condition | Result |
|-----------|--------|
| `Src == Dst` | OK |
| `Dst == "any"` and `Src ≠ "void"` | OK |
| `Dst == "int"` and `Src == "char"` | OK |
| `Dst == "char"` and `Src == "int"` | OK |
| `Src == "void"` (null) and `Dst ≠ "any"` | OK (null literal) |
| `Dst` is a union and `Src` is a member | OK |
| `Dst` is `arr[any]` and `Src` is any array | OK |
| otherwise | `1507` |

A mismatch produces error `1507`.

### 2.3. Rule of Union Assignment

When assigning to a union variable `x: T<A, B>`:

1. If the value is `void` (null):
   - The union's **current type** is reset to **unknown**.
   - No error. (null is a "placeholder" that clears the current type.)
2. If the value's type is `T`:
   - If `T` is a member of the union → OK; set current type to `T`.
   - Otherwise → `0612`.
3. If the value's type is `any` → OK; current type becomes `any`.

`null` cannot **initialize** a union variable: if `x: T<A,B> = null` → `1557`.

### 2.4. Rule of Const Variables

A `const` variable:
- **must** have an initializer (`0557`, parse-time);
- **cannot** be reassigned (`1509`);
- **cannot** be modified via `++`/`--` (`1509`);
- **cannot** be the target of a compound assignment (`1509`).

### 2.5. Rule of Array Declarations

For `arr[T] x = Expr`:

1. If `T == "void"` → `1543`.
2. If `Expr` is an array literal:
   - For each element, check its type against `T`.
   - If `T == "any"`:
     - `null` elements are **forbidden** (`1542`): a heterogeneous array cannot contain `null`.
   - Else:
     - If `T` is an array type (`arr[…]`) and the element is not an array literal → `1534`.
     - Else if the element's type is `void` → allow (null in typed array).
     - Else if the element's type ≠ `T` and is not `""` → `1534`.
3. If `Expr` is not an array literal → the expression's type must be `arr[T]` or `arr[any]` (implementation-defined; reference does not check this).

### 2.6. Rule of Dictionary Declarations

For `dict x = Expr`:

1. If `Expr` is a dict literal:
   - Each element's value type is recorded in `x`'s key-type map.
2. A dict variable may be indexed with a string key (`x["key"]`) or accessed with a dot (`x.key`).

### 2.7. Rule of Promise Variables

A variable declared as:

```
T x = asyncFunc(...)
```

where `asyncFunc` is an async function and `T` matches `asyncFunc`'s return type is a **promise variable**.

A promise variable:
- is **read-only**: assignment produces `0674`;
- **cannot** be `++`/`--`'d (`0674`);
- may be `await`'d (see §7.5).

A promise variable's `RealType` is `"promise"`.

## 3. Expressions

### 3.1. Rule of Expression Type

Every expression has a **type**. `getNodeType(expr)` computes it.

The type of an expression is:

| Expression | Type |
|------------|------|
| number literal | `int`, `float`, or `double` (per suffix/dot) |
| string literal | `string` |
| char literal | `char` |
| unicode literal | `char` |
| `null` | `void` |
| `true` / `false` | `bool` |
| identifier | symbol's type |
| dict literal | `dict` |
| array literal | `arr[any]` |
| `type(x)` | `string` |
| error instance | the error type |
| range expression | `arr[int]` |
| format suffix `^0f` | `int` |
| format suffix `^Nf` (N>0) | type of inner |
| format suffix `^X...` | type of inner |
| call expression | function return type |
| range-method call | function return type |
| field access | field type / `any` for dict |
| index `x[i]` | element type / `any` for dict |
| `await` | return type of awaited function |
| `Promise[...]` | async function's return type |
| unary `$` | `string` |
| unary `!` | `bool` |
| unary `-` | type of inner |
| binary `&&`, `\|\|` | `bool` |
| binary comparisons | `bool` |
| binary arithmetic | see §3.3 |
| ternary | type of `Then` (or `any`) |

### 3.2. Rule of Binary Operator Types

| Operator | Left | Right | Result |
|----------|------|-------|--------|
| `+` | `string` | `string` | `string` |
| `+` | `char` | `char` | `string` |
| `+` | `char` | `string` | `string` |
| `+` | `string` | `char` | `string` |
| `+` | numeric | numeric | numeric (per §3.3) |
| `- * / **` | numeric | numeric | numeric |
| `%` | `int` | `int` | `int` |
| `&& \|\|` | `bool` | `bool` | `bool` |
| `< > <= >= == !=` | numeric | numeric | `bool` |

Type violations produce `1511` (arithmetic), `1512` (comparison), `1528`/`1529` (`&&`/`||`).

### 3.3. Rule of Numeric Result Types

For arithmetic on numeric types:

| Left / Right | Result |
|--------------|--------|
| `double` in either | `double` |
| `float` in either | `float` |
| otherwise | `int` |

`char` participates as `int` in this computation.

### 3.4. Rule of `any` in Arithmetic

If either operand is `any`, the result type is `any`. The reference implementation **does not** type-check the arithmetic — it assumes runtime dispatch.

### 3.5. Rule of Division by Zero

If the right operand of `/` is a numeric literal with value `0` or `0.0`, a **warning** `1541` is emitted.

This does **not** prevent compilation.

### 3.6. Rule of Unary Operators

| Operator | Operand | Result |
|----------|---------|--------|
| `!` | `bool` | `bool` |
| `!` | `void` | `1555` |
| `!` | other | `1526` |
| `-` | numeric | numeric |
| `-` | non-numeric | `1527` |
| `$` | any | `string` |

`$` is the **string conversion** operator: it produces the textual representation of the operand.

### 3.7. Rule of Ternary Expressions

```
cond ? then : else
```

1. `cond`'s type must be `bool` (or `""`): otherwise `1530`.
2. `then`'s and `else`'s types must match (or one is `""`): otherwise `1531`.
3. The result type is the common type of `then` and `else`.

### 3.8. Rule of Ternary Inside Unions

If `then` or `else` is a union, the result is the union type.

## 4. Functions

### 4.1. Rule of Function Registration

A top-level function is registered in the global scope:

1. If a symbol with the same name exists → `1500`.
2. If the name matches an error type → `1500`.
3. Otherwise, define with the function's return type.

**Two functions with the same name are forbidden**, regardless of parameter types. Skorpion does **not** support overloading.

### 4.2. Rule of Function Analysis

For each function body:

1. Create a function scope.
2. Register parameters (§4.3).
3. Analyze the body.
4. If return type ≠ `void` and the body does not return on all paths → `1535`.
5. If body is empty → warning `2003`.
6. Collect used identifiers.
7. Warn about unused parameters (`2001`) and variables (`2000`).

### 4.3. Rule of Parameters

For each parameter:

1. If it is a **union**, check members (§1.9).
2. Register in function scope.
3. Duplicate parameter names → `1536`.
4. A parameter with default after a parameter without default → `1537`.
5. More than one variadic parameter → `0560`.
6. A variadic parameter not last → `0560`.

### 4.4. Rule of Return Paths

A function with a non-`void` return type **must** return on all control-flow paths.

The **hasReturn** predicate is true if:

| Statement | hasReturn |
|-----------|-----------|
| `return expr` | true |
| `do { … } while …` | false |
| `{ … }` | true if any statement hasReturn |
| `try { } catch (…) { }` | true if body hasReturn **and** all catches haveReturn |
| `if (…) { } [elsif …] else { }` | true if `then` hasReturn **and** all `elsif`s haveReturn **and** `else` is present and hasReturn |
| `case (…) { … _ { } }` | true if all branches haveReturn and default exists and hasReturn |
| `while`, `for` | false |
| other | false |

If `hasReturn` is false for a non-`void` function → `1535`.

### 4.5. Rule of `main`

Unless the analyzer is in **library mode**, the program **must** have a `main` function.

`main` **must**:
- return `void` (`1502`);
- take exactly one parameter (`1503`);
- that parameter must be of type `arr` (`1504`).

A missing `main` → `1501`.

### 4.6. Rule of Function Calls

For a call `f(args)`:

1. Resolve `f` (§4.7).
2. If `f` is not found → `1518`.
3. If the identifier is a non-function symbol (variable) → `1539`.
4. Count required, optional, and variadic parameters.
5. Check argument count:
   - `args < required` → `1519`;
   - `args > total` and no variadic → `1519`.
6. Check each argument's type:
   - Union parameter: `arg ∈ union` or `any`, else `0612`.
   - `null` argument: `param ≠ any` (else `1552`) and `param` must allow null.
   - Otherwise: `argType == paramType` or implicit conversion (§1.7), else `1520`.

### 4.7. Rule of Function Resolution

Function names are resolved in this order:

1. Local functions in the same file (exact name).
2. Imported functions under the exact key (`module.func` or `alias.func`).
3. Local functions by **simple name** (after stripping the last `.`).
4. Imported functions by simple name.
5. Any imported function whose `Name` matches.
6. Any `AllFunctions` entry whose `Name` matches.

The first match wins.

### 4.8. Rule of Built-in Function Calls

Built-in functions (`to_int`, `to_float`, `to_double`, `to_string`, `to_bool`, `to_arr`, `detruncate`, `getConfig`, `getConfigField`, `isAsyncEnded`) are recognized by simple name.

For built-ins (except `isAsyncEnded`):
- arguments are analyzed but not type-checked;
- the return type is fixed (§9).

`isAsyncEnded` is special (§7.7).

## 5. Statements

### 5.1. Rule of If

For `if (cond) { … } [elsif …] [else …]`:

1. `cond`'s type must be `bool` (or `""`): otherwise `1521`.
2. Same for each `elsif` condition: `1524`.
3. Analyze `then`, each `elsif` branch, and `else`.

### 5.2. Rule of While

For `while (cond) { … }`:

1. Increment `LoopDepth`.
2. `cond` must be `bool`: otherwise `1522`.
3. Analyze the body.
4. Decrement `LoopDepth`.

### 5.3. Rule of Do-While

For `do { … } while (cond)`:

1. Increment `LoopDepth`.
2. Analyze the body.
3. `cond` must be `bool`: otherwise `1563`.
4. Decrement `LoopDepth`.

### 5.4. Rule of For-In

For `for (T x in iterable) { … }`:

1. Increment `LoopDepth`.
2. Compute `iterable`'s type:
   - `string` → element type `string`;
   - `arr[E]` → element type `E`;
   - `arr` → element type `any`;
   - `arr[int]` → `int`;
   - otherwise → `0631`.
3. Check `T` against the element type: mismatch → `0632`.
4. Register `x` in the loop scope.
5. Analyze the body.
6. Decrement `LoopDepth`.

### 5.5. Rule of Case

For `case (scrutinee) { … }`:

1. `scrutinee`'s type is the **pattern type**.
2. For each branch:
   - For each pattern, its type must match the scrutinee's type (or `""`): otherwise `1525`.
   - If the pattern is a constant (number or string), it is recorded as a key. Duplicate key → `1540`.
   - Analyze the branch body.
3. Analyze the default branch, if present.

### 5.6. Rule of Break / Continue

`break` and `continue` are valid only inside a loop.

Outside a loop:
- `break` → `1561`;
- `continue` → `1562`.

Loops include `while`, `do-while`, `for-in`.

### 5.7. Rule of Return

For `return [expr]`:

1. If the enclosing function returns `void`:
   - `expr` present → `1515`.
2. Else (non-`void` return):
   - `expr` absent → `1517`.
   - `expr` present:
     - Union return type: `exprType ∈ union`, else `0612`.
     - Non-union: `exprType == returnType` (or implicit conversion), else `1516`.
     - `exprType == void` → allow (null assignable to non-`any`).

### 5.8. Rule of Assignment

For `target op value`:

1. `target`'s symbol must exist: else `1508`.
2. If `target`'s symbol is a promise variable → `0674`.
3. If `target` is `const` → `1509`.

#### 5.8.1. Simple Assignment

`x = value`:

1. If `x`'s type is a union → §2.3.
2. If `value`'s type is `void`:
   - `x`'s type is `any` → `1557`;
   - otherwise → allow.
3. Otherwise check compatibility (§2.2): mismatch → `1510`.

#### 5.8.2. Compound Assignment

`x op= value`:

1. `op` must be one of `+`, `-`, `*`, `/`, `%`, `**`.
2. The operation `x op value` must be valid (§3.2).
3. The result must be assignable back to `x`.

Special cases:
- `string += string` / `string += char` → OK;
- `char += string` / `char += char` → OK;
- `int %= int` → OK; `%` on non-`int` → `1511`;
- numeric compound with numeric → OK;
- `any` accepts any compound;
- otherwise → `1510`/`1511`.

#### 5.8.3. Index Assignment

`x[i] op= value`:

1. If `x` is `const` → `1509`.
2. If `x` is not `arr` or `dict` → `1539`.
3. `i`'s type:
   - `arr`: `int`;
   - `dict`: `string` (or `int` for a lenient implementation).
   - Otherwise → `1520`.
4. For `arr[T]`: `value`'s type must be `T` (or `""`, or `void`): else `1510`.
5. For `dict`: any value type.
6. Compound assignment in an index → same as §5.8.2.

#### 5.8.4. Field Assignment

Field assignment (`x.field = value`) is **not** supported by SNAR-A3 (§8.4.2). If it is supported by an extended implementation, it behaves like dict/error field assignment.

### 5.9. Rule of Postfix `++` / `--`

1. The operand must be a variable: else `1508`.
2. The variable's type must be `int`: else `1564`.
3. The variable must not be `const`: else `1509`.
4. The variable must not be a promise variable: else `0674`.

### 5.10. Rule of Throw

For `throw expr`:

1. `expr` must be present (`0579`, parse-time).
2. `expr`'s type must be an error type: else `1548`.
3. Analyze `expr`.

### 5.11. Rule of Try / Catch

For `try { … } catch (T as e) { … }`:

1. Analyze `try` body.
2. For each catch clause:
   - If `TypeName != ""` and `TypeName != "Error"`:
     - Strip the qualifier.
     - If the type is not registered → `1560`.
   - If `VarName != ""`:
     - Define `VarName` in the catch's scope with type `TypeName` (or `Error` if empty).
   - Analyze the catch body.

### 5.12. Rule of `includeC` and `IknowIdo`

`includeC` blocks are **not** analyzed. The raw C code is passed through.

`IknowIdo` blocks are **not** analyzed. They are completely opaque to the semantic phase.

## 6. Expressions — Detail

### 6.1. Rule of Field Access

`x.field`:

1. `x` must be defined: else `1514`.
2. If `x`'s type is `dict` → OK, result type is `any` (or the recorded key type).
3. If `x`'s type is an error type:
   - If `field` is not a field of that error type → `1539`.
   - Result type is the field's type.
4. Otherwise → `1539`.

### 6.2. Rule of Array Indexing

`x[i]`:

1. `x` must be defined: else `1514`.
2. If `x`'s type is `dict` → OK, result type `any`.
3. If `x`'s type is `arr[T]`:
   - `i` must be `int`: else `1520`.
   - If `x` has per-element types and `i` is a constant → return the recorded element type.
   - Otherwise → `T`.
4. Otherwise → `1539`.

### 6.3. Rule of Format Suffixes

`expr ^ Nf` and `expr ^ X...`:

1. `expr` must be numeric: else `0626`.
2. `^0f` produces `int`; `^Nf` (N>0) and `^X...` preserve `expr`'s type.

### 6.4. Rule of Range-Method Calls

`start..end.method(args)`:

1. `start` and `end` must be **constant integers**: else `1533`.
2. `method` must be a registered function: else `1518`.
3. The number of arguments is `|end - start| + 1 + len(extra)`. This must equal the function's parameter count: else `1519`.
4. Range-expanded arguments must be `int` (or `any`): else `1520`.
5. Extra arguments must match their parameter types: else `1520`.

### 6.5. Rule of `type(x)`

`type(x)` returns a `string` containing the type name of `x`.

`x` is analyzed normally.

### 6.6. Rule of Error Instances

For `TypeName { field: value, … }`:

1. `TypeName` must be a registered error type: else `1560`.
2. For each field:
   - If `field` is not a field of `TypeName` (including inherited) → `1547`.
   - Otherwise, `value`'s type must match the field's type: else `1532`.
3. For each field declared without default:
   - If not provided → `1551`.

## 7. Async / Promise

### 7.1. Rule of Async Functions

An `async` function:

1. **must not** return `void` (`0665`);
2. **must** contain exactly one `Promise[...]` statement (`0675`);
3. the `Promise[...]` **must** be the first statement (`0670`);
4. the `Promise[...]` value **must** be a literal (`0671`);
5. the `Promise[...]` value's type **must** match the return type (`0669`).

If the async function contains only static operations, a **warning** `2005` is emitted.

### 7.2. Rule of `Promise[...]`

`Promise[expr]` is valid only inside an `async` function: else `0662`.

`expr` **must** be a literal:
- number;
- string;
- char;
- unicode;
- `null`;
- `true` / `false`.

Any other expression → `0671`.

`expr`'s type must match the enclosing async function's return type: else `0669`.

### 7.3. Rule of Fire-and-Forget Async Calls

A call to an async function in **statement position** is a **fire-and-forget** call:

```
fooAsync()
```

This is valid. The result is discarded; the Promise's value is not awaited.

The call's arguments are type-checked as in §4.6.

A fire-and-forget call does **not** need to be `await`'d.

### 7.4. Rule of Await

For `await expr`:

1. If `expr` is a call `f(...)`:
   - `f` must exist: else `1518`;
   - `f` must be `async`: else `0664`.
   - The result type is `f`'s return type.
2. If `expr` is an identifier `x`:
   - `x` must exist: else `1514`;
   - `x` should be a promise variable (implementation-defined; reference does not enforce this).
   - The result type is `x`'s declared type.
3. Otherwise → `0663`.

### 7.5. Rule of Promise Variables in Await

A promise variable `x` (declared as `T x = asyncFunc(...)`) may be `await`'d:

```
await x
```

The result type is `T`.

### 7.6. Rule of Async Call in Variable Declaration

`T x = asyncFunc(args)`:

1. `asyncFunc` must exist (`1518`).
2. `asyncFunc` must be async.
3. `T` must equal `asyncFunc`'s return type (`1507`).
4. Arguments are checked as in §4.6.
5. `x` is a **promise variable**.

### 7.7. Rule of `isAsyncEnded`

`isAsyncEnded("name")`:

1. Must have exactly one argument (`0666`).
2. The argument must be a **string literal** (`0667`).
3. The literal must name a function (`1518`).
4. The function must be async (`0664`).

The return type is `bool`.

## 8. Error Types

### 8.1. Rule of the Built-in `Error`

The `Error` type is predefined:

```
const Error { msg: string } = new Error
```

It is always registered in the global scope.

### 8.2. Rule of User Error Types

For `const Name { fields } = [new] Parent`:

1. `Name` must be unique (`1500`).
2. `Parent` must be a registered error type: else `1549`.
3. Each field:
   - Its type must be valid (`1506`).
   - If it overrides a parent field with a different type → `1550`.
4. Register the new type.

### 8.3. Rule of Field Inheritance

`collectErrorFields(decl)` walks the inheritance chain and returns the union of all fields, with child fields overriding parent fields of the same name.

### 8.4. Rule of Error Instances

See §6.6.

### 8.5. Rule of Throw

See §5.10. The thrown expression must be of an error type.

### 8.6. Rule of Catch

See §5.11. The catch type must be a registered error type (or `Error`).

## 9. Built-in Functions

### 9.1. Rule of Built-in Function Names

The built-in functions are recognized by simple name:

| Name | Signature | Return type |
|------|-----------|-------------|
| `to_int` | `(any) → int` | `int` |
| `to_float` | `(any) → float` | `float` |
| `to_double` | `(any) → double` | `double` |
| `to_string` | `(any) → string` | `string` |
| `to_bool` | `(any) → bool` | `bool` |
| `to_arr` | `(any) → arr[any]` | `arr[any]` |
| `detruncate` | `(any) → string` | `string` |
| `getConfig` | `() → dict` | `dict` |
| `getConfigField` | `(string) → any` | `any` |
| `isAsyncEnded` | `(string) → bool` | `bool` |

### 9.2. Rule of `to_*` Conversion Functions

The `to_*` functions perform explicit conversions:

| Function | Behaviour |
|----------|-----------|
| `to_int` | Converts to `int`; truncates floats |
| `to_float` | Converts to `float` |
| `to_double` | Converts to `double` |
| `to_string` | Converts to `string` |
| `to_bool` | Converts to `bool` |
| `to_arr` | Converts to `arr[any]` |

Arguments are not type-checked; the conversion is runtime-dispatched.

### 9.3. Rule of `detruncate`

`detruncate(x)` returns the string representation of `x` **without** the last character.

The reference semantics are implementation-defined; SNAR-A4 does not specify the exact truncation behaviour.

### 9.4. Rule of `getConfig` / `getConfigField`

`getConfig()` returns the parsed `manifest.spc` as a `dict`.

`getConfigField(name)` returns the field `name` from the config, or `null` if absent.

The exact field names are defined by SNAR-A1.

### 9.5. Rule of `isAsyncEnded`

See §7.7.

## 10. Union Types — Detail

### 10.1. Rule of Union Declarations

A union variable `T<A, B> x`:

1. Members must be valid, non-union, non-`any`, non-`void` types.
2. Any violation → `0611` / `0615`.
3. `x`'s type is the union string.

### 10.2. Rule of Union Current Type

The analyzer tracks a **current type** for each union variable:

- Before the first assignment: `""` (unknown).
- After `x = value`: the value's type.
- After `x = null`: `""` (reset).
- After a control-flow construct (`if`, `while`, `case`, `try`, `for`): reset to `""`.

### 10.3. Rule of Union Operations

For `left op right` where at least one operand is a union:

1. Compute the set of possible types for each operand:
   - If the operand is a union variable with a known current type, the set is a singleton.
   - Otherwise, the set is the union's members.
2. For each combination `(l, r)`:
   - If `op` is valid for `(l, r)` → valid.
   - Else → invalid; record `l op r`.
3. If **no** combination is valid → `0613`.
4. If **some** combinations are valid but not all → `0614` (may fail at runtime).
5. If **all** combinations are valid → OK.

### 10.4. Rule of `isBinaryOpValid`

| Op | Valid for |
|----|-----------|
| `+` | `string + *`, `* + string`, or numeric + numeric |
| `- * / **` | numeric + numeric |
| `%` | `int + int` |
| `&& \|\|` | `bool + bool` |
| `< > <= >= == !=` | numeric + numeric |

## 11. Conformance

### 11.1. Rule of Conformance

A program **conforms** to SNAR-A4 if and only if the semantic analyzer reports **zero errors**.

Warnings do not affect conformance.

### 11.2. Rule of Non-Conformance

A program that produces at least one semantic error does not conform.

### 11.3. Rule of Violation

A program that violates any rule of this standard is **invalid**.

## 13. Known Limitations of the Reference Implementation

### 13.1. No Overloading

Skorpion does **not** support function overloading. `f(int)` and `f(string)` are forbidden (`1500`).

### 13.2. No Implicit Numeric Widening

`int` → `float` and `float` → `double` are **not** implicit. Explicit conversion (`to_float`, `to_double`) is required.

### 13.3. `void` Parameter Type

`void x` as a parameter is accepted at parse time but rejected at semantic time (`1558`). §1.4 documents this.

### 13.4. No Field Assignment

`x.field = value` is rejected at parse time (SNAR-A3 §8.4.2, §14.3).

### 13.5. `IknowIdo` Is Opaque

`IknowIdo { … }` blocks are not analyzed. Identifiers declared inside are not visible outside; identifiers used inside are not checked.

### 13.6. `includeC` Is Opaque

`includeC ~~~ ... ~~~` blocks are not analyzed. The raw C code is passed through.

### 13.7. `to_*` Arguments Not Checked

`to_int("hello")`, `to_int(null)`, etc. parse and analyze without error. The runtime conversion is implementation-defined.

### 13.8. `getConfigField` Type

`getConfigField(name)` returns `any`, regardless of the actual field type.

### 13.9. Union Reset Is Conservative

Any control-flow construct resets union current types. This is conservative: `if (x) { y = 1 } else { y = "s" }` leaves `y`'s current type unknown, even though the two branches assign concrete types.

### 13.10. Error Codes Are Informative

The numeric codes (`1507`, `0614`, etc.) are implementation-defined and may change. The **conditions** are normative.

### 13.11. `await` on Non-Promise

The reference implementation does **not** verify that `await x` is applied to a promise variable. `await someInt` parses and analyzes without error.

### 13.12. `Promise` Value Type Check

The reference implementation compares `Promise[...]`'s value type to the async function's return type. `async int f() { Promise[0] }` is OK; `async int f() { Promise["x"] }` is `0669`.

### 13.13. Fire-and-Forget Args

Fire-and-forget async calls check argument count and types (§7.3) but do not check that the return value is used correctly (there is no return value to check).
