# SNAR-A2

## Skorpion Norms And Rules, A generation. Standard A2

### Vocabulary of the Skorpion Programming Language

---

## 1. Scope

**1.1.** This standard defines the lexical structure (*vocabulary*) of the Skorpion programming language.

**1.2.** This standard specifies:

- a) rules for reading source text;
- b) rules for separating tokens;
- c) types of tokens and their forms;
- d) rules for handling lexical errors and warnings;
- e) the lexical grammar of the language.

**1.3.** This standard does **not** specify:

- a) syntactic rules — see **SNAR-A3**;
- b) semantic rules — see **SNAR-A4**;
- c) implementation details of any particular compiler.

**1.4.** In case of any conflict between this standard and other documents of the SNAR-A generation regarding the vocabulary, this standard takes precedence.

---

## 2. Conformance

**2.1.** A conforming implementation **SHALL** accept every source text that this standard declares valid.

**2.2.** A conforming implementation **SHALL** reject every source text that this standard declares invalid, or emit the diagnostic required by this standard.

**2.3.** A conforming implementation **MAY** emit additional warnings.

**2.4.** A conforming implementation **SHALL** report the position of each token exactly as specified in **§5.3**.

**2.5.** This standard uses the keywords **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** as defined in RFC 2119.

## 4. Terms and Definitions

**Source text** — an ordered sequence of characters encoding a program in the Skorpion language. See **§5.1**.

**Line terminator** — the character U+000A (Line Feed), which terminates a line of source text. See **§5.2**.

**Position** — a pair *(line, column)* describing the location of a character in source text. See **§5.3**.

**Lexeme** — a contiguous sequence of source characters forming a single token.

**Token** — the smallest lexical unit of the language, produced from a lexeme and characterized by a type and a position.

**Whitespace** — source characters whose only purpose is to separate tokens. See **§7.1**.

**Comment** — source characters that are ignored by the lexer. See **§7.2–7.3**.

**Vocabulary** — the set of all possible token types.

**Lexical error** — a violation of this standard that prevents the source text from being fully lexed.

**Lexical warning** — a recoverable violation of this standard after which lexing continues with a defined token.

**Maximal munch** — the rule that each token is formed from the longest possible contiguous sequence of source characters matching a valid token form. See **§9**.

## 5. Source Text

### 5.1. Character Encoding

**5.1.1.** Source text **SHALL** be interpreted as a sequence of characters encoded in **UTF-8**.

**5.1.2.** The behavior of a conforming implementation on source text that is not valid UTF-8 is **undefined** by this standard.

**5.1.3.** A byte order mark (U+FEFF) at the start of a source text **SHALL NOT** be considered valid vocabulary and **SHALL** be reported as an unknown character (see **§10**).

### 5.2. Line Terminators

**5.2.1.** Only the character **U+000A (Line Feed)** terminates a line of source text.

**5.2.2.** The character **U+000D (Carriage Return)** **SHALL NOT** terminate a line and **SHALL** be treated as whitespace (see **§7.1**).

**5.2.3.** Consequently, source text using the CRLF sequence (`\r\n`) is handled correctly: `\r` is whitespace; `\n` terminates the line.

**5.2.4.** The last line of a source text need not end with a line terminator.

### 5.3. Positions

**5.3.1.** A *position* is a pair *(line, column)* of positive integers.

**5.3.2.** The first line of a source text has line number **1**.

**5.3.3.** The first character of a line has column number **1**.

**5.3.4.** The line number **SHALL** be incremented by one for each line terminator that has been passed.

**5.3.5.** The column number **SHALL** be incremented by one for each character of the current line that has been passed.

**5.3.6.** Every token **SHALL** report the position of **its first character** — never the position of its last character, nor a position after it.

**5.3.7.** A token **SHALL NOT** report a column number pointing at an interior character of a multi-character source element (e.g., a multi-byte UTF-8 character). Columns are counted in Unicode code points.

## 6. Lexical Grammar

### 6.1. Overview

**6.1.1.** The lexical grammar transforms a source text into a sequence of tokens.

**6.1.2.** Every source text **SHALL** end with the special token `EOF`, which has no lexeme and whose position is the position immediately after the last source character.

**6.1.3.** Between any two tokens, whitespace and comments **MAY** appear (see **§7**).

**6.1.4.** Whitespace and comments themselves **SHALL NOT** be emitted as tokens.

### 6.2. Grammar Notation

**6.2.1.** In this standard, a lexical rule has the form

```
Name :: Production
```

where `Name` is a nonterminal and `Production` is a sequence of terminals (source characters), nonterminals, or repetition/alternative operators:

- `A?` — an optional occurrence of `A`;
- `A*` — zero or more occurrences of `A`;
- `A+` — one or more occurrences of `A`;
- `A | B` — an alternative of `A` and `B`;
- `[A-Za-z]` — a character class;
- `"abc"` — a literal sequence of characters.

**6.2.2.** Terminals are written in `code font`.

---

## 7. Whitespace and Comments

### 7.1. Whitespace

**7.1.1.** Whitespace is any of:

- Space `U+0020`;
- Horizontal Tabulation `U+0009`;
- Carriage Return `U+000D`;
- Line Feed `U+000A`.

**7.1.2.** Any sequence of whitespace characters **SHALL** be ignored (except insofar as it separates tokens and updates positions — see **§5.2–5.3**).

**7.1.3.** The lexical grammar of whitespace is:

```
WhiteSpace :: (" " | "\t" | "\r" | "\n")+
```

### 7.2. Line Comments

**7.2.1.** A line comment begins with `//` and ends at, but does not include, the next line terminator or the end of source text.

**7.2.2.** The lexical grammar of a line comment is:

```
LineComment :: "//" (SourceCharacter except "\n")*
```

**7.2.3.** A line comment **SHALL NOT** be emitted as a token.

### 7.3. Block Comments

**7.3.1.** A block comment begins with `/*` and ends with the first subsequent `*/`.

**7.3.2.** The lexical grammar of a block comment is:

```
BlockComment :: "/*" (SourceCharacter except "*/")* "*/"
```

**7.3.3.** If a block comment is not terminated by `*/` before the end of source text, it is a **lexical error** (code **`0104`**). The behavior afterwards is **undefined**; a conforming implementation **SHALL** emit the diagnostic.

**7.3.4.** A block comment **SHALL NOT** be emitted as a token.

**7.3.5.** Block comments **SHALL NOT** nest.

## 8. Tokens

### 8.1. Token Classification

**8.1.1.** The vocabulary of Skorpion consists of the following token types:

| Class | Description | Reference |
|-------|-------------|-----------|
| Identifier | User-defined names | **§8.2** |
| Keyword | Reserved words | **§8.3** |
| Numeric literal | Numbers | **§8.4** |
| String literal | Double-quoted strings | **§8.5** |
| Character literal | Single-quoted characters | **§8.6** |
| Unicode literal | Unicode code points | **§8.7** |
| Version literal | `@x.y.z` specifiers | **§8.8** |
| Raw code block | `~…~~~` C code blocks | **§8.9** |
| Punctuator | Operators and delimiters | **§8.10** |
| End of file | Termination marker | **§6.1.2** |

**8.1.2.** Keywords, identifiers, and punctuators are **case-sensitive**.

### 8.2. Identifiers

**8.2.1.** An identifier is a name not equal to any keyword (see **§8.3**).

**8.2.2.** The lexical grammar of an identifier is:

```
IdentifierStart :: [A-Za-z_] 
IdentifierPart  :: IdentifierStart | [0-9]
Identifier      :: IdentifierStart IdentifierPart*
```

**8.2.3.** The current revision of this standard restricts identifier characters to ASCII. Support for non-ASCII identifier characters is reserved for future revisions.

**8.2.4.** A lexeme matching the identifier grammar that is equal to one of the keywords in **§8.3** **SHALL** be tokenized as that keyword, not as an identifier.

### 8.3. Keywords

**8.3.1.** The following lexemes are reserved keywords and **SHALL** be tokenized as such:

| Group | Keywords |
|-------|----------|
| Control flow | `if`, `elsif`, `else`, `case`, `for`, `in`, `while`, `do`, `break`, `continue`, `return` |
| Declarations | `const`, `use`, `func`, `type`, `new` |
| Type names | `void`, `int`, `float`, `double`, `bool`, `char`, `string`, `arr`, `dict`, `any`, `T` |
| Literals | `null`, `true`, `false` |
| Concurrency | `async`, `await`, `Promise` |
| Errors | `Error`, `throw`, `try`, `catch`, `as` |
| Augmentation | `IknowIdo` |

**8.3.2.** The lexeme `includeC` **SHALL** be tokenized as a distinct token type (`INCLUDE_C`) and **SHALL NOT** be tokenized as either a keyword or an identifier.

**8.3.3.** A keyword **SHALL NOT** be used as an identifier.

**8.3.4.** The `includeC` token **SHALL NOT** be used as an identifier.

### 8.4. Numeric Literals

**8.4.1.** The lexical grammar of a numeric literal is:

```
Digit        :: [0-9]
Sign         :: "-"?
IntegerPart  :: Digit+
FractionPart :: "." Digit+
FloatSuffix  :: ("f" | "F")?
Numeric      :: Sign IntegerPart FractionPart? FloatSuffix?
```

**8.4.2.** A numeric literal **SHALL NOT** contain any of the following:

- a) a leading `+`;
- b) decimal exponents (`e` / `E`);
- c) hexadecimal, octal, or binary prefixes;
- d) numeric separators (e.g., `_`).

**8.4.3.** The optional `Sign` **SHALL** be treated as part of the numeric literal **if and only if** the character `-` is immediately followed by a `Digit`.

- `-5` — one numeric literal;
- `-5f` — one numeric literal;
- `-x` — punctuator `-` followed by identifier `x`;
- `--5` — punctuator `--` followed by numeric literal `5`.

**8.4.4.** A `.` **SHALL** be part of the fractional part **if and only if** it is immediately followed by a `Digit`. Otherwise, `.` is a separate punctuator.

- `1.5` — one numeric literal;
- `1.` — numeric literal `1` followed by punctuator `.`;
- `1.5.6` — numeric literal `1.5` followed by punctuator `.` followed by numeric literal `6`.

**8.4.5.** The `FloatSuffix` (`f` or `F`), if present, **SHALL** be interpreted as part of the numeric literal regardless of whether a fraction was present.

**8.4.6.** A numeric literal whose lexeme ends with `f` or `F` has the *static type* `float`.

**8.4.7.** A numeric literal whose lexeme contains a decimal point but no `f`/`F` suffix has the *static type* `double`.

**8.4.8.** A numeric literal whose lexeme contains neither a decimal point nor an `f`/`F` suffix has the *static type* `int`.

**8.4.9.** Consequence: a `-` that follows a numeric literal without intervening whitespace may start a new numeric literal. Implementations **SHALL** lex `5-3` as the numeric literal `5` followed by the numeric literal `-3`, whereas `5 - 3` **SHALL** be lexed as `5`, punctuator `-`, `3`.

### 8.5. String Literals

**8.5.1.** The lexical grammar of a string literal is:

```
StringChar    :: SourceCharacter except `"`, `\`, and the line terminator
StringEscape  :: "\" EscapeChar
EscapeChar    :: "n" | "t" | "r" | "0" | "\\" | "\"" | "'" | "a" | "b" | "f" | "v"
String        :: '"' (StringChar | StringEscape)* '"'
```

**8.5.2.** A string literal **SHALL NOT** contain an unescaped line terminator.

**8.5.3.** The escape sequences **SHALL** be interpreted as follows:

| Escape | Resulting character |
|--------|---------------------|
| `\n` | U+000A (Line Feed) |
| `\t` | U+0009 (Horizontal Tab) |
| `\r` | U+000D (Carriage Return) |
| `\0` | U+0000 (Null) |
| `\\` | U+005C (Backslash) |
| `\"` | U+0022 (Double Quote) |
| `\'` | U+0027 (Single Quote) |
| `\a` | U+0007 (Bell) |
| `\b` | U+0008 (Backspace) |
| `\f` | U+000C (Form Feed) |
| `\v` | U+000B (Vertical Tab) |

**8.5.4.** An escape sequence not listed in **§8.5.3** constitutes a **lexical warning** (code **`0105`**). The value of the string literal **SHALL** retain the two characters `\` and the escape character itself.

**8.5.5.** An unterminated string literal — i.e., one that ends before finding a matching `"` — constitutes a **lexical error** (code **`0102`**). The behavior afterwards is **undefined**.

**8.5.6.** A string literal's *static type* is `string`.

### 8.6. Character Literals

**8.6.1.** The lexical grammar of a character literal is:

```
CharContent   :: SourceCharacter except `'`, `\`, and the line terminator
CharEscape    :: "\" EscapeChar     (same EscapeChar as in §8.5)
CharLiteral   :: "'" (CharContent | CharEscape) "'"
```

**8.6.2.** A character literal **SHALL** contain exactly one source character or one escape sequence between its quotes.

**8.6.3.** Escape sequences in character literals **SHALL** be interpreted identically to those in string literals (**§8.5.3**).

**8.6.4.** An unknown escape sequence in a character literal constitutes a **lexical warning** (code **`0111`**). The value of the character literal **SHALL** be the escaped character itself (not the two-character sequence).

**8.6.5.** A character literal not terminated by `'` constitutes a **lexical error** (code **`0112`**).

**8.6.6.** A character literal's *static type* is `char`.

**8.6.7.** A character literal **SHALL** represent exactly one byte of a UTF-8 code unit. Multi-byte Unicode characters **SHALL** be expressed using a Unicode literal (**§8.7**).

### 8.7. Unicode Literals

**8.7.1.** The lexical grammar of a Unicode literal is:

```
HexDigit       :: [0-9A-Fa-f]
UnicodeLiteral :: "Unicode" "[" '"' HexDigit+ '"' "]"
```

**8.7.2.** The `Unicode` introducer **SHALL** be interpreted as the beginning of a Unicode literal **if and only if** it is immediately followed by `[`.

**8.7.3.** If the source text contains `Unicode` **not** immediately followed by `[`, it **SHALL** be tokenized as an identifier.

**8.7.4.** The hexadecimal sequence inside a Unicode literal **SHALL** be interpreted as a Unicode code point.

**8.7.5.** A Unicode literal has *static type* `char`.

**8.7.6.** The following conditions constitute lexical errors:

| Code | Condition |
|------|-----------|
| `0120` | `Unicode` not followed by `[` |
| `0121` | `[` not followed by `"` |
| `0122` | Unicode literal not terminated by `"` |
| `0123` | `"` not followed by `]` |

**8.7.7.** Validation of the hexadecimal sequence as a legal Unicode code point (not exceeding U+10FFFF, not within the surrogate range D800–DFFF) is a semantic property; it is deferred to the syntactic stage (**SNAR-A3**).

### 8.8. Version Literals

**8.8.1.** The lexical grammar of a version literal is:

```
Version :: "@" Digit+ ("." Digit+)*
```

**8.8.2.** The version literal is used exclusively in `use lib:` declarations (see **SNAR-A3**).

**8.8.3.** The lexeme of a version literal **SHALL** include the leading `@`.

**8.8.4.** An `@` not immediately followed by a decimal digit constitutes a **lexical error** (code **`0127`**).

**8.8.5.** Version suffix components such as `-dev`, `-rc1`, or `+build.123` are **not part of this standard**. Only the numeric `x.y.z` form is a version literal; any additional suffixes are tokenized separately.

### 8.9. Raw Code Blocks (Tilde Blocks)

**8.9.1.** A raw code block is a sequence of characters enclosed in `~` or `~~` or `~~~` markers:

```
TildeOpen  :: "~~~" | "~~" | "~"
TildeClose :: "~~~"
TildeBlock :: TildeOpen (SourceCharacter)* TildeClose
```

**8.9.2.** A raw code block **SHALL** be terminated by the first subsequent occurrence of `~~~`.

**8.9.3.** The *value* of the raw code block is its enclosed content with leading and trailing whitespace removed.

**8.9.4.** The `TildeBlock` token **SHALL** carry the position of the leading `~`.

**8.9.5.** An unterminated raw code block constitutes a **lexical error** (code **`0103`**).

**8.9.6.** Raw code blocks are used only in `includeC` statements (see **SNAR-A3**).

### 8.10. Punctuators

**8.10.1.** The punctuators of the Skorpion language are the following lexemes:

| Category | Punctuators |
|----------|-------------|
| Grouping | `(` `)` `{` `}` `[` `]` |
| Separators | `,` `;` `:` |
| Member access | `.` |
| Range | `..` `...` |
| Arithmetic | `+` `-` `*` `/` `%` `**` `^` |
| Comparison | `<` `<=` `>` `>=` `==` `!=` |
| Logical | `&&` `\|\|` `!` |
| Bitwise/reference | `&` |
| Assignment | `=` `+=` `-=` `*=` `/=` `%=` `**=` |
| Increment/decrement | `++` `--` |
| Ternary | `?` |
| Unary reference | `#` |
| Interpolation | `$` |
| Version introducer | `@` (see **§8.8**) |
| Tilde block introducer | `~` (see **§8.9**) |

**8.10.2.** The single character `|` (U+007C) **SHALL NOT** be a valid token. Occurrence of `|` not immediately followed by `|` constitutes a **lexical error** (code **`0101`**).

**8.10.3.** The single character `&` **SHALL** be tokenized as an independent punctuator, not only as part of `&&`.

**8.10.4.** `**` is the exponentiation operator; `**=` is exponentiation-assignment. The `^` punctuator is **not** the exponentiation operator; it begins a format specifier (see **SNAR-A3**).

## 9. Token Separation and Maximal Munch

**9.1.** The lexer **SHALL** produce tokens in source order.

**9.2.** After skipping any whitespace and comments, the lexer **SHALL** consume the longest possible sequence of characters that forms a valid token (maximal munch).

**9.3.** Consequences of maximal munch:

- `++` **SHALL** be lexed as one `++` punctuator, not two `+` punctuators.
- `+=` **SHALL** be lexed as one `+=` punctuator.
- `**=` **SHALL** be lexed as one `**=` punctuator, **not** as `**` followed by `=`.
- `..` **SHALL** be lexed as one `..` punctuator; `...` **SHALL** be lexed as one `...` punctuator.
- `@1.2.3` **SHALL** be lexed as one version literal.

**9.4.** Two adjacent tokens that do not require a whitespace separator **MAY** be written without intervening whitespace only where the maximal munch rule preserves their intended token boundaries. Otherwise, a whitespace separator is required.

**9.5.** The reader is advised that **§8.4.3** and **§8.4.4** create certain non-obvious consequences:

- `x-5` — identifier `x` followed by numeric literal `-5`;
- `x - 5` — identifier `x`, punctuator `-`, numeric literal `5`;
- `a+++b` — identifier `a`, punctuator `++`, punctuator `+`, identifier `b`;
- `1..5` — numeric literal `1`, punctuator `..`, numeric literal `5`.

## 10. Error Handling

### 10.1. Lexical Errors

**10.1.1.** A conforming implementation **SHALL** emit a diagnostic for every lexical error described in this standard.

**10.1.2.** After a lexical error, the implementation **SHALL NOT** produce the token that would have resulted from the malformed lexeme, unless the error description specifically states otherwise.

**10.1.3.** An implementation **MAY** continue lexing after certain recoverable errors as specified in the error's description. Nevertheless, the source text **SHALL** be considered invalid.

**10.1.4.** The complete list of lexical errors in this standard is:

| Code | Description | Recoverable |
|------|-------------|-------------|
| `0100` | Unknown character | Yes (skip and continue) |
| `0101` | Unknown character `\|` | Yes (skip and continue) |
| `0102` | Unterminated string literal | No |
| `0103` | Unterminated tilde block | No |
| `0104` | Unterminated block comment | No |
| `0110` | Unterminated character literal (empty) | No |
| `0112` | Expected closing `'` in character literal | No |
| `0120` | Expected `[` after `Unicode` | No |
| `0121` | Expected `"` in `Unicode[...]` | No |
| `0122` | Unterminated Unicode literal | No |
| `0123` | Expected `]` after `Unicode[...]` | No |
| `0127` | Expected version number after `@` | No |

### 10.2. Lexical Warnings

**10.2.1.** A lexical warning is not an error; lexing continues and the token is produced.

**10.2.2.** The complete list of lexical warnings in this standard is:

| Code | Description | Behavior |
|------|-------------|----------|
| `0105` | Unknown escape sequence in string | Retain `\X` as two characters |
| `0111` | Unknown escape sequence in character | Retain `X` as one character |

## 11. Lexical Grammar (Summary)

The complete lexical grammar of the Skorpion language, in BNF notation, is the following.

```
Program       ::= Token*
Token         ::= Identifier
                | Keyword
                | INCLUDE_C
                | Numeric
                | String
                | Character
                | UnicodeLiteral
                | Version
                | TildeBlock
                | Punctuator
                | EOF

Identifier    ::= IdentifierStart IdentifierPart*
IdentifierStart ::= [A-Za-z_]
IdentifierPart  ::= IdentifierStart | [0-9]

Keyword       ::= "use" | "const" | "func" | "if" | "elsif" | "else" | "case"
                | "for" | "in" | "while" | "do" | "break" | "continue"
                | "return" | "type" | "void" | "int" | "float" | "double"
                | "bool" | "char" | "string" | "arr" | "dict" | "any" | "T"
                | "null" | "true" | "false"
                | "async" | "await" | "Promise"
                | "new" | "Error" | "throw" | "try" | "catch" | "as"
                | "IknowIdo"

Numeric       ::= "-"? Digit+ ("." Digit+)? ("f" | "F")?

String        ::= '"' StringItem* '"'
StringItem    ::= SourceCharacter except '"' and '\' and '\n'
                | "\" EscapeChar

Character     ::= "'" CharItem "'"
CharItem      ::= SourceCharacter except "'" and '\' and '\n'
                | "\" EscapeChar

EscapeChar    ::= "n" | "t" | "r" | "0" | "\\" | "\"" | "'"
                | "a" | "b" | "f" | "v"

UnicodeLiteral ::= "Unicode" "[" '"' [0-9A-Fa-f]+ '"' "]"

Version       ::= "@" Digit+ ("." Digit+)*

TildeBlock    ::= ("~~~" | "~~" | "~") (SourceCharacter)* "~~~"

Punctuator    ::= "(" | ")" | "{" | "}" | "[" | "]"
                | "," | ";" | ":" | "."
                | ".." | "..."
                | "+" | "-" | "*" | "/" | "%" | "**" | "^"
                | "<" | "<=" | ">" | ">=" | "==" | "!="
                | "&&" | "||" | "!"
                | "&"
                | "=" | "+=" | "-=" | "*=" | "/=" | "%=" | "**="
                | "++" | "--"
                | "?" | "#" | "$"

LineComment   ::= "//" (SourceCharacter except '\n')*
BlockComment  ::= "/*" (SourceCharacter except "*/")* "*/"

WhiteSpace    ::= (" " | "\t" | "\r" | "\n")+
```

**Note.** The grammar above is *lexical*, not *syntactic*. In particular, the placement of whitespace between tokens, as well as the alternation between tokens and whitespace, is described in **§7–§9**.
