# SNAR-A2

## Skorpion Norms And Rules, A generation. Standard A2

This standard defines the **lexis** (vocabulary) of the Skorpion programming language with the `*.sk` extension. It describes how a Skorpion source file is decomposed into a stream of tokens.

The rules of this standard are normative. Informative notes are explicitly marked as such. A rule that references a Common Rule does not restate it.

## 0. Common Rules

The rules of this section are referenced from other sections. They are normative. A rule in Sections 1–12 that references a Common Rule does not restate it.

### R-C1. Rule of Source File

A Skorpion source file is a sequence of bytes encoded in **UTF-8** with the extension `*.sk`.

A source file consists of zero or more lines.

A line is a maximal contiguous sequence of characters that does not contain a LineFeed character or a CarriageReturn character.

The line-ending character(s) are not part of the line content.

### R-C2. Rule of Position

Every token has a **position** consisting of a **line** number and a **column** number.

Line numbers are **1-based**. Column numbers are **1-based**.

A position refers to the character at which the token begins.

### R-C3. Rule of Line Endings

A **LineFeed** character (LF, U+000A), a **CarriageReturn followed by a LineFeed** character (CRLF, U+000D U+000A), and a **lone CarriageReturn** character (CR, U+000D) are **equivalent** as line endings.

A lone CarriageReturn that is not followed by a LineFeed is **both** a line ending and a whitespace character.

Line endings are **not part of any token**.

### R-C4. Rule of Token Stream

A Skorpion source file is decomposed into a stream of **tokens** by the **lexer**.

Every character of the source file belongs to exactly one of the following:
- whitespace (Section 2);
- a comment (Section 3);
- a token (Sections 4–8).

The token stream always ends with the **EOF token** (Section 9.3).

### R-C5. Rule of Token Atomicity

A token is a contiguous sequence of characters.

A token is **atomic**: no rule of this standard may split a token into smaller tokens or merge two adjacent tokens into one.

### R-C6. Rule of Error Reporting

A lexical violation is reported by the lexer with a **code**, a **line**, and a **column**.

Lexical violations are of two kinds:
- **errors** — they are fatal and the compilation does not continue;
- **warnings** — they are non-fatal and the compilation continues.

The standard does **not** define specific error codes; codes are implementation-defined.

### 1.2. Rule of Token Categories

The Skorpion lexer produces tokens of the following **categories**:

- **identifier** (Section 4);
- **keyword** (Section 5);
- **number literal** (Section 6.1);
- **string literal** (Section 6.2);
- **char literal** (Section 6.3);
- **unicode literal** (Section 6.4);
- **version literal** (Section 6.5);
- **tilde block** (Section 7);
- **operator or punctuation** (Section 8);
- **EOF** (Section 9.3).

A single token belongs to exactly one category.

## 2. Whitespace

### 2.1. Rule of Whitespace Characters

The **whitespace characters** are:
- Space (U+0020);
- Tab (U+0009);
- LineFeed (U+000A);
- CarriageReturn (U+000D).

### 2.2. Rule of Whitespace Insignificance

Whitespace characters are **insignificant** between tokens: the lexer skips them and produces no token for them.

Whitespace characters are **significant** inside string literals and char literals (Sections 6.2 and 6.3).

### 2.3. Rule of Whitespace Permitted Positions

Whitespace characters may be placed in any position **between** tokens.

Whitespace characters may **not** be placed inside a token (R-C5).

### 2.4. Rule of Whitespace Within Comments

Whitespace characters are part of a comment's content and are **insignificant** for the lexer.

## 3. Comments

### 3.1. Rule of Single-Line Comments

A **single-line comment** starts with the sequence `//` and ends with a LineFeed character or with the end of the file.

A single-line comment produces **no token**.

#### 3.1.1. Rule of Comment Content

The content of a single-line comment is **insignificant**.

A single-line comment may contain any character except a LineFeed character.

### 3.2. Rule of Multi-Line Comments

A **multi-line comment** starts with the sequence `/*` and ends with the sequence `*/`.

A multi-line comment produces **no token**.

#### 3.2.1. Rule of Multi-Line Comment Content

The content of a multi-line comment may contain any character, including LineFeed characters.

#### 3.2.2. Rule of Multi-Line Comment Closure

A multi-line comment that is not closed by `*/` is **invalid** and **does not conform to this standard**.

### 3.3. Rule of Comment Nesting Prohibition

Comments **cannot** be nested. The first `*/` sequence closes the multi-line comment, even if it is inside another multi-line comment.

The sequence `/*` inside a multi-line comment is **literal** and does **not** start a new comment.

The sequence `//` inside a multi-line comment is **literal** and does **not** start a single-line comment.

The sequence `/*` inside a single-line comment is **literal** and does **not** start a multi-line comment.

## 4. Identifiers

### 4.1. Rule of Identifier Form

An **identifier** is a sequence of characters from the set:
- `A`–`Z`;
- `a`–`z`;
- `0`–`9`;
- `_` (underscore).

An identifier **cannot** be empty.

The first character of an identifier is from the set `A`–`Z`, `a`–`z`, `_`. The first character **cannot** be a digit.

The first character of an identifier is a **letter** if it is from `A`–`Z` or `a`–`z`; it is an **underscore** if it is `_`.

### 4.2. Rule of Identifier Case

Identifiers are **case-sensitive**. `name`, `Name`, and `NAME` are three different identifiers.

### 4.3. Rule of Identifier Keyword Conflict

An identifier whose text is identical to a **keyword** (Section 5) is **not** an identifier. It is a **keyword token**.

The lexer resolves the conflict by **longest match followed by keyword lookup**. The sequence of characters is first read as an identifier; then the text is looked up in the keyword table. If a match is found, the token is a keyword; otherwise, it is an identifier.

### 4.4. Rule of Unicode Identifier Special Case

An identifier that begins with the literal sequence `Unicode` is treated specially: if the character immediately after `Unicode` is `[` (LBracket), the lexer produces a **unicode literal** token (Section 6.4) instead of an identifier.

If the character after `Unicode` is any other character, the sequence is read as an ordinary identifier.

#### 4.4.1. Rule of Unicode Name Reservation

The identifier `Unicode` followed immediately by `[` is **reserved** for the unicode literal syntax. A user-defined variable, function, or parameter named `Unicode` **cannot** be used with array-indexing syntax `Unicode[...]`, because the sequence `Unicode[` is always interpreted as the start of a unicode literal.

## 5. Keywords

### 5.1. Rule of Keyword Recognition

A **keyword** is a reserved word recognized by the lexer from the identifier text.

Keywords are **case-sensitive**. `if` is a keyword; `IF` and `If` are identifiers.

### 5.2. Rule of Reserved Keywords

The set of keywords is **closed**. The standard does **not** reserve any other word by prefix, suffix, or pattern.

#### 5.3.1. Rule of the `includeC` Token

The keyword `includeC` produces a token of a **separate type** (`TOKEN_INCLUDE_C`), not of the generic `TOKEN_KEYWORD` type. The token text is the literal `includeC`.

#### 5.3.2. Rule of `true` and `false`

The keywords `true` and `false` are lexed as keywords. In the parser, they are treated as identifier expressions (see SNAR-A3).

#### 5.3.3. Rule of `T`

The keyword `T` is a special marker for union types in the parser (see SNAR-A3). It is not a general type keyword.

### 5.4. Rule of Unused Keywords

The keyword `func` is **reserved for future use** and is currently not consumed by the parser. A source file containing the `func` keyword outside of a comment or string **conforms lexically**, but the parser may reject it.

## 6. Literals

### 6.1. Rule of Number Literals

A **number literal** consists of:
1. an optional leading Minus character (`-`);
2. one or more decimal digits (`0`–`9`);
3. an optional fractional part consisting of a Dot character (`.`) followed by one or more decimal digits;
4. an optional suffix character `f` or `F`.

#### 6.1.1. Rule of Number Literal Form

A number literal **cannot** be empty.

A number literal **cannot** begin with a Plus character.

A number literal **cannot** contain an exponent part (`e` or `E`).

A number literal **cannot** contain hexadecimal, binary, or octal notation.

A number literal **cannot** contain underscores (`_`) as digit separators.

The fractional part requires at least one digit after the Dot. The sequence `5.` is **not** a number literal; it is the number literal `5` followed by the Dot operator.

#### 6.1.2. Rule of the Leading Minus

A Minus character is part of a number literal **if and only if** the character immediately after the Minus is a decimal digit.

Otherwise, the Minus character is the **Minus operator** (Section 8).

#### 6.1.3. Rule of Number Literal Type Classification

The type of a number literal is determined by its syntax:
- a literal ending in `f` or `F` has type `float`;
- a literal containing a Dot has type `double`;
- otherwise, the literal has type `int`.

#### 6.1.4. Rule of Number Literal Atomicity

A number literal is a single token. It cannot be split into two tokens.

#### 6.1.5. Rule of Minus Ambiguity

Because of Rule 6.1.2, the sequence `a-5` is lexed as **two** tokens: the identifier `a` followed by the number literal `-5`. It is **not** lexed as the identifier `a`, the Minus operator, and the number literal `5`.

To obtain the Minus operator after an identifier, a whitespace character must be placed between the Minus and the following digit: `a - 5` is lexed as the identifier `a`, the Minus operator, and the number literal `5`.

This rule is **normative** and **intentional**.

### 6.2. Rule of String Literals

A **string literal** is a sequence of characters enclosed between two Quote characters (`"`).

#### 6.2.1. Rule of String Content

The content of a string literal may contain any character except an unescaped Quote character.

Whitespace characters (including LineFeed and CarriageReturn) are **permitted** inside a string literal and are part of the string value.

#### 6.2.2. Rule of String Enclosure

A string literal begins with a Quote character and ends with a Quote character.

A string literal that is not closed by a Quote character is **invalid** and **does not conform to this standard**.

#### 6.2.3. Rule of String Escape Sequences

A Backslash character inside a string literal begins an **escape sequence**.

The escape sequences are defined in Section 10.

#### 6.2.4. Rule of String Line Counting

An implementation **should** correctly increment the line counter when a LineFeed character appears inside a string literal.

An implementation that does not increment the line counter inside a string literal is **conformant** for valid inputs, but line numbers in error messages may be incorrect for tokens that follow a multi-line string.

### 6.3. Rule of Char Literals

A **char literal** is a sequence enclosed between two Apostrophe characters (`'`).

#### 6.3.1. Rule of Char Content

A char literal contains exactly **one character** after the opening Apostrophe.

If the character after the opening Apostrophe is a Backslash, the Backslash begins an escape sequence (Section 10). The escape sequence produces exactly **one** character.

#### 6.3.2. Rule of Char Enclosure

A char literal begins with an Apostrophe and ends with an Apostrophe.

A char literal that is not closed by an Apostrophe is **invalid** and **does not conform to this standard**.

#### 6.3.3. Rule of Char Content Length

A char literal that contains more than one character (after resolving escape sequences) is **invalid** and **does not conform to this standard**.

### 6.4. Rule of Unicode Literals

A **unicode literal** is a sequence of the form:

`Unicode` `[` `"` `hex-digits` `"` `]`

where `hex-digits` is one or more hexadecimal digits (`0`–`9`, `A`–`F`, `a`–`f`).

#### 6.4.1. Rule of Unicode Literal Closure

A unicode literal that is not closed by `]` is **invalid** and **does not conform to this standard**.

#### 6.4.2. Rule of Unicode Codepoint Range

The hexadecimal value of a unicode literal **cannot** exceed `0x10FFFF`.

#### 6.4.3. Rule of Unicode Surrogate Prohibition

A unicode literal whose value lies in the surrogate range `0xD800`–`0xDFFF` is **invalid** and **does not conform to this standard**.

### 6.5. Rule of Version Literals

A **version literal** starts with the At character (`@`) followed by one or more digits and, optionally, further sequences of a Dot and one or more digits.

The form is:

`@` `digits` { `.` `digits` }

#### 6.5.1. Rule of Version Literal Minimum

A version literal **must** contain at least one digit after the At character.

The sequence `@` alone is **invalid** and **does not conform to this standard**.

#### 6.5.2. Rule of Version Literal Closure

The sequence of digits and Dots ends at the first character that is not a digit and not a Dot followed by a digit.

The sequence `@1.` is **not** a valid version literal; it is the version literal `@1` followed by the Dot operator.

#### 6.5.3. Rule of Version Suffix

A version literal **cannot** contain a suffix (such as `-dev`). The character after the version literal is lexed as a separate token.

## 7. Tilde Blocks

### 7.1. Rule of Tilde Block Form

A **tilde block** is a sequence of characters enclosed between an **opening** sequence of Tilde characters (`~`) and a **closing** sequence of Tilde characters.

#### 7.1.1. Rule of Tilde Block Opening

The opening sequence consists of **one**, **two**, or **three** Tilde characters.

#### 7.1.2. Rule of Tilde Block Closing

The closing sequence consists of **exactly three** Tilde characters (`~~~`).

#### 7.1.3. Rule of Tilde Block Closure

A tilde block that is not closed by `~~~` is **invalid** and **does not conform to this standard**.

### 7.2. Rule of Tilde Block Content

The content of a tilde block may contain any character, including LineFeed, CarriageReturn, Quote, Apostrophe, Backslash, and Tilde — **except** for the closing sequence `~~~`.

The sequence `~` (single Tilde) and `~~` (double Tilde) are **literal** inside a tilde block.

### 7.3. Rule of Tilde Block Trimming

The leading and trailing **whitespace** characters (Space, Tab, LineFeed, CarriageReturn) of the tilde block content are **removed**.

Whitespace characters **inside** the content (between non-whitespace characters) are **preserved**.

#### 7.3.1. Rule of Trimming Scope

Trimming applies only to the **boundaries** of the content. Interior whitespace is not affected.

### 7.4. Rule of Tilde Block Atomicity

A tilde block is a **single token**. It cannot be split into two tokens.

The content of a tilde block is **not** re-lexed. It is a raw text value.

### 7.5. Rule of Tilde Block Line Counting

An implementation **must** correctly increment the line counter when a LineFeed character appears inside a tilde block.

## 8. Operators and Punctuation

### 8.1. Rule of Operator Tokens

An **operator token** is a token whose category is "operator or punctuation" (Section 8.4).

Operators and punctuation are recognized by **longest match**: when several operator tokens begin with the same prefix, the longest token is chosen.

#### 8.1.1. Rule of Longest Match

The lexer **must** choose the longest possible token from the input.

For example, `**` is one token (the Pow operator), not two `*` tokens. `**=` is one token (the PowEq operator), not `**` followed by `=`.

### 8.2. Rule of Compound Operators

A **compound operator** is an operator token consisting of two or more characters.

The compound operators are:
- `**` (Pow);
- `**=` (PowEq);
- `++` (PlusPlus);
- `--` (MinusMinus);
- `==` (EqEq);
- `!=` (Neq);
- `<=` (Lte);
- `>=` (Gte);
- `+=` (PlusEq);
- `-=` (MinusEq);
- `*=` (StarEq);
- `/=` (SlashEq);
- `%=` (PercentEq);
- `&&` (And);
- `||` (Or);
- `..` (DotDot);
- `...` (Ellipsis).

### 8.3. Rule of Ambiguous Minus

The Minus character (`-`) has two possible interpretations:
- it is part of a **number literal** if the next character is a decimal digit;
- it is the **Minus operator** otherwise.

A Minus followed by another Minus produces the **MinusMinus** token (`--`).

A Minus followed by Equals produces the **MinusEq** token (`-=`).

#### 8.3.1. Rule of Ambiguity Resolution

The lexer **must** resolve the ambiguity as follows:
- if the next character after the Minus is a decimal digit, the Minus is part of a number literal;
- otherwise, if the next character is `-`, the token is `--`;
- otherwise, if the next character is `=`, the token is `-=`;
- otherwise, the token is `-`.

### 8.5. Rule of the Apostrophe Ambiguity

The Apostrophe character (`'`) begins a **char literal** (Section 6.3). It is **never** an operator.

A stray Apostrophe that does not begin a valid char literal is an **error**.

### 8.6. Rule of the Backtick

The Backtick character (`` ` ``) is part of the lexis but is **not** consumed by the current lexer. A Backtick in the source is an **error**.

The Backtick is **reserved for future use**.

### 8.7. Rule of the Vertical Bar

A single Vertical Bar (`|`) that is not followed by another Vertical Bar is an **error**.

The sequence `||` is the **Or** operator.

## 9. Tokens and Token Stream

### 9.1. Rule of Token Categories

The full set of token categories produced by the lexer:

- **IDENT** — identifier (Section 4);
- **KEYWORD** — keyword (Section 5);
- **NUMBER** — number literal (Section 6.1);
- **STRING** — string literal (Section 6.2);
- **CHARLIT** — char literal (Section 6.3);
- **UNICODE_LIT** — unicode literal (Section 6.4);
- **VERSION** — version literal (Section 6.5);
- **TILDE** — tilde block (Section 7);
- **INCLUDE_C** — the `includeC` keyword (Section 5.3.1);
- **operator / punctuation** — one of the tokens in Section 8.4;
- **EOF** — end of file (Section 9.3).

### 9.2. Rule of Token Table

| Token | Category | Value |
|-------|----------|-------|
| `TOKEN_IDENT` | identifier | the identifier text |
| `TOKEN_KEYWORD` | keyword | the keyword text |
| `TOKEN_NUMBER` | number | the literal text (including leading `-` and suffix) |
| `TOKEN_STRING` | string | the resolved string value |
| `TOKEN_CHARLIT` | char | the resolved char value as a single-character string |
| `TOKEN_UNICODE_LIT` | unicode | the hexadecimal digits |
| `TOKEN_VERSION` | version | the version text (including `@`) |
| `TOKEN_TILDE` | tilde | the trimmed block content |
| `TOKEN_INCLUDE_C` | includeC | the literal `includeC` |
| operator | operator | the operator literal |
| `TOKEN_EOF` | EOF | the empty string |

### 9.3. Rule of EOF Token

The **EOF token** is the last token in the token stream.

The EOF token has category **EOF** and an empty literal.

The EOF token's position is the position immediately after the last character of the source file.

#### 9.3.1. Rule of EOF Presence

Every token stream contains **exactly one** EOF token.

#### 9.3.2. Rule of EOF Position

The EOF token is produced when the lexer has consumed all characters of the source file.

## 10. Escape Sequences

### 10.1. Rule of Escape Sequence Application

Escape sequences are recognized **only** inside:
- string literals (Section 6.2);
- char literals (Section 6.3).

Escape sequences are **not** recognized in:
- identifiers;
- keywords;
- number literals;
- unicode literals;
- version literals;
- tilde blocks;
- comments;
- operator tokens.

### 10.2. Rule of String Escape Sequences

Inside a string literal, a Backslash character followed by one of the characters in the table below produces the **escaped character**:

| Sequence | Result (codepoint) |
|----------|---------------------|
| `\n` | U+000A LineFeed |
| `\t` | U+0009 Tab |
| `\r` | U+000D CarriageReturn |
| `\0` | U+0000 Null |
| `\\` | U+005C Backslash |
| `\"` | U+0022 Quote |
| `\'` | U+0027 Apostrophe |
| `\a` | U+0007 Bell |
| `\b` | U+0008 Backspace |
| `\f` | U+000C Form Feed |
| `\v` | U+000B Vertical Tab |

#### 10.2.1. Rule of Unknown Escape in String

A Backslash followed by a character **not** in the table above is an **unknown escape sequence**.

An unknown escape sequence in a string produces a **warning** and is preserved **as-is**: both the Backslash and the following character are part of the string value.

Example: `"\q"` produces the string value `\q` (two characters), with a warning.

#### 10.2.2. Rule of Backslash at End of String

A Backslash at the very end of a string literal (i.e., immediately before the closing Quote) does **not** begin an escape sequence. It is a literal Backslash, followed by the closing Quote.

### 10.3. Rule of Char Escape Sequences

Inside a char literal, a Backslash followed by one of the characters in the table below produces the **escaped character**. The char literal contains exactly **one** resolved character.

| Sequence | Result (codepoint) |
|----------|---------------------|
| `\n` | U+000A LineFeed |
| `\t` | U+0009 Tab |
| `\r` | U+000D CarriageReturn |
| `\0` | U+0000 Null |
| `\\` | U+005C Backslash |
| `\"` | U+0022 Quote |
| `\'` | U+0027 Apostrophe |
| `\a` | U+0007 Bell |
| `\b` | U+0008 Backspace |
| `\f` | U+000C Form Feed |
| `\v` | U+000B Vertical Tab |

#### 10.3.1. Rule of Unknown Escape in Char

A Backslash followed by a character **not** in the table above is an **unknown escape sequence**.

An unknown escape sequence in a char literal produces a **warning** and the **following character** is used as the resolved character. The Backslash is **discarded**.

Example: `'\q'` produces the char `q`, with a warning.

#### 10.3.2. Rule of Divergence from String Behavior

The behavior of unknown escape sequences differs between string literals and char literals:
- in a **string**, the Backslash is preserved;
- in a **char literal**, the Backslash is discarded.

This divergence is **intentional** and **normative**.

### 10.4. Rule of Escape Sequence Table

The full set of escape sequences is the same for string literals and char literals (except for unknown escapes).

## 11. Conformance

### 11.1. Rule of Conformance

A `*.sk` file **conforms** to this standard if and only if all rules of Sections 1–10 are satisfied.

### 11.2. Rule of Non-Conformance

A `*.sk` file that violates at least one rule of this standard **does not conform** to this standard.

### 11.3. Rule of Partial Conformance

Partial conformance is **not defined** by this standard. A file either conforms or does not conform.

### 11.4. Rule of Violation

A record that violates any rule of this standard is **invalid** and **does not conform to this standard**.

The local formulation of this consequence within individual rules is **informative** and does not create additional rules.

### 12.2. Rule of Invalid Token Examples

The following tokens do **not** conform to this standard:

| Source text | Reason |
|-------------|--------|
| `@` alone | At must be followed by a digit |
| `@1.` | Trailing dot is not part of version |
| `'ab'` | Char literal contains more than one character |
| `''` | Char literal is empty |
| `'` alone | Char literal is unterminated |
| `"` alone | String literal is unterminated |
| `Unicode[""]` | Unicode literal has no hex digits |
| `Unicode["110000"]` | Codepoint exceeds 0x10FFFF |
| `Unicode["D800"]` | Surrogate codepoint |
| `Unicode[` (without `"`) | Unicode literal missing Quote |
| `/* unterminated` | Multi-line comment is not closed |
| `~~~ unterminated` | Tilde block is not closed |
| `\|` alone | Vertical bar must be doubled |
| `` ` `` alone | Backtick is reserved |
| `0x1F` | Hexadecimal literals are not supported |
| `0b101` | Binary literals are not supported |
| `1e5` | Exponent notation is not supported |
| `1_000` | Digit separators are not supported |
| `1..5` (as a single number) | Cannot be a single number literal |
| A file ending with an unclosed block comment | Comment closure required |

### 12.3. Rule of Lexically Valid Examples

A source file consisting **only** of the following is **lexically valid**:

```
// This is a comment
use foo

int main() {
    string name = "World"
    return 0
}
```

A source file consisting of **only** whitespace and comments is **lexically valid** and produces only the EOF token.

A source file that is **empty** is **lexically valid** and produces only the EOF token.

### 12.4. Rule of Lexically Invalid Examples

A source file containing any of the following sequences is **lexically invalid**:

- an unclosed string literal (`"abc`);
- an unclosed char literal (`'a`);
- an unclosed multi-line comment (`/* abc`);
- an unclosed tilde block (`~~~abc`);
- a stray Backtick (`` ` ``);
- a lone vertical bar (`a | b`);
- an unknown non-ASCII character outside a literal;
- a Unicode codepoint out of range in a unicode literal.

## 13. Token Grammar

### 13.1. Rule of Regular Grammar

The following grammar describes the **token forms** (not the full program). Each production defines one token category, using a regular-expression-like syntax.

```
identifier  = ( letter | "_" ) , { letter | digit | "_" } ;
letter      = "A".."Z" | "a".."z" ;
digit       = "0".."9" ;

number      = [ "-" ] , digit , { digit } ,
              [ "." , digit , { digit } ] ,
              [ "f" | "F" ] ;

string      = '"' , { string-char | escape } , '"' ;
string-char = ? any char except '"' and "\" ? ;
escape      = "\" , ( "n" | "t" | "r" | "0" | "\\" | '"' | "'" |
              "a" | "b" | "f" | "v" | ? any char (warning) ? ) ;

char        = "'" , ( char-char | escape ) , "'" ;
char-char   = ? any char except "'" and "\" ? ;

unicode     = "Unicode" , "[" , '"' , hex , { hex } , '"' , "]" ;
hex         = "0".."9" | "A".."F" | "a".."f" ;

version     = "@" , digit , { digit } , { "." , digit , { digit } } ;

tilde       = ( "~" | "~~" | "~~~" ) , { any-char-except-triple-tilde } , "~~~" ;

comment     = "//" , { any char except LF } , ( LF | EOF )
            | "/*" , { any char } , "*/" ;

whitespace  = " " | "\t" | "\r" | "\n" ;
```

### 13.2. Rule of Grammar Priority

Where the regular grammar in Section 13.1 and the textual rules of Sections 1–12 disagree, the **textual rules take priority**.

The grammar is **informative**.

### 13.3. Rule of Grammar Scope

The grammar in Section 13.1 defines the **lexical structure** of `*.sk` files.

The **syntactic structure** of Skorpion programs is defined by SNAR-A3.

The **semantics** of Skorpion programs is defined by SNAR-A4.
