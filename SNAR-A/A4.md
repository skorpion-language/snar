# SNAR-A4

## Skorpion Norms And Rules — Generation A — Standard A4

### Semantics of the Skorpion Programming Language

---

## 1. Scope

**1.1.** This standard defines the **semantics** of the Skorpion programming language — that is, the meaning of every syntactically valid construct (as defined in **SNAR-A3**), the properties that a conforming implementation **SHALL** enforce statically, and the observable behavior of a program at runtime.

**1.2.** This standard specifies:

- a) the program execution model;
- b) the scope and name-resolution rules;
- c) the types of the language and their compatibility;
- d) the meaning of function declarations, parameters, return values, and async functions;
- e) the meaning of variable and constant declarations;
- f) the meaning of each statement form;
- g) the meaning of each expression form;
- h) the semantics of `async`, `await`, `Promise`, and `isAsyncEnded`;
- i) the semantics of built-in operations;
- j) the import and visibility rules;
- k) the set of conditions that **SHALL** be diagnosed as errors;
- l) the set of conditions that **SHOULD** be diagnosed as warnings.

**1.3.** This standard does **not** specify:

- a) the vocabulary — see **SNAR-A2**;
- b) the syntactic grammar — see **SNAR-A3**;
- c) the SPC configuration language — see **SNAR-A1**;
- d) any implementation detail, including memory layout, code generation, optimization passes, diagnostic levels, or warning presentation.

**1.4.** Optimization levels and diagnostic-level policies (for example, treating warnings as errors) are **implementation-defined** and **SHALL NOT** affect the observable behavior of a conforming program as specified in this standard.

**1.5.** In case of any conflict between this standard and other documents of the SNAR-A generation regarding semantics, this standard takes precedence.

---

## 2. Conformance

**2.1.** A conforming implementation **SHALL** reject every program that violates any rule in §17.1 (Errors).

**2.2.** A conforming implementation **SHOULD** emit a diagnostic for every condition listed in §17.2 (Warnings).

**2.3.** A conforming implementation **MAY** emit additional warnings not listed in §17.2.

**2.4.** A conforming implementation **SHALL** preserve the observable behavior specified in §5–§16 regardless of the optimization level, provided that the program satisfies §17.1.

**2.5.** This standard uses the keywords **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** as defined in RFC 2119.

## 4. Terms and Definitions

**Program** — a syntactically valid Skorpion source text (see **SNAR-A3 §4**).

**Entry point** — the function named `main`. See §5.2.

**Symbol** — an entry in a scope associating a name with a kind (variable, function, constant, error type) and a type. See §6.

**Scope** — a mapping from identifiers to symbols, nested within an enclosing scope. See §6.

**Binding** — the association of a name with a symbol in a scope.

**Static type** — the type known at compile time, derived from declarations and syntactic rules.

**Runtime type** — the concrete type of a value at execution time; relevant only for `any` and union values.

**Conversion** — the process of producing a value of one type from a value of another. See §9.

**Promise** — the asynchronous result of an async function call. See §14.

**Promise handle** — a variable bound to a promise. See §14.3.

**Deep copy** — a copy of a value in which nested structures are also copied, so that the copy is independent of the original.

**Undefined behavior** — behavior for which this standard imposes no requirements. Programs relying on undefined behavior are non-conforming.

## 5. Program Model

### 5.1. Overall Execution

**5.1.1.** A conforming implementation processes a program in the following conceptual stages:

1. resolve imports (§16);
2. register error-type declarations and function declarations in the global scope (§6.1);
3. perform semantic analysis on every function body (§10–§15);
4. if no errors are detected, execute the program starting from the entry point (§5.2).

**5.1.2.** Semantic analysis **SHALL** be performed on every function that is not imported from a library or module, whether or not the function is reachable from the entry point, unless otherwise stated in this standard.

**5.1.3.** A program is invalid if semantic analysis detects any violation of §17.1.

### 5.2. Entry Point

**5.2.1.** Every executable program **SHALL** declare a function named `main`.

**5.2.2.** The `main` function **SHALL** have the following signature:

```
void main(arr args)
```

**5.2.3.** The `args` parameter receives the command-line arguments of the running program as an array of strings, excluding the program name.

**5.2.4.** Execution begins by invoking `main` with the command-line arguments.

**5.2.5.** The return type of `main` **SHALL** be `void`.

**5.2.6.** `main` **SHALL** have exactly one parameter, of an array type.

### 5.3. Library Mode

**5.3.1.** A program compiled in **library mode** does not require a `main` function.

**5.3.2.** In library mode, the program is treated as a collection of functions (exported and private) that may be used by another program.

**5.3.3.** Whether a program is compiled in library mode is an **implementation-defined** property of the compilation request.

## 6. Scopes and Name Resolution

### 6.1. Scope Hierarchy

**6.1.1.** A program has the following scopes:

- a) a single **global scope**, containing all top-level error-type declarations and function declarations;
- b) a **function scope** for each function, nested in the global scope;
- c) a **block scope** for each block, nested in the scope enclosing the block.

**6.1.2.** A catch clause's body (§12.11) has an additional inner scope in which the caught variable is bound.

### 6.2. Name Resolution

**6.2.1.** When an identifier is used, it is resolved by searching the current scope, then each enclosing scope, until the global scope is reached.

**6.2.2.** If no scope contains a symbol with the given name, the program is invalid (undefined identifier).

**6.2.3.** A function name or an error-type name **SHALL** be resolvable from the global scope.

### 6.3. Shadowing

**6.3.1.** A variable declared in an inner scope **MAY** shadow a variable with the same name declared in an enclosing scope.

**6.3.2.** Inside the inner scope, references to the name resolve to the inner declaration.

**6.3.3.** Outside the inner scope, references to the name resolve to the outer declaration.

### 6.4. Duplicate Declarations

**6.4.1.** Declaring two symbols with the same name in the **same** scope is invalid.

**6.4.2.** A function name **SHALL NOT** collide with the name of another function or an error type in the global scope.

**6.4.3.** Error types declared at the top level of a program are also placed in the global scope; the duplicate rules of §6.4.2 apply.

### 6.5. Unresolved References

**6.5.1.** Any identifier that is not resolvable at the point of use makes the program invalid.

**6.5.2.** The exception is use within an `IknowIdo` block or a C code fragment introduced by `includeC`; both have undefined behavior when such references are unresolvable (see §12.12 and §12.13).

## 7. Types

### 7.1. Type Categories

**7.1.1.** The types of the Skorpion language are grouped as follows:

| Category | Types |
|----------|-------|
| Scalar | `int`, `float`, `double`, `bool`, `char`, `string` |
| Container | `arr[T]`, `dict` |
| Union | `T<A,B,...>` |
| Error | User-declared error types, plus the built-in `Error` |
| Special | `void`, `any` |

### 7.2. Scalar Types

**7.2.1.** `int` — an integer value.

**7.2.2.** `float` — a single-precision floating-point value.

**7.2.3.** `double` — a double-precision floating-point value.

**7.2.4.** `bool` — one of `true` or `false`.

**7.2.5.** `char` — a single Unicode code point.

**7.2.6.** `string` — a sequence of Unicode code points.

### 7.3. The `void` Type

**7.3.1.** `void` denotes the absence of a value.

**7.3.2.** `void` is a valid **function return type** (see §10.2).

**7.3.3.** `void` **SHALL NOT** be used as a variable type or as an array element type.

**7.3.4.** The literal `null` has static type `void`. See §8.

**7.3.5.** A parameter whose declared type is `void` is syntactically acceptable but semantically odd: it can only receive a `null` argument. This standard does not forbid such a parameter, but a conforming implementation **MAY** emit an additional warning.

**7.3.6.** A union type that includes `void` as a component is syntactically acceptable, but the component is effectively unusable: §8.2.3 forbids assigning `null` to a union.

### 7.4. The `any` Type

**7.4.1.** `any` may hold a value of any non-`void` type.

**7.4.2.** Reading a value of type `any` as a value of a specific type requires an explicit conversion (see §9.2).

**7.4.3.** `any` **SHALL NOT** appear inside a union type (see §7.7.3).

### 7.5. Array Types

**7.5.1.** `arr[T]` denotes an ordered sequence of values of type `T`.

**7.5.2.** The form `arr` without an element type is equivalent to `arr[any]`.

**7.5.3.** The element type `T` **SHALL** be one of:

- a) a scalar type from §7.2;
- b) the `any` type;
- c) another array type `arr[...]`.

**7.5.4.** The element type **SHALL NOT** be `void`, `dict`, or a union type.

**7.5.5.** Arrays are **immutable**: no operation modifies an existing array value. Operations that produce a new array (such as literal construction or a range) produce a **new** array value. See §13.10.

### 7.6. Dict Type

**7.6.1.** `dict` denotes a mapping from string keys to values of type `any`.

**7.6.2.** The literal `{key: value, ...}` creates a `dict`. See §13.12.

### 7.7. Union Types

**7.7.1.** `T<A,B,...>` denotes a value that is one of the listed component types.

**7.7.2.** A union type **SHALL** contain at least one component type.

**7.7.3.** A union type **SHALL NOT**:

- a) contain another union type as a component;
- b) contain `any` as a component.

**7.7.4.** `T<A>` with a single component is equivalent to `A`.

**7.7.5.** The runtime type of a union-typed value is the type of the value it currently holds.

### 7.8. Error Types

**7.8.1.** An error type is declared with `const Name { ... } = Parent`. See §11.3.

**7.8.2.** Every error type inherits from a parent error type. The built-in `Error` type has no parent.

**7.8.3.** The built-in `Error` type has a single inherited field `msg: string`.

**7.8.4.** An error type **SHALL** be a valid `throw` operand (§12.10) and a valid `catch` operand (§12.11).

**7.8.5.** Error types **SHALL NOT** be used as:

- a) the type of a variable declaration outside a `catch` clause;
- b) the return type of a function;
- c) the parameter type of a function.

### 7.9. Type Identity

**7.9.1.** Two types are **identical** if and only if they have the same structure:

- a) two scalar names are identical if the names are equal;
- b) `arr[A]` and `arr[B]` are identical if `A` and `B` are identical;
- c) `T<A,B,...>` and `T<C,D,...>` are identical if the component lists are identical element-by-element in order;
- d) two error types are identical if they have the same name.

## 8. Values and Nullability

### 8.1. Null

**8.1.1.** The literal `null` represents the absence of a value.

**8.1.2.** The static type of `null` is `void`.

**8.1.3.** A variable of a concrete type (scalar, array, dict, or error type) **MAY** hold a null value.

**8.1.4.** Operations on a null value are governed by the rules of the specific operation (see §13).

### 8.2. Assignment of Null

**8.2.1.** `null` **MAY** be assigned to a variable whose type is a concrete type (for example, `int`, `string`, `arr[int]`).

**8.2.2.** `null` **SHALL NOT** be assigned to a variable whose static type is `any`.

**8.2.3.** `null` **SHALL NOT** be assigned to a variable whose static type is a union type.

**8.2.4.** `null` **SHALL NOT** be passed as an argument to a parameter whose static type is `any` or a union type.

### 8.3. Comparison with Null

**8.3.1.** A value of any non-`void` type **MAY** be compared with `null` using `==` or `!=`.

**8.3.2.** `x == null` is `true` if and only if `x` currently holds a null value.

**8.3.3.** Using `null` with any other comparison operator is invalid.

### 8.4. Undefined Behavior on Null

**8.4.1.** Using a null value in arithmetic, logical, or string operations has **undefined behavior**, unless the operation explicitly states otherwise.

**8.4.2.** Dereferencing a null array or dict has **undefined behavior**.

## 9. Type Compatibility and Conversions

### 9.1. Implicit Conversions

**9.1.1.** The following implicit conversions are permitted and **SHALL** be performed automatically when required by the target type:

| From | To | Context |
|------|-----|---------|
| `char` | `int` | assignment, argument, return |
| `int` | `char` | assignment, argument, return |
| `int` | `float` | arithmetic binary operation |
| `int` | `double` | arithmetic binary operation |
| `float` | `double` | arithmetic binary operation |

**9.1.2.** No other implicit conversions are permitted.

**9.1.3.** Implicit conversion from `any` or from a union type to a concrete type **SHALL NOT** occur. Explicit conversion (see §9.2) is required.

### 9.2. Explicit Conversions

**9.2.1.** The following operations produce a value of a different type from their argument:

| Operation | Result Type |
|-----------|-------------|
| `to_int(x)` | `int` |
| `to_float(x)` | `float` |
| `to_double(x)` | `double` |
| `to_bool(x)` | `bool` |
| `to_char(x)` | `char` |
| `to_string(x)` | `string` |
| `to_arr(x)` | `arr[any]` |
| `$x` | `string` |

**9.2.2.** The behavior of each conversion is specified in §15.

**9.2.3.** Whether every conversion listed in §9.2.1 is accepted in every type context is determined by the implementation; an implementation **MAY** reject a conversion that is not meaningful for the argument's type. If the implementation rejects a conversion, the program is invalid.

### 9.3. Assignment Compatibility

**9.3.1.** An expression of type `A` **SHALL** be assignable to a variable of type `B` if and only if one of the following holds:

- a) `A` and `B` are identical (§7.9);
- b) `A` is `void` (i.e., the value is `null`) and `B` is a concrete type;
- c) `B` is `any` and `A` is not `void`;
- d) `A` and `B` are related by an implicit conversion (§9.1);
- e) `B` is a union type and `A` is one of its components;
- f) `A` is a union type and `B` is `any`.

### 9.4. Parameter Compatibility

**9.4.1.** Argument compatibility with parameters follows the same rules as assignment compatibility (§9.3).

**9.4.2.** A parameter whose declared type is `any` accepts any non-`void` argument.

**9.4.3.** A parameter whose declared type is a union accepts any argument whose type is a component of the union.

### 9.5. Return Compatibility

**9.5.1.** A `return` expression's type **SHALL** be assignable to the function's declared return type per §9.3.

**9.5.2.** A `void` function **SHALL NOT** return a value.

**9.5.3.** A non-`void` function **SHALL** return a value on every reachable path (see §10.5).

## 10. Function Semantics

### 10.1. Function Signature

**10.1.1.** A function has a **signature** consisting of:

- a) its parameter list;
- b) its return type;
- c) whether it is async;
- d) whether it is exported.

**10.1.2.** No two functions **SHALL** have the same name (see §6.4).

### 10.2. Return Type

**10.2.1.** Every function **SHALL** declare a return type.

**10.2.2.** The return type **MAY** be `void`, a scalar type, an array type, a dict type, `any`, or a union type.

**10.2.3.** The return type **SHALL NOT** be an error type.

### 10.3. Parameters

**10.3.1.** Each parameter **SHALL** have a unique name within the function's parameter list.

**10.3.2.** At most one parameter **MAY** be variadic.

**10.3.3.** A variadic parameter, if present, **SHALL** be the last parameter.

**10.3.4.** A parameter with a default value **SHALL NOT** be followed by a parameter without a default value.

**10.3.5.** The static type of a variadic parameter is `arr[any]`; its declared type in the source text is not consulted.

**10.3.6.** A parameter's type **SHALL NOT** be `void` or an error type.

### 10.4. Function Body

**10.4.1.** A function body is a block (§12) analyzed in the function scope of the enclosing function.

**10.4.2.** Parameters are bound in the function scope before the body is analyzed.

### 10.5. Return Requirements

**10.5.1.** For a function whose return type is `void`, every reachable path **MAY** end without an explicit `return`.

**10.5.2.** For a function whose return type is non-`void`, every reachable path **SHALL** end with a `return` statement (§12.8) or with a construct whose sub-paths all end with `return`.

**10.5.3.** The following constructs are considered "returning" for the purposes of §10.5.2:

- a) a `return` statement;
- b) an `if` statement which has an `else` block, where the `then` block, all `elsif` blocks, and the `else` block all return;
- c) a `case` statement which has a default branch, where the default branch returns and every case branch returns;
- d) a `try` statement whose body returns and every catch clause returns.

**10.5.4.** `break` and `continue` do not satisfy §10.5.2.

**10.5.5.** A `while`, `do`–`while`, or `for`-in loop does not satisfy §10.5.2, because a loop body might execute zero times or exit via `break`.

**10.5.6.** A `throw` statement does not, by itself, satisfy §10.5.2. A function ending only with a `throw` is invalid.

### 10.6. Async Functions

**10.6.1.** A function marked with `async` is an **async function**.

**10.6.2.** An async function **SHALL NOT** have `void` as its return type.

**10.6.3.** The return type of an async function is the *resolved type* of the promise that the function produces.

**10.6.4.** Within the body of an async function, at most one `Promise[...]` statement **MAY** appear.

**10.6.5.** If a `Promise[...]` statement appears in the body of an async function, it **SHALL** be the first statement of the function body.

**10.6.6.** The operand of `Promise[...]` **SHALL** be a literal (see §13.1.6).

**10.6.7.** The static type of the operand of `Promise[...]` **SHALL** be assignable to the async function's return type.

**10.6.8.** If an async function contains no dynamic construct (see §10.6.9) and no `Promise[...]` statement, the function **SHOULD** be diagnosed as having a "useless async" (see §17.2).

**10.6.9.** *Dynamic constructs* for the purposes of §10.6.8 are: `Promise[...]`, `await`, `throw`, `try`/`catch`, `includeC`, calls to async functions, and calls to functions whose body contains an `includeC` statement.

### 10.7. The Entry Point

**10.7.1.** The `main` function **SHALL** satisfy §5.2.

**10.7.2.** In library mode (§5.3), the `main` function **SHALL NOT** be required.

**10.7.3.** In library mode, if a `main` function is present, §10.7.1 still applies.

## 11. Declaration Semantics

### 11.1. Variable Declarations

**11.1.1.** A variable declaration has the form `T x = e` or `T x`.

**11.1.2.** `T` **SHALL** be a valid declared type: one of the scalar types, `arr[T']`, `dict`, `any`, or a union type.

**11.1.3.** `void` **SHALL NOT** be used as `T`.

**11.1.4.** If an initializer `e` is present, the static type of `e` **SHALL** be assignable to `T` (see §9.3).

**11.1.5.** If no initializer is present, the variable is bound to a default value:

- a) scalar types: null;
- b) array types: a new empty array;
- c) `dict`: null;
- d) `any`: null;
- e) union types: null.

**11.1.6.** The variable's name **SHALL** be bound in the current scope.

### 11.2. Constant Declarations

**11.2.1.** A constant declaration has the form `const T x = e`.

**11.2.2.** The rules of §11.1.2 and §11.1.4 apply.

**11.2.3.** A constant **SHALL** have an initializer.

**11.2.4.** A constant **SHALL NOT** be reassigned (§12.1) or modified by compound assignment (§12.2), element assignment (§12.3), or postfix increment/decrement (§12.2).

### 11.3. Error-Type Declarations

**11.3.1.** An error-type declaration has the form `const Name { f: T, ... } = Parent` or `const Name { ... } = new Parent` (see **SNAR-A3 §7**).

**11.3.2.** `Name` **SHALL** begin with an uppercase letter.

**11.3.3.** `Name` **SHALL NOT** collide with the name of another function or error type in the global scope.

**11.3.4.** `Parent` **SHALL** be a declared error type, or the built-in `Error` type.

**11.3.5.** Each field **SHALL** have a unique name within the declaration, unless it shadows a parent's field of the same type (see §11.3.6).

**11.3.6.** If a field in the declaration has the same name as an inherited field, the two fields **SHALL** have identical types.

**11.3.7.** Each field's type **SHALL** be a valid declared type per §11.1.2.

**11.3.8.** A field's default value, if present, **SHALL** be an expression of a type assignable to the field's declared type.

### 11.4. Async Variable Declarations

**11.4.1.** A variable declaration has the special form `T x = f(args)` where `f` is an async function.

**11.4.2.** In this form, the static type of `x` is `T`, and `x` is a **promise handle** (§14.3).

**11.4.3.** `T` **SHALL** equal the return type of `f`.

**11.4.4.** The argument rules of §13.14 apply to the call `f(args)`.

**11.4.5.** A promise handle **SHALL NOT** be reassigned, modified by compound assignment, or otherwise mutated by §12.1–§12.3.

**11.4.6.** Reading a promise handle yields the current value of the promise (see §14.3).

## 12. Statement Semantics

### 12.1. Simple Assignment

**12.1.1.** A simple assignment statement has the form `x = e`.

**12.1.2.** `x` **SHALL** resolve to a variable (not a function or error type).

**12.1.3.** `x` **SHALL** be mutable (not `const`, not a promise handle).

**12.1.4.** The static type of `e` **SHALL** be assignable to the type of `x` (see §9.3).

**12.1.5.** After the statement, `x` holds the value of `e`.

### 12.2. Compound Assignment and Postfix Operations

**12.2.1.** A compound assignment has the form `x op= e` where `op` is one of `+`, `-`, `*`, `/`, `%`, `**`.

**12.2.2.** `x` **SHALL** be mutable.

**12.2.3.** The operation `x op e` **SHALL** be valid per §13.3 (or §13.4 for `%` and `**`) and its result **SHALL** be assignable to `x`'s type.

**12.2.4.** A postfix operation has the form `x++` or `x--`, where `x` is a mutable variable of type `int`.

**12.2.5.** A postfix operation used as a statement is equivalent to `x = x + 1` or `x = x - 1` respectively.

**12.2.6.** In expression position, `x++` and `x--` produce the value `x + 1` and `x - 1` respectively, **without** modifying `x`.

### 12.3. Element Assignment

**12.3.1.** An array element assignment has the form `x[i] = e`, `x[i] op= e`, or (for postfix) an appropriate compound form.

**12.3.2.** `x` **SHALL** be a mutable variable whose type is `arr[T]` or `dict`.

**12.3.3.** If `x` is an array, `i` **SHALL** be an `int` expression. The static type of `e` **SHALL** be assignable to `T`, or `T` is `any`.

**12.3.4.** If `x` is a dict, `i` **SHALL** be a `string` expression. The static type of `e` **SHALL** be any non-`void` type.

**12.3.5.** The element at position `i` of `x` **SHALL** be set to the value of `e`.

**12.3.6.** For dicts, if the key does not exist, it is created.

**12.3.7.** For arrays, if `i` is outside the valid range `[0, len(x) - 1]`, the behavior is **undefined**.

**12.3.8.** A dict field assignment `d.k = e` is equivalent to `d["k"] = e`.

### 12.4. Conditional Statements

**12.4.1.** The `if` statement, `elsif` clauses, and `else` clause are evaluated in order (see **SNAR-A3 §10.6**).

**12.4.2.** The condition of each `if` or `elsif` **SHALL** be of type `bool`.

**12.4.3.** The block of the first branch whose condition evaluates to `true` is executed; if no condition is `true`, the `else` block (if present) is executed.

### 12.5. Loops

**12.5.1.** `while (cond) { body }`:

- a) `cond` **SHALL** be of type `bool`;
- b) `cond` is evaluated; if `true`, `body` is executed;
- c) the loop repeats from step (b).

**12.5.2.** `do { body } while (cond)`:

- a) `body` is executed;
- b) `cond` **SHALL** be of type `bool`;
- c) `cond` is evaluated; if `true`, the loop repeats from step (a).

**12.5.3.** `for (T x in iter) { body }`:

- a) `iter` **SHALL** be of type `arr[U]` or `string`;
- b) `T` **SHALL** be assignable from `U` (if `iter` is `arr[U]`) or `string` (if `iter` is `string`);
- c) `x` is bound in the loop's inner scope;
- d) for each element of `iter` in order, `x` is bound to that element and `body` is executed.

**12.5.4.** For `string` iteration, each element is a single Unicode code point as a `string` of one character.

### 12.6. Break and Continue

**12.6.1.** `break` **SHALL** be used only inside a loop body.

**12.6.2.** `continue` **SHALL** be used only inside a loop body.

**12.6.3.** `break` exits the innermost enclosing loop.

**12.6.4.** For `while` and `for`-in, `continue` jumps to the loop's next iteration. For `do`–`while`, `continue` jumps to the condition evaluation.

### 12.7. Case Statements

**12.7.1.** The value expression of a `case` **SHALL** be evaluated first.

**12.7.2.** Each pattern **SHALL** have the same static type as the case value.

**12.7.3.** Two patterns in the same `case` **SHALL NOT** be equal as compile-time constants.

**12.7.4.** Patterns are compared to the value with `==`.

**12.7.5.** The first branch whose pattern matches is executed. If no branch matches, the default branch (if present) is executed.

**12.7.6.** A branch **SHALL NOT** fall through to the next branch; execution leaves the `case` after the branch's block completes.

### 12.8. Return Statements

**12.8.1.** See §10.5 for return requirements.

**12.8.2.** A `return` statement in a non-async function **SHALL** terminate the function with the specified value (or with no value, if the function's return type is `void`).

**12.8.3.** A `return` statement in an async function **SHALL** complete the function's promise with the specified value (see §14).

### 12.9. Break, Continue, and Case — Interaction with Scopes

**12.9.1.** `break` and `continue` transfer control out of the loop's scope; any variables declared within the loop body are no longer accessible.

### 12.10. Throw Statements

**12.10.1.** A `throw` statement has the form `throw e`.

**12.10.2.** The static type of `e` **SHALL** be an error type.

**12.10.3.** A `throw` statement transfers control to the innermost enclosing `try` statement whose matching `catch` clause accepts the thrown error (see §12.11).

**12.10.4.** If no matching `catch` exists in the current call stack, the program terminates abnormally.

### 12.11. Try Statements

**12.11.1.** A `try` statement has the form `try { body } catch (T as e) { h } ...`.

**12.11.2.** If an error is thrown from `body` (or any function called from `body` that does not handle the error itself), control transfers to the first `catch` clause whose declared type matches the error's type.

**12.11.3.** Matching is performed by name equality on the error type and its ancestors: a `catch` clause with type `T` matches any thrown error whose type is `T` or a descendant of `T`.

**12.11.4.** A `catch` clause's declared type **SHALL** be an error type.

**12.11.5.** If a `catch` clause has no declared type (i.e., a bare `catch`), it matches any error.

**12.11.6.** If no `catch` clause matches, the error propagates to the enclosing `try` (if any), or terminates the program.

**12.11.7.** The caught variable `e` is bound in the catch clause's scope with the caught error's type.

### 12.12. `includeC` Statements

**12.12.1.** An `includeC` statement inserts its enclosed C source code verbatim.

**12.12.2.** Semantic analysis **SHALL NOT** be performed on the contents of the C code.

**12.12.3.** Variables declared within a function containing `includeC` **MAY** be referenced by the included code; the behavior of such references is **implementation-defined**.

**12.12.4.** If an unused-parameter or unused-variable warning would be emitted for a function containing `includeC`, the diagnostic **MAY** be suppressed or altered to account for potential use from the C code.

### 12.13. `IknowIdo` Statements

**12.13.1.** An `IknowIdo` statement's block is **not** semantically analyzed.

**12.13.2.** Within the block, undeclared identifiers and type mismatches have **undefined behavior**.

**12.13.3.** Variables declared elsewhere in the enclosing function **MAY** be referenced from within the `IknowIdo` block; the behavior of such references is **implementation-defined**.

### 12.14. Expression Statements

**12.14.1.** An expression may appear as a statement (**SNAR-A3 §10.19**).

**12.14.2.** The expression is evaluated and its value discarded.

**12.14.3.** A function call whose result is discarded is still executed; any side effects (including async spawning, see §14.5) occur.

**12.14.4.** Using an expression as a statement whose sole purpose is producing a value (for example, a bare literal) is valid but may be diagnosed as a warning at the implementation's discretion.

## 13. Expression Semantics

### 13.1. Literal Expressions

**13.1.1.** An `int` literal has static type `int`.

**13.1.2.** A numeric literal with a fraction has static type `double`.

**13.1.3.** A numeric literal ending in `f` or `F` has static type `float`.

**13.1.4.** A string literal has static type `string`.

**13.1.5.** A character literal or `Unicode[...]` literal has static type `char`.

**13.1.6.** The literals `true` and `false` have static type `bool`. The literal `null` has static type `void`.

**13.1.7.** An array literal has static type `arr[any]` unless a contextual expected type is present, in which case the expected type is used for element checking.

**13.1.8.** A dict literal has static type `dict`.

**13.1.9.** An error instance `T{...}` has static type `T` (an error type).

### 13.2. Identifier Expressions

**13.2.1.** An identifier **SHALL** resolve to a declared symbol (§6.2).

**13.2.2.** If the identifier refers to a variable, its static type is the variable's declared type.

**13.2.3.** If the identifier refers to a constant, its static type is the constant's declared type.

**13.2.4.** If the identifier refers to a promise handle (§14.3), reading it yields the current value of the underlying promise.

### 13.3. Binary Arithmetic

**13.3.1.** The binary operators `+`, `-`, `*`, `/`, `**` have the following meaning:

- a) if both operands are numeric, the operation is arithmetic; the result type is the widest of the two operand types, in the order `int` → `float` → `double`;
- b) if the operator is `+` and at least one operand is `string` and the other is `string`, `char`, or `any`, the operation is string concatenation; the result is `string`;
- c) if the operator is `+` and both operands are `char`, the operation is string concatenation; the result is `string`;
- d) if the operator is `+` and one operand is `char` and the other is `int`, the result is `int`;
- e) if either operand is `any` or a union type, the result has static type `any`, and the operation is performed at runtime based on the runtime types of the operands. If the runtime types are not compatible with the operator, the result is `null` (for arithmetic operators) or `false` (for comparison operators).

**13.3.2.** Division by zero produces a `null` value of the result type. A conforming implementation **SHOULD** emit a warning when the divisor is a literal zero.

**13.3.3.** If either operand is `void` (i.e., `null`), the program is invalid for arithmetic operators; see §8.4 for other operators.

### 13.4. Modulo and Exponentiation

**13.4.1.** The operator `%` is the modulo operator. Both operands **SHALL** be `int`. The result is `int`.

**13.4.2.** The operator `**` is exponentiation. Both operands **SHALL** be numeric. The result type follows §13.3.1(a).

### 13.5. Comparison

**13.5.1.** The operators `<`, `>`, `<=`, `>=` produce a `bool` result.

**13.5.2.** For `<` and `>`, both operands **SHALL** be numeric; otherwise the program is invalid.

**13.5.3.** For `<=` and `>=`, operand types are not statically constrained by this standard; the behavior on non-numeric operands is **undefined**.

**13.5.4.** The operators `==` and `!=` produce a `bool` result.

**13.5.5.** For `==` and `!=`, operand types are not statically constrained by this standard. If the operands have different static types, the result is `false` (for `==`) or `true` (for `!=`). For operands of the same non-comparable type, the behavior is **undefined**.

**13.5.6.** Comparing a value with `null` is always valid (§8.3).

### 13.6. Logical Operators

**13.6.1.** The operators `&&` and `||` **SHALL** have operands of type `bool` and produce a `bool`.

**13.6.2.** `!` **SHALL** have an operand of type `bool` and produce a `bool`.

**13.6.3.** Whether `&&` and `||` short-circuit (do not evaluate the right operand when the result is already determined) is **implementation-defined**.

### 13.7. Unary Operators

**13.7.1.** Unary `-` **SHALL** have a numeric operand and produce a result of the operand's type.

**13.7.2.** Unary `!` **SHALL** have a `bool` operand and produce a `bool`.

**13.7.3.** Unary `$` **MAY** have an operand of any type. The result has static type `string`. A `null` operand produces the string `"null"` (see §15.1.5).

### 13.8. Ternary

**13.8.1.** A ternary expression `c ? t : e` **SHALL** have `c` of type `bool`.

**13.8.2.** The static types of `t` and `e` **SHALL** be identical.

**13.8.3.** The result has the static type of `t` (and `e`).

**13.8.4.** Evaluation order: `c` first, then exactly one of `t` or `e`.

### 13.9. Range

**13.9.1.** A range expression `a..b` **SHALL** have both operands of type `int`.

**13.9.2.** The result has static type `arr[int]`.

**13.9.3.** The result contains every integer from `a` to `b` inclusive, in ascending order if `a <= b` and in descending order otherwise.

**13.9.4.** If `a` or `b` is not a compile-time constant, the construction of the range is deferred to runtime; the resulting sequence follows §13.9.3.

### 13.10. Array Operations

**13.10.1.** `xs[i]` — array indexing:

- a) `xs` **SHALL** be `arr[T]` (or `arr`, equivalent to `arr[any]`);
- b) `i` **SHALL** be `int`;
- c) the result has static type `T`, or `any` if `xs` is `arr[any]`;
- d) if `i` is outside the range `[0, len(xs) - 1]`, the behavior is **undefined**.

**13.10.2.** `xs.length` — the number of elements in `xs`. The result is `int`.

**13.10.3.** `xs + x` — array append:

- a) `xs` **SHALL** be `arr[T]`;
- b) `x` **SHALL** be assignable to `T` (or `T` is `any`);
- c) the result is a **new** array of type `arr[T]` containing all elements of `xs` followed by `x`;
- d) `xs` itself is not modified (§7.5.5).

Note: some conforming implementations may currently reject this form; an implementation that rejects it diagnoses an error, and the program is invalid.

**13.10.4.** An array literal `[...]` or `(...)` produces a new array of type `arr[any]` or, in a typed context, `arr[T]` where `T` is the expected element type.

### 13.11. String Operations

**13.11.1.** `s.length` — the number of Unicode code points in `s`. The result is `int`.

**13.11.2.** `s[i]` — the `i`-th Unicode code point of `s` as a string of one code point. The result is `string`.

**13.11.3.** Concatenation of a string with a string or char follows §13.3.1(b).

### 13.12. Dict Operations

**13.12.1.** A dict literal `{k: v, ...}` creates a new dict. Each key `k` **SHALL** be a unique identifier. Each value `v` **SHALL** be any non-`void` expression.

**13.12.2.** `d.k` or `d["k"]` — dict access:

- a) `d` **SHALL** be `dict`;
- b) `k` is a string key;
- c) the result has static type `any`, unless the key's type is statically known (from the literal that initialized `d`), in which case the result has that type;
- d) if the key does not exist, the result is `null`.

**13.12.3.** `d.k = v` or `d["k"] = v` — dict assignment; see §12.3.

### 13.13. Error Field Access

**13.13.1.** `e.f` where `e` is an error type value:

- a) `e` **SHALL** have an error type;
- b) `f` **SHALL** be a field of that error type, including inherited fields;
- c) the result has the field's declared type.

**13.13.2.** Accessing a field that does not exist is invalid (§17.1).

### 13.14. Function Calls

**13.14.1.** A function call `f(a1, a2, ...)`:

- a) `f` **SHALL** resolve to a function;
- b) the number of arguments **SHALL** be compatible with the parameter list (see §13.14.2);
- c) each argument's static type **SHALL** be assignable to the corresponding parameter's type (see §9.4);
- d) the result has static type equal to the function's return type (or `void` if the function's return type is `void`, in which case the call is only valid as a statement).

**13.14.2.** Argument-count compatibility:

- a) if the function has no variadic parameter: `n_args` **SHALL** be between the number of required parameters and the total number of parameters (required + optional);
- b) if the function has a variadic parameter: `n_args` **SHALL** be at least the number of required parameters before the variadic.

**13.14.3.** Default values are substituted for missing arguments at the end of the call.

**13.14.4.** Extra arguments beyond the non-variadic parameters are collected into the variadic parameter as an array of `any`.

**13.14.5.** The evaluation order of arguments is **implementation-defined**.

### 13.15. Qualified Calls

**13.15.1.** A call of the form `module.f(args)` where `module` is an import name or import alias resolves to the function `f` in that import's scope.

**13.15.2.** A call of the form `receiver.method(args)` where `receiver` is a value (not an import) resolves to the function `method` with `receiver` prepended to the argument list.

**13.15.3.** The rules of §13.14 apply to both forms.

### 13.16. Postfix Operations

**13.16.1.** `x++` and `x--` — postfix increment/decrement; see §12.2.4 and §12.2.6.

**13.16.2.** `.length` — see §13.10.2 and §13.11.1.

**13.16.3.** `[...]` — see §13.10.1, §13.11.2, and §13.12.2.

### 13.17. Async Operations

**13.17.1.** The rules for `async`, `await`, `Promise`, and `isAsyncEnded` are specified in §14.

### 13.18. Format Suffix

**13.18.1.** The format suffix `^Nf` applies to an expression of numeric type.

- a) `N` **SHALL** be an integer between `0` and `20` inclusive;
- b) if `N` is `0`, the result has static type `int` and is the operand truncated toward zero;
- c) if `N` is greater than `0`, the result has the same static type as the operand and its value is the operand rounded to `N` fractional digits.

**13.18.2.** The format suffix `^X...` applies to an expression of numeric type and trims trailing characters according to the trim set. Its result has the same static type as the operand.

**13.18.3.** The format suffix **SHALL NOT** be applied to non-numeric expressions.

## 14. Concurrency Semantics

### 14.1. Async Function Calls

**14.1.1.** A call to an async function starts a new **asynchronous operation**. The call itself returns immediately.

**14.1.2.** The asynchronous operation eventually completes with one of:

- a) a **value** of the async function's return type;
- b) an **error** that was thrown within the async function.

**14.1.3.** The result of the call is a **promise**: an opaque handle representing the eventual outcome.

### 14.2. The `Promise[...]` Statement

**14.2.1.** The statement `Promise[v]` within an async function sets the initial value of the promise to `v`.

**14.2.2.** `v` **SHALL** be a literal (§13.1).

**14.2.3.** The static type of `v` **SHALL** be assignable to the async function's return type.

**14.2.4.** `Promise[...]` **SHALL** be the first statement of the async function body if it is present (§10.6.5).

**14.2.5.** If `Promise[...]` is absent, the promise's initial value is null (or the default value of the return type).

### 14.3. Promise Handles

**14.3.1.** A declaration `T x = f(args)` where `f` is an async function binds `x` to the promise of the async call.

**14.3.2.** The static type of `x` is `T`, which **SHALL** equal `f`'s return type.

**14.3.3.** Reading `x` in an expression yields the **current value** of the underlying promise. This value may be:

- a) the initial value set by `Promise[...]`;
- b) an intermediate value set by the async function (if any);
- c) the final value (if the async function has completed);
- d) null (if no value has been set).

**14.3.4.** Reading `x` **SHALL NOT** block.

**14.3.5.** A promise handle **SHALL NOT** be reassigned, modified, or otherwise mutated (§11.4.5).

### 14.4. `await`

**14.4.1.** An `await` expression has the form `await e`, where `e` is either:

- a) a call to an async function: `await f(args)`;
- b) a promise handle: `await x`.

**14.4.2.** `await` blocks the current execution until the underlying promise completes.

**14.4.3.** If the promise completes with a value, `await` yields that value, with static type equal to the promise's underlying type.

**14.4.4.** If the promise completes with an error, `await` propagates the error as if `throw` had been executed in the current context.

**14.4.5.** `await` **MAY** be used in an async function or a synchronous function; the blocking behavior applies to the calling context.

### 14.5. Fire-and-Forget Calls

**14.5.1.** An async function call used as a statement (not assigned, not awaited, not used as an expression value) is a **fire-and-forget** call.

**14.5.2.** The async function is started; its result is discarded.

**14.5.3.** Errors thrown by a fire-and-forget call that are not caught inside the async function are **unhandled** and **SHALL** terminate the program.

### 14.6. Async Calls in Expression Context

**14.6.1.** An async function call used in an expression that is neither awaited nor assigned to a promise handle (for example, as an argument to another function) produces the **current value** of the promise, with the same semantics as reading a promise handle (§14.3.3).

### 14.7. `isAsyncEnded`

**14.7.1.** The call `isAsyncEnded("name")` **SHALL** have exactly one argument.

**14.7.2.** The argument **SHALL** be a string literal whose value is the name of an async function.

**14.7.3.** The function name **SHALL** resolve to an async function.

**14.7.4.** The call yields `true` if and only if the most recent async call to that function within the current function scope has completed; otherwise `false`.

**14.7.5.** The result type is `bool`.

**14.7.6.** If no async call to the named function has been made in the current function scope, a conforming implementation **SHALL** diagnose an error (see §17.1).

## 15. Built-in Operations

### 15.1. Numeric Conversions

**15.1.1.** `to_int(x)` converts `x` to `int`. The result depends on the static type of `x`:

- `bool` → `1` or `0`;
- `char` → its code point;
- `float`, `double` → truncated toward zero;
- `string` → parsed as decimal integer; invalid input yields `0`;
- `int` → unchanged;
- `any` → the current runtime type is consulted and the corresponding rule is applied.

**15.1.2.** `to_float(x)` and `to_double(x)` convert `x` to `float` / `double` with analogous rules.

**15.1.3.** `to_bool(x)` converts `x` to `bool`:

- `0`, `0.0`, `""` → `false`;
- non-zero, non-empty → `true`.

**15.1.4.** `to_char(x)` converts `x` to `char`. For `int`, the value is interpreted as a Unicode code point. For `string`, the first code point is used. Whether `to_char` is recognized as a built-in is **implementation-defined**; an implementation that does not recognize it treats it as an ordinary function name and diagnoses an undefined function.

**15.1.5.** `to_string(x)` converts `x` to `string`. The result depends on the static or runtime type:

- `int`, `float`, `double` → decimal representation;
- `bool` → `"true"` or `"false"`;
- `char` → a string of one code point;
- `string` → unchanged;
- `arr` → a bracketed list representation;
- `dict` → a `{k: v, ...}` representation.

**15.1.6.** `to_arr(x)` converts `x` to `arr[any]`. If `x` is already an array, its elements are copied.

### 15.2. `type(x)` and `detruncate(x)`

**15.2.1.** `type(x)` yields a `string` naming the **runtime** type of `x`. For `any` and union values, the concrete runtime type is used. If the runtime type cannot be named (for example, some values of type `any` whose runtime type is `dict` or `char` in the reference compiler), the result may be the string `"unknown"`.

**15.2.2.** `detruncate(x)` yields a `string` naming the **static** (declared) type of `x`.

### 15.3. String Operations

**15.3.1.** String concatenation with `+` produces a new string equal to the concatenation of its operands.

**15.3.2.** `s.length` returns the number of Unicode code points in `s`.

**15.3.3.** `s[i]` returns the `i`-th code point of `s` as a one-character string.

### 15.4. Config Operations

**15.4.1.** `getConfig()` yields the current project's SPC configuration (see **SNAR-A1**) as a `dict`.

**15.4.2.** `getConfigField("name")` yields the value of the named configuration field, or `null` if absent. The result type is `any`.

### 15.5. Async Operations

See §14.

## 16. Imports and Visibility

### 16.1. Import Forms

**16.1.1.** An import `use m` makes the exported functions of module `m` available as `m.func` and (unless a more specific binding applies) as `func`.

**16.1.2.** An import `use #m` makes all exported functions of module `m` available by their simple names.

**16.1.3.** An import `use m &a` introduces an alias `a` for module `m`; the module's exported functions are available as `a.func` and (by §16.1.1) as `func`.

**16.1.4.** A library import `use #lib:...` follows the same rules as §16.1.2.

### 16.2. Export Visibility

**16.2.1.** A function is **exported** unless its declaration is marked with `*` (see **SNAR-A3 §8.3**).

**16.2.2.** Only exported functions **SHALL** be visible to importers.

**16.2.3.** A non-exported function **SHALL NOT** be resolvable from a module that imports the enclosing module.

### 16.3. Import Name Resolution

**16.3.1.** If a function is available under both a fully-qualified name (`m.func` or `a.func`) and a simple name (`func`), both forms **SHALL** resolve to the same function.

**16.3.2.** If two imported modules export functions with the same simple name and neither is aliased, resolution is **implementation-defined**. A conforming implementation **SHOULD** diagnose the ambiguity.

### 16.4. Library-Mode Declarations

**16.4.1.** In library mode (§5.3), the library's exported functions **SHALL** be the unit of reuse.

**16.4.2.** A library's private functions **SHALL NOT** be visible outside the library.

### 17.2. Warnings

**17.2.1.** A conforming implementation **SHOULD** emit a warning for each of the following conditions. Whether warnings are treated as errors is an implementation-defined diagnostic-level policy (§1.4).

| Condition | Reference |
|-----------|-----------|
| Unused variable | — |
| Unused parameter (except `main`'s parameter) | — |
| Empty function body | — |
| Division by a literal zero | §13.3.2 |
| "Useless async": an async function with no dynamic constructs | §10.6.8 |
| Unused-parameter analysis skipped due to `includeC` in the function | §12.12.4 |
| Import name ambiguity | §16.3.2 |

### 17.3. Implementation-Defined Behavior

**17.3.1.** The following behaviors are **implementation-defined**:

- a) argument evaluation order (see §13.14.5);
- b) short-circuit evaluation of `&&` and `||` (see §13.6.3);
- c) use of variables from within `includeC` code (see §12.12.3);
- d) use of undeclared identifiers from within an `IknowIdo` block (see §12.13.2);
- e) resolution of import name ambiguity (see §16.3.2);
- f) the diagnostic-level policy (whether warnings are errors);
- g) the set of additional warnings emitted;
- h) the optimization level, provided observable behavior is preserved;
- i) whether `to_char` is recognized as a built-in conversion (§15.1.4);
- j) whether `xs + x` array-append is accepted (§13.10.3).

## Appendix B — Behavior of Operations on `null`

The following table summarizes the behavior of operations when one or more operands are null.

| `-x` | Undefined |

## Appendix C — Complete Example

The following program is fully valid and demonstrates the semantics of the language.

```skorpion
use std/io

const HttpError{
    code: int,
    message: string
} = new Error

void process(int x) {
    case (x) {
        1 { io.sendln("one") },
        (2, 3) { io.sendln("few") },
        _ { io.sendln("many") },
    }
}

async int fetchValue() {
    Promise[42]
    return 42
}

void main(arr args) {
    const int MAX = 100

    int i = 0
    i += 1
    i -= 2
    i *= 3

    if (MAX == 100) {
        io.sendln("max is 100")
    }

    int handle = fetchValue()
    io.sendln(await handle)

    try {
        throw HttpError{msg: "bad", code: 500, message: "server error"}
    } catch (HttpError as e) {
        io.sendln(e.message)
    } catch {
        io.sendln("unknown")
    }

    arr[int] xs = [1, 2, 3]

    for (int n in xs) {
        process(n)
    }

    string s = "hello"
    s += " world"
    s += '!'

    dict d = {name: "Skorpion", age: 25}
    io.sendln(d.name)

    T<int, string> u = 42
    u = "forty-two"
}
```
