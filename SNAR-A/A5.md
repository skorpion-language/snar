# SNAR-A5

## Skorpion Norms And Rules, A generation. Standard A5

### The `.sklib` Library Format

---

## 1. Scope

**1.1.** This standard defines the **binary file format** of Skorpion libraries, identified by the `.sklib` file extension, and the rules by which a conforming implementation writes, reads, locates, and resolves such libraries.

**1.2.** This standard specifies:

- a) the byte layout of a `.sklib` file;
- b) the magic bytes and format version marker;
- c) the serialization and compression of the payload;
- d) the structure of the payload (the `Library` record);
- e) the set of AST node types that may appear in the payload;
- f) the path syntax used to identify a library;
- g) the rules for locating a library on disk;
- h) the dependency-declaration and dependency-resolution rules;
- i) format versioning, backward and forward compatibility;
- j) the error conditions a conforming implementation **SHALL** detect.

**1.3.** This standard does **not** specify:

- a) the Skorpion language itself — see **SNAR-A2**–**SNAR-A4**;
- b) the SPC configuration language — see **SNAR-A1**;
- c) the standard library of the Skorpion language, which is a separate normative document;
- d) the mechanism by which a `Program` payload is produced from source text, or how it is consumed after loading;
- e) any implementation detail beyond what the file format requires.

**1.4.** This standard uses the keywords **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** as defined in RFC 2119.

---

## 2. Conformance

**2.1.** A conforming writer **SHALL** produce files that satisfy every rule of **§5–§8**.

**2.2.** A conforming reader **SHALL** accept every file that satisfies every rule of **§5–§8** and whose format version is supported by the reader (see **§10**).

**2.3.** A conforming reader **SHALL** reject every file that violates any rule of **§5–§8** or whose format version is not supported, and **SHALL** report the reason as specified in **§13**.

**2.4.** A conforming implementation **SHALL** implement both the writer and the reader rules unless it explicitly declares itself read-only or write-only.

## 4. Terms and Definitions

**Library file** — a file whose name ends with `.sklib` and whose contents satisfy this standard.

**Library record** — the logical object serialized into a library file. See **§8**.

**Payload** — the portion of a library file that follows the header; that is, the compressed serialized library record. See **§7**.

**Header** — the first five bytes of a library file, identifying it as a Skorpion library and declaring its format version. See **§6**.

**Magic bytes** — the four-byte sequence `S`, `K`, `L`, `B`. See **§6.2**.

**Format version** — a single-byte integer in the header identifying the version of this standard under which the file was written. See **§6.3**.

**Producer** — a conforming implementation that writes `.sklib` files.

**Consumer** — a conforming implementation that reads `.sklib` files.

**Library identifier** — a string of the form `lib:author/name` or `lib:author/name@version` identifying a library. See **§11**.

**Library directory** — the on-disk directory in which `.sklib` files are stored, as configured by the SPC `libs` parameter (**SNAR-A1 §12.1.1**).

**AllFunctions** — the derived field of `Program` that lists all functions visible to a program (local plus imported). See **§8.4**.

---

## 5. File Overview

**5.1.** A `.sklib` file consists of exactly two parts, in this order:

1. a **header** (§6), exactly 5 bytes;
2. a **payload** (§7), one or more bytes.

**5.2.** The file length **SHALL** be at least 5 bytes. A file shorter than 5 bytes is invalid.

**5.3.** A `.sklib` file **SHALL NOT** contain any trailing bytes after the payload. A file with trailing bytes after the payload is invalid.

**5.4.** The payload **SHALL** be the gzip-compressed, gob-encoded serialization of a single `Library` record (§8).

**5.5.** There **SHALL** be exactly one `Library` record per file.

---

## 6. Header

### 6.1. Byte Layout

**6.1.1.** The header occupies bytes 0 through 4 of the file (inclusive), in this order:

| Offset | Length | Field | Value |
|--------|--------|-------|-------|
| 0 | 1 | Magic byte 0 | `0x53` (`S`) |
| 1 | 1 | Magic byte 1 | `0x4B` (`K`) |
| 2 | 1 | Magic byte 2 | `0x4C` (`L`) |
| 3 | 1 | Magic byte 3 | `0x42` (`B`) |
| 4 | 1 | Format version | See **§6.3** |

**6.1.2.** All header bytes are unsigned. Multi-byte integers **SHALL NOT** appear in the header; only single-byte values are permitted.

### 6.2. Magic Bytes

**6.2.1.** The four magic bytes are, in order: `0x53`, `0x4B`, `0x4C`, `0x42`.

**6.2.2.** As ASCII characters, the magic bytes spell `SKLB`.

**6.2.3.** A file whose first four bytes do not equal the magic bytes **SHALL NOT** be treated as a `.sklib` file.

**6.2.4.** The magic bytes are invariant across all format versions.

### 6.3. Format Version

**6.3.1.** Byte 4 of the file contains a single unsigned integer in the range 0–255 representing the format version.

**6.3.2.** The current version of this standard defines format version **1**.

**6.3.3.** A file whose format version is not supported by a conforming consumer is invalid and **SHALL** be rejected (see **§10**).

---

## 7. Payload

### 7.1. Composition

**7.1.1.** The payload **SHALL** be the result of applying the following transformations in order:

1. serialize the `Library` record (**§8**) using the gob binary encoding defined in **§7.2**;
2. compress the resulting bytes using gzip as defined in RFC 1952 (**§7.3**).

**7.1.2.** Equivalently, in the reverse direction, the `Library` record is obtained from the payload by:

1. decompressing the payload using gzip;
2. decoding the decompressed bytes using gob.

**7.1.3.** The payload starts at byte offset 5 of the file and extends to the end of the file.

### 7.2. Gob Encoding

**7.2.1.** The serialization **SHALL** use the gob binary encoding format as defined by the Go standard library's `encoding/gob` package.

**7.2.2.** The value encoded **SHALL** be a single `Library` record as defined in **§8**.

**7.2.3.** Every AST node type that may appear in the `Program` payload **SHALL** be registered with the gob encoder before serialization, so that the encoder emits its type name alongside the value. The set of node types that **SHALL** be registered is listed in **§8.6**.

**7.2.4.** A producer **SHALL** register all node types listed in **§8.6**, including any node types that do not appear in the particular `Program` being serialized. This ensures that any `.sklib` file produced by any conforming writer is readable by any conforming reader.

**7.2.5.** A consumer **SHALL** register the same set of node types before deserialization.

### 7.3. Gzip Compression

**7.3.1.** The gob-encoded bytes **SHALL** be compressed using gzip as defined in RFC 1952.

**7.3.2.** A conforming writer **MAY** choose any compression level permitted by RFC 1952.

**7.3.3.** A conforming reader **SHALL** accept gzip streams produced at any compression level.

**7.3.4.** The gzip stream **SHALL** contain exactly one gzip member. Concatenated gzip members are **SHALL NOT** be used.

**7.3.5.** Gzip header fields not constrained by RFC 1952 (such as the modification time, original file name, and OS byte) **SHOULD** be set to their default/zero values. A conforming reader **SHALL NOT** rely on any particular value for these fields.

## 8. The `Library` Record

### 8.1. Logical Structure

**8.1.1.** The `Library` record is a composite value with the following fields:

| Field | Type | Presence |
|-------|------|----------|
| `FormatVersion` | integer | Required |
| `Name` | string | Required |
| `Version` | string | Required |
| `Author` | string | Required |
| `Dependencies` | array of string | Required (may be empty) |
| `Program` | `Program` (see **§8.3**) | Required |

**8.1.2.** The serialized field order is determined by gob; a conforming reader **SHALL NOT** depend on any particular byte layout within the gob payload. The logical fields and their semantics are normative.

### 8.2. Field Semantics

**8.2.1.** `FormatVersion` **SHALL** equal the format version declared in the header (§6.3). A file in which these two values differ is invalid (§10.4).

**8.2.2.** `Name` **SHALL** be the name of the library. It **SHALL** be a non-empty string.

**8.2.3.** `Version` **SHALL** be the version string of the library. It **SHALL** be a non-empty string in the format `x.y.z` where `x`, `y`, and `z` are non-empty decimal-digit sequences.

**8.2.4.** `Author` **SHALL** be the author name of the library. It **SHALL** be a non-empty string.

**8.2.5.** `Dependencies` **SHALL** list every other library that this library requires. Each element **SHALL** be a library identifier (see **§11**) or the portion of such an identifier that follows `lib:`. An empty list is valid and means the library has no dependencies.

**8.2.6.** `Program` **SHALL** be a `Program` value as defined in **§8.3**.

### 8.3. The `Program` Payload

**8.3.1.** The `Program` field contains a snapshot of the AST that results from parsing all Skorpion source files that constitute the library, after import resolution.

**8.3.2.** A `Program` value consists of:

| Field | Type | Semantics |
|-------|------|-----------|
| `Position` | position | Source position of the program |
| `Imports` | array of `Import` | Imports declared by the library |
| `Functions` | array of `Function` | All functions declared by the library |
| `ErrorDecls` | array of `ErrorDecl` | All error-type declarations in the library |
| `AllFunctions` | array of `Function` | Not serialized; see **§8.4** |
| `GlobalIncludeC` | array of string | All top-level `includeC` blocks in the library |

**8.3.3.** `Functions` **SHALL** contain both exported and non-exported functions. The consumer decides which functions to expose based on the `IsExport` flag of each function (see **§12**).

**8.3.4.** `ErrorDecls` **SHALL** contain every error-type declaration from the library, in source order. Each declaration **SHALL** carry the module name of the library in its `Module` field so that name collisions across libraries can be detected.

**8.3.5.** `GlobalIncludeC` **SHALL** contain the concatenation of all top-level `includeC` blocks across the library's source files, in the order they appear after import resolution.

### 8.4. The `AllFunctions` Field

**8.4.1.** The `AllFunctions` field is a **derived** field that contains the union of the library's own functions and the functions exported by its dependencies.

**8.4.2.** A producer **SHALL NOT** serialize `AllFunctions`. Before writing the payload, `AllFunctions` **SHALL** be cleared (set to nil or to an empty array).

**8.4.3.** A consumer **SHALL** recompute `AllFunctions` after loading, using the same rule as **§8.4.1**.

**8.4.4.** If a `.sklib` file's payload contains a non-empty `AllFunctions` value, the consumer **SHOULD** ignore it and recompute it. It is not a validity error, but it is redundant.

### 8.5. The `Module` Field

**8.5.1.** The `Module` field of each `ErrorDecl` in `ErrorDecls` **SHALL** be set to the library's `Name`.

**8.5.2.** This rule allows error types from different libraries to be distinguished even when they have the same local name.

### 8.6. Registered AST Node Types

**8.6.1.** A conforming implementation **SHALL** register every node type listed in this subsection before reading or writing a `.sklib` file. Registration maps each node type to a stable type name that gob emits into the payload.

**8.6.2.** The **top-level nodes** are:

- `Program`
- `Import`
- `Function`
- `ErrorDecl`

**8.6.3.** The **declaration nodes** are:

- `Param`
- `VarDecl`
- `ErrorField`

**8.6.4.** The **statement nodes** are:

- `Block`
- `Assign`
- `ReturnStmt`
- `IfStmt`
- `Elsif`
- `CaseStmt`
- `CaseBranch`
- `WhileStmt`
- `DoWhileStmt`
- `ForInStmt`
- `BreakStmt`
- `ContinueStmt`
- `ThrowStmt`
- `TryStmt`
- `CatchClause`
- `PromiseSet`
- `AwaitExpr`
- `IncludeC`
- `IknowIdoBlock`

**8.6.5.** The **expression nodes** are:

- `BinaryExpr`
- `UnaryExpr`
- `CallExpr`
- `CallRangeExpr`
- `RangeExpr`
- `TernaryExpr`
- `TypeOf`
- `FormatExpr`
- `PostfixExpr`
- `Ident`
- `Number`
- `String`
- `CharLiteral`
- `UnicodeLiteral`
- `NullLiteral`
- `ArrayLiteral`
- `ArrayIndex`
- `ArrayLength`
- `ArrayAdd`
- `DictLiteral`
- `DictElement`
- `DictIndex`
- `FieldAccess`
- `ErrorInstance`

**8.6.6.** The **auxiliary nodes** are:

- `IsAsyncEnded`

**8.6.7.** The list in **§8.6.2–§8.6.6** is exhaustive for format version 1. Any future format version that adds new node types **SHALL** increment the format version number (§10.2).

**8.6.8.** A producer **SHALL NOT** emit a node type that is not in the list above. A consumer **SHALL** reject a payload containing a node type that is not in the list above.

## 9. The Program Payload at a Glance

**9.1.** The following table maps each `Program` field to its relationship with the Skorpion source language:

| Field | Content | Corresponding SNAR-A3 section |
|-------|---------|-------------------------------|
| `Imports` | All `use` declarations | **§7** |
| `Functions` | All function declarations | **§10** |
| `ErrorDecls` | All top-level `const Name{...}=...` declarations | **§9** |
| `GlobalIncludeC` | All top-level `includeC` blocks | **§12.15** |

**9.2.** Statements and expressions inside each `Function.Body` are stored as their full AST. See **SNAR-A3 §12** and **§13** for the corresponding syntactic forms.

**9.3.** The AST nodes in the payload are a **snapshot**: they are not re-parsed or re-analyzed by a consumer. Whether a consumer performs additional semantic checks on the loaded payload is **implementation-defined**, but such checks **SHALL NOT** alter the meaning of a payload that was valid under the producer's `SNAR-A2`–`SNAR-A4` versions.

## 10. Format Versioning

### 10.1. Current Version

**10.1.1.** The current format version of this standard is **1**.

**10.1.2.** The header value **SHALL** be `0x01` for format version 1.

### 10.2. When to Increment the Version

**10.2.1.** The format version **SHALL** be incremented whenever any of the following changes:

- a) the header layout (**§6.1**);
- b) the magic bytes (**§6.2**);
- c) the serialization format (**§7.2**);
- d) the compression format (**§7.3**);
- e) the set of `Library` fields (**§8.1**) or their semantics (**§8.2**);
- f) the set of `Program` fields (**§8.3**) or their semantics;
- g) the set of registered AST node types (**§8.6**) or any node's serialized fields;
- h) the path syntax (**§11**) or the on-disk layout rules (**§12**).

**10.2.2.** The format version **SHALL NOT** be incremented for changes that are purely editorial or that do not affect the bytes on disk.

### 10.3. Backward Compatibility

**10.3.1.** A consumer of format version N **SHALL** read files written in any format version ≤ N if the reader explicitly supports those versions.

**10.3.2.** Version 1 is the base version; a version-1 consumer reads only version-1 files.

### 10.4. Version Consistency

**10.4.1.** The header version (§6.3) and the `Library.FormatVersion` field (§8.2.1) **SHALL** be equal.

**10.4.2.** A file in which these two values differ is invalid and **SHALL** be rejected (§13).

## 11. Library Identifiers

### 11.1. Syntax

**11.1.1.** A *library identifier* has one of the following forms:

```
lib:author/name
lib:author/name@version
```

where:

- `lib:` is a literal prefix;
- `author` is a non-empty sequence of characters not containing `/`, `@`, or whitespace;
- `name` is a non-empty sequence of characters not containing `/`, `@`, or whitespace;
- `@` is a literal separator, present only in the versioned form;
- `version` is a non-empty sequence of decimal digits and periods in the form `x.y.z`.

**11.1.2.** The `author` and `name` fields **SHOULD** be valid Skorpion identifiers (see **SNAR-A2 §8.2**), but this standard **SHALL NOT** reject a library identifier whose `author` or `name` uses hyphens (e.g., `my-lib`).

**11.1.3.** The `version` field, when present, **SHALL** match the `Version` field of the target library's `Library` record.

### 11.2. Parsing

**11.2.1.** A conforming implementation **SHALL** parse a library identifier by:

1. verifying the prefix `lib:`;
2. locating the last `@` (if any) and treating the text after it as the version;
3. splitting the remaining text at the first `/` to obtain `author` and `name`.

**11.2.2.** If the prefix is missing, the identifier is invalid.

**11.2.3.** If either `author` or `name` is empty, the identifier is invalid.

**11.2.4.** If `@` is present but the version is empty, the identifier is invalid.

**11.2.5.** If the version, once extracted, does not match the pattern `x.y.z`, the identifier is invalid. (This is stricter than the syntax in **§11.1.1**, which only requires "digits and periods"; a conforming implementation **SHALL** reject versions that do not contain at least one `.`.)

### 11.3. Unversioned Identifier Resolution

**11.3.1.** An unversioned identifier (`lib:author/name`) is resolved against the library directory by the rules of **§12.3**.

**11.3.2.** A versioned identifier (`lib:author/name@version`) is resolved by the rules of **§12.4**.

---

## 12. Locating Libraries on Disk

### 12.1. Library Directory

**12.1.1.** The library directory is the value of the SPC `libs` parameter (see **SNAR-A1 §12.1.1**). If not specified, it defaults to `libs/` relative to the project root.

**12.1.2.** Within the library directory, each library resides in a subdirectory named `{author}/{name}`.

**12.1.3.** A library directory that does not contain a `{author}/{name}` subdirectory for a requested library is treated as "library not found".

### 12.2. File Naming

**12.2.1.** A `.sklib` file **SHALL** have the `.sklib` extension.

**12.2.2.** The base name of the file (before `.sklib`) is **not** constrained by this standard. Multiple `.sklib` files **MAY** coexist in the same library directory, provided they have different versions (see **§12.4**).

**12.2.3.** Non-`.sklib` files in the library directory **SHALL** be ignored.

### 12.3. Unversioned Lookup

**12.3.1.** Given an unversioned identifier `lib:author/name`, the consumer **SHALL**:

1. enumerate the `.sklib` files in `{libs}/{author}/{name}/`;
2. if exactly one `.sklib` file is present, read it and use it;
3. if zero `.sklib` files are present, report "library not found";
4. if two or more `.sklib` files are present, report "multiple versions found; specify @version".

**12.3.2.** If the directory `{libs}/{author}/{name}/` does not exist, this is treated as "library not found".

### 12.4. Versioned Lookup

**12.4.1.** Given a versioned identifier `lib:author/name@version`, the consumer **SHALL**:

1. enumerate the `.sklib` files in `{libs}/{author}/{name}/`;
2. read each file's `Library` record;
3. if exactly one file's `Version` equals `version`, use that file;
4. if zero files match, report "library not found at version";
5. if two or more files match, report "multiple files with the same version".

**12.4.2.** Files whose `Version` does not equal `version` **SHALL** be ignored.

**12.4.3.** A file in the directory that is not a valid `.sklib` file (§13) **SHALL** cause the lookup to fail with the appropriate error, even if another file in the same directory matches the requested version. The consumer **SHALL NOT** silently skip invalid files.

### 12.5. Validation of the Matched Record

**12.5.1.** After locating a file, the consumer **SHALL** verify that:

- a) the file's `Name` equals the `name` component of the identifier;
- b) the file's `Author` equals the `author` component of the identifier (if the file's `Author` field is non-empty);
- c) if the identifier was versioned, the file's `Version` equals the requested version.

**12.5.2.** A mismatch in `Name` or `Author` makes the file invalid (§13). A version mismatch **SHALL NOT** occur under §12.4, but if it does (e.g., due to a race condition), the file is invalid.

## 13. Error Handling

### 13.1. Error Codes

**13.1.1.** A conforming implementation **SHALL** report errors using the codes below. The specific presentation of these codes is implementation-defined; the codes themselves are normative.

| Code | Description |
|------|-------------|
| `SKLIB-E001` | File is too short to contain a valid header |
| `SKLIB-E002` | File does not begin with the magic bytes `SKLB` |
| `SKLIB-E003` | Header format version is not supported by this consumer |
| `SKLIB-E004` | Header format version does not match `Library.FormatVersion` |
| `SKLIB-E005` | Payload is not a valid gzip stream |
| `SKLIB-E006` | Decompressed payload is not valid gob encoding |
| `SKLIB-E007` | Decompressed payload contains an unregistered node type |
| `SKLIB-E008` | File contains trailing bytes after the payload |
| `SKLIB-E009` | `Library.Name` is empty or does not match the requested identifier |
| `SKLIB-E010` | `Library.Author` is empty or does not match the requested identifier |
| `SKLIB-E011` | `Library.Version` is empty or does not match the requested version |
| `SKLIB-E012` | Library directory does not contain the requested library |
| `SKLIB-E013` | Multiple `.sklib` files found; specify `@version` |
| `SKLIB-E014` | Multiple files match the requested version |
| `SKLIB-E015` | Library declares a dependency that has not been imported |
| `SKLIB-E016` | Library identifier is malformed |
| `SKLIB-E017` | Library is not configured (`libs` parameter missing) |

### 13.2. Error Reporting

**13.2.1.** A conforming reader **SHALL** report the first error it encounters and **SHALL** reject the file.

**13.2.2.** An implementation **MAY** report additional diagnostic information (such as the offending byte offset), but this information **SHALL NOT** affect whether the file is accepted or rejected.

**13.2.3.** A conforming writer **SHALL NOT** produce a file that a conforming reader would reject under §13.1. If the writer cannot produce a valid file, it **SHALL** report an error rather than write a malformed one.

## 14. Dependencies

### 14.1. Declaration

**14.1.1.** A library declares its dependencies in the `Library.Dependencies` field (§8.2.5).

**14.1.2.** Each element of `Dependencies` **SHALL** be either a full library identifier (`lib:author/name@version`) or the same identifier without the `lib:` prefix (`author/name@version`).

**14.1.3.** The version component **MAY** be omitted. If omitted, the dependency is satisfied by any version of the library, subject to §14.3.

**14.1.4.** A library **SHALL NOT** list itself as a dependency.

**14.1.5.** A library **SHALL NOT** list two dependencies that resolve to the same `author/name`.

### 14.2. Resolution Order

**14.2.1.** When a library `L` is loaded, its dependencies are resolved before `L` is considered loaded. If a dependency `D` in turn has dependencies, those are resolved first (recursively).

**14.2.2.** Circular dependency detection **SHALL** be performed by the same mechanism as circular source-file imports (see **SNAR-A3 §7**). A cyclic dependency graph is invalid.

### 14.3. Dependency Satisfaction

**14.3.1.** A declared dependency is *satisfied* if and only if the library identified by the dependency's identifier has already been imported into the current project by the same import manager (either directly via a `use` statement or transitively via another library's dependency list).

**14.3.2.** When the dependency declares no version, any loaded version of the library satisfies it.

**14.3.3.** When the dependency declares a version, the loaded library **SHALL** have exactly that version.

**14.3.4.** If a declared dependency is not satisfied, the loaded library is invalid and **SHALL** be rejected with `SKLIB-E015`.

**14.3.5.** A conforming implementation **SHOULD** include in the diagnostic the hint that the missing dependency must be added as an import before the dependent library.

### 14.4. Transitive Dependencies

**14.4.1.** A library's dependencies are not required to be explicitly imported by the top-level project if they are already reachable via some other library in the dependency graph.

**14.4.2.** The consumer **SHALL** compute the transitive closure of the dependency graph and **SHALL** report any missing library (a library that appears as a dependency but is not present in the library directory) as an error.

---

## 15. Interaction with the Skorpion Compiler

### 15.1. Exported Functions

**15.1.1.** Only functions in `Program.Functions` whose `IsExport` field is `true` are visible to a consumer of the library.

**15.1.2.** Non-exported functions remain in `Program.Functions` in the payload (so that library-internal calls resolve correctly), but the consumer **SHALL NOT** make them available by name to the importing program.

**15.1.3.** The `AllFunctions` recomputation (§8.4) **SHALL** include both exported and non-exported functions of the library, so that internal calls work.

### 15.2. Error-Type Visibility

**15.2.1.** All `ErrorDecl` records in `Program.ErrorDecls` are visible to a consumer, regardless of whether the corresponding functions are exported.

**15.2.2.** A consumer **SHALL** use the `Module` field (§8.5) to disambiguate error types with the same local name from different libraries.

### 15.3. includeC Blocks

**15.3.1.** `Program.GlobalIncludeC` is propagated from a library to its importer as specified in **SNAR-A3 §12.15**. The payload's `GlobalIncludeC` field is the complete list of top-level `includeC` blocks to be propagated.

### 15.4. Imports of a Library

**15.4.1.** `Program.Imports` records the imports that the library itself declared. A consumer uses this to (a) detect missing dependencies and (b) resolve names during any post-load analysis.

**15.4.2.** A consumer **SHALL NOT** re-execute the imports of a loaded library; the library's AST is self-contained.

---

## 16. Writing Conformance

### 16.1. Producer Obligations

**16.1.1.** A conforming producer **SHALL**:

- a) write the header per §6;
- b) serialize the `Library` record per §8, with `AllFunctions` cleared;
- c) register all node types listed in §8.6 before serialization;
- d) compress the serialized bytes per §7.3;
- e) write no bytes after the payload.

**16.1.2.** A conforming producer **SHALL** populate every `Library` field per §8.2.

**16.1.3.** A conforming producer **SHALL NOT** emit a node type not listed in §8.6.

### 16.2. Field Consistency

**16.2.1.** A conforming producer **SHALL** set `Library.FormatVersion` to the version declared in the header.

**16.2.2.** A conforming producer **SHALL** set `Library.Module` on every `ErrorDecl` to the library's `Name`.

**16.2.3.** A conforming producer **SHALL** verify that all declared dependencies (§14) are satisfiable from the current import manager before writing.

---

## 17. Reading Conformance

### 17.1. Consumer Obligations

**17.1.1.** A conforming consumer **SHALL**:

- a) verify the header per §6 and report §13 errors on mismatch;
- b) decompress the payload per §7.3;
- c) decode the payload using gob per §7.2, with all node types (§8.6) registered;
- d) verify §10.4;
- e) verify §12.5 after matching against a library identifier;
- f) recompute `AllFunctions` per §8.4.

**17.1.2.** A conforming consumer **SHALL NOT** mutate the payload in place. If it needs to modify the `Program` (for example, to add resolved import functions to `AllFunctions`), it **SHALL** produce a new in-memory value.

**17.1.3.** A conforming consumer **SHOULD NOT** eagerly parse or analyze the `Program` payload. Lazy consumption is permitted.

---

## 18. Examples

### 18.1. Byte Layout of a Minimal File

The following example shows the byte layout of a minimal `.sklib` file whose payload, after decompression, decodes to:

```
Library{
  FormatVersion: 1,
  Name:          "Mini",
  Version:       "0.1.0",
  Author:        "alice",
  Dependencies:  [],
  Program:       Program{Imports: [], Functions: [], ErrorDecls: [], GlobalIncludeC: []},
}
```

| Offset | Bytes | Interpretation |
|--------|-------|----------------|
| 0 | `53` | `S` |
| 1 | `4B` | `K` |
| 2 | `4C` | `L` |
| 3 | `42` | `B` |
| 4 | `01` | Format version 1 |
| 5… | `1F 8B 08 00 …` | gzip magic bytes, followed by gzip-deflated gob data |
| end | — | No trailing bytes |

The payload's exact length depends on the serializer; the gzip header magic bytes `1F 8B` (§7.3, RFC 1952) **SHALL** appear immediately after the header.

### 18.2. Library Identifier Parsing

| Input | `author` | `name` | `version` |
|-------|----------|--------|-----------|
| `lib:alice/core` | `alice` | `core` | — |
| `lib:alice/core@1.0.0` | `alice` | `core` | `1.0.0` |
| `lib:iamtowvee/MyLib@2.3.1` | `iamtowvee` | `MyLib` | `2.3.1` |
| `lib:alice/my-lib@0.0.1` | `alice` | `my-lib` | `0.0.1` |
| `alice/core` | — | — | invalid (missing `lib:`) |
| `lib:alice/` | — | — | invalid (empty `name`) |
| `lib:alice/core@` | — | — | invalid (empty `version`) |
| `lib:alice/core@1` | — | — | invalid (version must be `x.y.z`) |

### 18.3. Directory Layout

A typical project after installing two libraries might look like:

```
project/
├── manifest.spc
├── libs/
│   ├── alice/
│   │   └── core/
│   │       └── core-1.0.0.sklib
│   └── iamtowvee/
│       └── MyLib/
│           ├── MyLib-1.0.0.sklib
│           └── MyLib-1.1.0.sklib
└── src/
    └── main.sk
```

Resolving `lib:alice/core` finds exactly one file (`core-1.0.0.sklib`), so the unversioned form succeeds.

Resolving `lib:iamtowvee/MyLib` finds two files, so the unversioned form fails with `SKLIB-E013`. Resolving `lib:iamtowvee/MyLib@1.1.0` reads both files and selects the one whose `Version` is `1.1.0`.

## Appendix A — Complete Byte-Level Layout

The following diagram summarizes the byte-level layout of a `.sklib` file.

```
+--------+--------+--------+--------+--------+-------------------------------+
| 0x53   | 0x4B   | 0x4C   | 0x42   | 0x01   |  gzip(gob(Library))           |
| 'S'    | 'K'    | 'L'    | 'B'    | ver    |  ... variable length ...      |
+--------+--------+--------+--------+--------+-------------------------------+
|<-------- magic bytes -------->|<--->|<---------- payload ---------------->|
|<---------------------- header (5 bytes) ----->|<----- body (≥1 byte) ---->|
```

The first bytes of the payload **SHALL** be the gzip magic bytes `1F 8B` (RFC 1952), because the payload is a gzip stream.

## Appendix D — Path and Dependency Examples

### D.1. Valid Library Identifiers

| Identifier | Author | Name | Version |
|------------|--------|------|---------|
| `lib:alice/core` | `alice` | `core` | none |
| `lib:alice/core@1.0.0` | `alice` | `core` | `1.0.0` |
| `lib:iamtowvee/MyLib@2.3.1` | `iamtowvee` | `MyLib` | `2.3.1` |
| `lib:alice/my-lib@0.0.1` | `alice` | `my-lib` | `0.0.1` |

### D.2. Invalid Library Identifiers

| Identifier | Reason |
|------------|--------|
| `alice/core` | Missing `lib:` prefix |
| `lib:` | Empty `author` and `name` |
| `lib:alice` | Missing `/name` |
| `lib:alice/` | Empty `name` |
| `lib:/core` | Empty `author` |
| `lib:alice/core@` | Empty version |
| `lib:alice/core@1` | Version not in `x.y.z` form |
| `lib:alice/core@1.0.0.0` | Version has too many components |

### D.3. Dependency Satisfaction

Suppose `lib:alice/core@1.0.0` declares:

```
Dependencies: ["lib:bob/utils@0.1.0"]
```

To load `lib:alice/core@1.0.0`, the implementation must first have loaded `lib:bob/utils@0.1.0`. If the importing program does not include a `use lib:bob/utils@0.1.0` statement (or a dependency edge that pulls it in), loading `alice/core` fails with `SKLIB-E015`.

Conversely, if `alice/core` declared:

```
Dependencies: ["lib:bob/utils"]
```

then any loaded version of `lib:bob/utils` satisfies the dependency. If the loader has already loaded `lib:bob/utils@0.2.0` for another reason, `alice/core` loads successfully.
