# SNAR-A1

## Skorpion Norms And Rules, A generation. Standard A1

### Skorpion Project Configuration (SPC) Language

---

## 1. Scope

**1.1.** This standard defines the structure of **Skorpion Project Configuration** files with the `*.spc` extension.

**1.2.** This standard specifies:

- a) the character set permitted in source text;
- b) the lexical structure of parameters, values, interpolation sequences, and References;
- c) the syntactic rules for parameter records and file structure;
- d) the semantics of parameter binding, resolution, and value storage;
- e) the reserved parameter names and their required types in `manifest.spc`;
- f) the format of the `env` and `execute` structured String values;
- g) the conformance rules for `*.spc` files.

**1.3.** This standard does **not** specify:

- a) the rules of the Skorpion programming language — see **SNAR-A2** through **SNAR-A4**;
- b) the behavior of the consumer of a configuration file after interpretation;
- c) implementation details of any particular configuration parser.

**1.4.** In case of any conflict between this standard and other documents of the SNAR-A generation regarding the SPC language, this standard takes precedence.

---

## 2. Conformance

**2.1.** A conforming `*.spc` file **SHALL** satisfy every rule of this standard.

**2.2.** A `*.spc` file that violates at least one rule of this standard **SHALL** be considered invalid and **SHALL NOT** conform to this standard.

**2.3.** Partial conformance is **not defined** by this standard. A file either conforms or does not conform.

**2.4.** The local formulations of invalidity scattered throughout this standard (e.g., "is invalid and does not conform to this standard") are **informative**; they restate **§2.2** for convenience and do not create additional conformance rules.

**2.5.** This standard uses the keywords **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** as defined in RFC 2119.

## 4. Terms and Definitions

**Configuration file** — a source text with the `*.spc` extension, structured according to this standard.

**Parameter** — a named value assigned within a configuration file. See **§10.1**.

**Parameter name** — an identifier serving as the key of a parameter. See **§6.2**.

**Reserved parameter name** — a name listed in the table of **§12.1.1**.

**Custom parameter name** — an identifier (see **§6.2**) that is not reserved. See **§11.4**.

**String value** — a scalar value enclosed in Quote characters. See **§8.2**.

**Array value** — an ordered list of elements enclosed between LParen and RParen. See **§8.5**.

**Interpolation sequence** — a substring of a String value of the form `{name}`. See **§9.1**.

**Reference** — an Array element of the form `&name`. See **§9.2**.

**Resolution** — the process of replacing an interpolation sequence or a Reference with the value of the parameter it refers to. See **§11.3**.

**Declaration order** — the order in which parameters appear in a source text from top to bottom. See **§10.7**.

## 5. Configuration Text

### 5.1. Character Encoding

**5.1.1.** A configuration file **SHALL** be interpreted as a sequence of characters encoded in **UTF-8**.

**5.1.2.** The behavior of a conforming implementation on source text that is not valid UTF-8 is **undefined** by this standard.

**5.1.3.** Outside String values, only the characters listed in **§6.1.1** are permitted. Any other character is a **syntactic error** (see **§13.2**).

**5.1.4.** Within a String value, any printable ASCII character (U+0020 through U+007E) except Quote is permitted. See **§8.2.3**.

### 5.2. Line Terminators

**5.2.1.** A *line terminator* is one of the following:

- a) the character U+000A (Line Feed);
- b) the character U+000D (Carriage Return);
- c) the two-character sequence U+000D U+000A (Carriage Return followed by Line Feed).

**5.2.2.** The three forms listed in **§5.2.1** are **equivalent** for all purposes of this standard, including line numbering and line-based parsing.

### 5.3. Positions

**5.3.1.** A *position* is a pair *(line, column)* of positive integers, where *line* is the 1-based index of the line containing the position and *column* is the 1-based index of the character within that line.

**5.3.2.** A conforming implementation **SHOULD** report the position of any syntactic error (see **§13.2**) as the position of the first character of the malformed construct.

**5.3.3.** This standard does **not** require any specific error-position reporting format.

## 6. Character Set and Identifier

### 6.1. Character Set

**6.1.1.** The characters of the SPC lexical vocabulary outside String values are the following:

| Character Name | Lexeme | Codepoint |
|----------------|--------|-----------|
| LBracket | `[` | U+005B |
| RBracket | `]` | U+005D |
| LParen | `(` | U+0028 |
| RParen | `)` | U+0029 |
| Comma | `,` | U+002C |
| Quote | `"` | U+0022 |
| LBrace | `{` | U+007B |
| RBrace | `}` | U+007D |
| Ampersand | `&` | U+0026 |
| Hash | `#` | U+0023 |
| Exclamation | `!` | U+0021 |
| Space | ` ` | U+0020 |
| Horizontal Tab | `\t` | U+0009 |
| Line Feed | `\n` | U+000A |
| Carriage Return | `\r` | U+000D |

**6.1.2.** A character not listed in **§6.1.1** **SHALL NOT** appear outside a String value. Such a character is a **syntactic error**.

**6.1.3.** Within a String value, any printable ASCII character (U+0020 through U+007E) except Quote is permitted, subject to the interpolation rule (see **§8.2**).

**6.1.4.** In particular, the Equal Sign character (`=`, U+003D) is **not** part of the SPC lexical vocabulary outside String values. It is significant only within the `env` String value (see **§12.4**).

**6.1.5.** The Exclamation character is significant only as the second character of the comment introducer `#!` (see **§7.2**). Its occurrence in any other position outside a String value is a syntactic error.

### 6.2. Identifiers

**6.2.1.** An *identifier* is a sequence of characters used as a parameter name, a reference name, or an interpolation name.

**6.2.2.** The lexical grammar of an identifier is:

```
IdentifierStart :: [A-Za-z_]
IdentifierPart  :: IdentifierStart | [0-9]
Identifier      :: IdentifierStart IdentifierPart*
```

**6.2.3.** An identifier **SHALL NOT** be empty.

**6.2.4.** An identifier **SHALL** begin with a letter (`A`–`Z`, `a`–`z`) or an underscore (`_`).

**6.2.5.** An identifier **SHALL NOT** begin with a digit.

**6.2.6.** Identifiers are **case-sensitive**. `name` and `Name` are distinct identifiers.

## 7. Whitespace and Comments

### 7.1. Whitespace

**7.1.1.** Whitespace is any of:

- Space `U+0020`;
- Horizontal Tabulation `U+0009`;
- Carriage Return `U+000D`;
- Line Feed `U+000A`.

**7.1.2.** Whitespace is **insignificant** outside String values; a conforming implementation **SHALL** ignore it.

**7.1.3.** Whitespace **MAY** appear in the following positions:

- a) before a parameter (leading whitespace of a line);
- b) after a parameter (trailing whitespace of a line);
- c) between parameters on different lines;
- d) between a comment and the following parameter or end of file;
- e) between elements of an Array;
- f) before or after a Comma inside an Array.

**7.1.4.** Whitespace **SHALL NOT** be placed in the positions listed in **§10.2.3** (the adjacency rule).

**7.1.5.** Whitespace within a String value is **significant** and is part of that value.

**7.1.6.** Within the `env` String, whitespace characters immediately before or immediately after a Comma are **insignificant** (see **§12.4.4**).

### 7.2. Comments

**7.2.1.** A comment begins with the two-character sequence `#!` and ends at the end of the current line.

**7.2.2.** A comment is recognized **only at the beginning of a line**, optionally preceded by whitespace.

**7.2.3.** A `#!` sequence appearing anywhere other than the beginning of a line (after optional leading whitespace) is **not** a comment. The interpretation of such a line is **undefined** by this standard.

**7.2.4.** The content of a comment is **insignificant**.

**7.2.5.** A comment **SHALL NOT** appear inside an Array value. A record in which a comment appears inside an Array value is invalid.

**7.2.6.** The sequence `#!` inside a String value is **not** a comment; it is part of the String value.

## 8. Values

### 8.1. Value Types

**8.1.1.** The SPC language recognizes values of exactly two types: **String** and **Array**.

**8.1.2.** Each value **SHALL** belong to exactly one of the two types.

**8.1.3.** The textual forms `true`, `false`, `123`, `1.5`, and `name` are **not** separate value types. They are ordinary String values when enclosed in Quote characters, and syntactic errors when not enclosed.

### 8.2. String Values

**8.2.1.** A String value is an arbitrary sequence of printable ASCII characters enclosed in Quote characters.

**8.2.2.** The lexical grammar of a String value is:

```
StringChar      :: ? any printable ASCII except `"` and `{` ?
Interpolation   :: "{" Identifier "}"
String          :: '"' (StringChar | Interpolation)* '"'
```

**8.2.3.** A String value **MAY** contain any printable ASCII character (U+0020 through U+007E) except Quote.

**8.2.4.** A Quote character **SHALL NOT** appear inside a String value. A record in which a String value contains an internal Quote character is invalid.

**8.2.5.** The LBrace character (`{`) is permitted within a String value, but it begins an interpolation sequence (see **§9.1**). The RBrace character (`}`), Ampersand (`&`), Backslash (`\`), and all other printable ASCII characters are **literal** inside a String value.

**8.2.6.** A String value **SHALL** be terminated by the closing Quote. A String value without a closing Quote is invalid.

**8.2.7.** The length of a String value is not limited by this standard.

### 8.3. String Atomicity

**8.3.1.** A String value is **atomic** for the purpose of delimiter counting.

**8.3.2.** An `(` or `)` character inside a String value is **not** an array delimiter.

**8.3.3.** A `,` character inside a String value is **not** an element separator.

**8.3.4.** A `[` or `]` character inside a String value is **not** a parameter delimiter.

### 8.4. Escape Sequences

**8.4.1.** The SPC language **does not define** any escape sequences.

**8.4.2.** A Backslash character within a String value is a literal Backslash and has no special meaning.

**8.4.3.** There is **no** way to write a literal LBrace character within a String value; an LBrace character within a String value always begins an interpolation sequence. See **§9.1**.

**8.4.4.** The absence of escape sequences is **intentional**.

### 8.5. Array Values

**8.5.1.** An Array value is an ordered list of elements enclosed between LParen and RParen.

**8.5.2.** The lexical grammar of an Array value is:

```
Element  ::= String | Reference
Array    ::= "(" (Element ("," Element)* ","?)? ")"
```

**8.5.3.** Each element **SHALL** be either a String value (see **§8.2**) or a Reference (see **§9.2**).

**8.5.4.** An Array value **SHALL NOT** contain another Array value as an element. A record in which an Array value appears as an element of another Array value is invalid.

**8.5.5.** A Comma is required between adjacent Array elements.

**8.5.6.** A Comma after the last element of an Array value is **optional**.

**8.5.7.** A Comma before the first element of an Array value is **forbidden**.

**8.5.8.** Two consecutive Comma characters within an Array value are **forbidden**.

**8.5.9.** An Array value **MAY** contain zero elements. An empty Array is written as `()`.

## 9. Interpolation and Reference

### 9.1. Interpolation Sequence

**9.1.1.** An interpolation sequence is a substring of a String value of the form `{name}`, where `name` is an identifier (see **§6.2**).

**9.1.2.** An interpolation sequence **SHALL** be closed by RBrace. An interpolation sequence that is not closed by RBrace before the end of the enclosing String value is invalid.

**9.1.3.** An interpolation sequence **SHALL NOT** have an empty name. A record containing `{}` within a String value is invalid.

**9.1.4.** An interpolation sequence **SHALL** refer to a parameter that is already declared (see **§10.7**). An interpolation sequence that refers to an undeclared parameter is invalid.

**9.1.5.** An interpolation sequence **SHALL NOT** refer to an Array parameter; only String-valued parameters may be referenced by interpolation.

**9.1.6.** An interpolation sequence **MAY** refer to **any** declared parameter, whether reserved (see **§12.1**) or custom (see **§11.4**).

**9.1.7.** An interpolation sequence **SHALL NOT** contain another interpolation sequence. A record in which an interpolation sequence contains an LBrace character before its closing RBrace is invalid.

**9.1.8.** The resolved value of an interpolation sequence is **always a String** (see **§11.3.4**).

### 9.2. Reference

**9.2.1.** A Reference is an Array element of the form `&name`, where `name` is an identifier (see **§6.2**).

**9.2.2.** A Reference **MAY** appear **only** as an element of an Array value. A Reference outside an Array value is invalid.

**9.2.3.** Consequently, the Ampersand character is **not** part of the SPC lexical vocabulary outside Array elements. An Ampersand in any other position is invalid.

**9.2.4.** A Reference **SHALL** refer to a parameter that is already declared (see **§10.7**). A Reference to an undeclared parameter is invalid.

**9.2.5.** A Reference **SHALL NOT** refer to an Array parameter; only String-valued parameters may be referenced.

**9.2.6.** A Reference **MAY** refer to **any** declared parameter, whether reserved (see **§12.1**) or custom (see **§11.4**).

**9.2.7.** A Reference `&name` within an Array is **semantically equivalent** to a String element `"{name}"`. Both forms are permitted.

**9.2.8.** The resolved value of a Reference is **always a String** (see **§11.3.4**).

## 10. Syntax

### 10.1. Parameter

**10.1.1.** A parameter is written according to the following pattern:

```
Parameter ::= Identifier "[" Value "]"
```

where `Value` is a String value (see **§8.2**) or an Array value (see **§8.5**).

**10.1.2.** The elements of a parameter **SHALL** appear in the following order:

- a) `Identifier` — the parameter name;
- b) `[` — LBracket;
- c) `Value` — the value;
- d) `]` — RBracket.

**10.1.3.** A parameter **SHALL** contain exactly one `Value`.

**10.1.4.** A parameter **SHALL** contain exactly one parameter name.

### 10.2. Parameter Delimiters and Adjacency

**10.2.1.** The delimiter pair LBracket/RBracket is **mandatory** for every parameter, regardless of the type of `Value`. A record in which these delimiters are omitted is invalid.

**10.2.2.** The parameter delimiters `[` and `]`, the array delimiters `(` and `)`, and the separator `,` are **not part of any value**. They delimit or separate values and are not interpreted as values.

**10.2.3.** No whitespace character **SHALL** be placed:

- a) between `Identifier` and `[`;
- b) between `[` and `Value`;
- c) between `Value` and `]`.

**10.2.4.** A record in which whitespace is placed in any of the positions listed in **§10.2.3** is invalid.

### 10.3. Array Parameters

**10.3.1.** For a parameter whose value is an Array:

- a) the parameter delimiters `[` and `]` are **mandatory**;
- b) the array delimiters `(` and `)` are **mandatory**;
- c) the array delimiters `(` and `)` **SHALL** be placed inside the parameter delimiters `[` and `]`.

**10.3.2.** The correct order of delimiters for an Array parameter is:

```
Identifier "[" "(" elements ")" "]"
```

**10.3.3.** The `[` **SHALL** be placed immediately after the parameter name; the `(` **SHALL** be placed immediately after `[`; the `)` **SHALL** be placed immediately before `]`; the `]` **SHALL** be placed immediately after `)`.

**10.3.4.** A record in which the array delimiters `(` and `)` are placed outside the parameter delimiters `[` and `]` is invalid.

### 10.4. String Parameters

**10.4.1.** For a parameter whose value is a String:

- a) the parameter delimiters `[` and `]` are **mandatory**;
- b) the array delimiters `(` and `)` are **forbidden**.

**10.4.2.** A record in which the array delimiters `(` and `)` are used for a String value is invalid.

### 10.5. Element Separators

**10.5.1.** Within an Array value:

- a) a Comma is placed between each pair of adjacent elements;
- b) a Comma after the last element is optional;
- c) a Comma before the first element is forbidden;
- d) two consecutive Comma characters are forbidden.

**10.5.2.** The number of Comma characters within an Array value is either equal to the number of elements minus one, or equal to the number of elements.

**10.5.3.** Comma characters are **not part of any value** (see **§10.2.2**).

### 10.6. File Structure

**10.6.1.** A configuration file consists of zero or more lines.

**10.6.2.** A configuration file is parsed **line by line**. Each parameter **SHALL** occupy exactly one line, and a line **SHALL** contain at most one parameter.

**10.6.3.** A line is one of the following:

- a) **empty** — contains only whitespace characters;
- b) **comment** — after optional leading whitespace, begins with `#!`;
- c) **parameter** — after optional leading whitespace, contains exactly one parameter followed by optional trailing whitespace.

**10.6.4.** Lines are separated by line terminators (see **§5.2**).

**10.6.5.** A file **MAY** end with or without a line terminator.

**10.6.6.** An empty file is **valid** under this section. However, `manifest.spc` has additional requirements (see **§12.2**).

### 10.7. Declaration Order

**10.7.1.** Parameters are processed in the order they appear in the file, from top to bottom.

**10.7.2.** A parameter **MAY** reference only parameters declared **above** it.

**10.7.3.** An interpolation sequence (see **§9.1**) or a Reference (see **§9.2**) that refers to a parameter declared **below** it is invalid.

## 11. Semantics

### 11.1. Parameter Binding

**11.1.1.** The parameter name acts as the **key** of the parameter; it specifies the name by which the parameter is identified.

**11.1.2.** The `Value` acts as the **value** of the parameter.

**11.1.3.** The `Value` is assigned to the parameter with the name specified by the parameter name.

**11.1.4.** Two parameters with the same name within a single configuration file are **forbidden**. A record in which two parameters have the same name is invalid.

**11.1.5.** The uniqueness requirement of **§11.1.4** applies regardless of whether the parameters are reserved or custom.

### 11.2. Value Storage

**11.2.1.** Every `Value` **SHALL** be stored as either a String or an Array of Strings, after all interpolation sequences and References have been resolved.

**11.2.2.** The order of elements within an Array value **SHALL** be preserved during interpretation.

### 11.3. Resolution

**11.3.1.** An interpolation sequence `{name}` within a String value **SHALL** be replaced by the String value of the parameter `name`.

**11.3.2.** A Reference `&name` within an Array element **SHALL** be replaced by the String value of the parameter `name`.

**11.3.3.** Resolution **SHALL** be performed at interpretation time, using the values known at the point of the referencing parameter in declaration order.

**11.3.4.** The result of resolving an interpolation sequence or a Reference is **always a String**.

**11.3.5.** An interpolation sequence or a Reference that resolves to an Array is invalid.

### 11.4. Reserved and Custom Names

**11.4.1.** A **reserved parameter name** is a name listed in the table of **§12.1.1**.

**11.4.2.** A **custom parameter name** is an identifier (see **§6.2**) that is not reserved.

**11.4.3.** The set of reserved names is **closed**. This standard does **not** reserve any name by prefix, suffix, or pattern.

**11.4.4.** The presence of a custom parameter does **not** by itself make a file invalid.

**11.4.5.** The meaning of a custom parameter name is **not defined** by this standard. It is defined by the consumer of the configuration file.

**11.4.6.** A custom parameter **MAY** be referenced by interpolation (see **§9.1**) or by a Reference (see **§9.2**) exactly like a reserved parameter.

**11.4.7.** A custom parameter is stored in the same way as a reserved parameter: its value is a String or an Array of Strings.

## 12. The `manifest.spc` File

**12.1.** The file named `manifest.spc` is the Skorpion project configuration file.

### 12.1. Reserved Parameters

**12.1.1.** This standard defines the following reserved parameters:

| Parameter | Type | Required | Purpose |
|-----------|------|----------|---------|
| `name` | String | Yes | Project name |
| `version` | String | Yes | Project version |
| `main` | String | Yes | Path to the main file |
| `authors` | Array of String | Required for `build-lib` | Author names |
| `target` | Array of String | No | Platform or platforms for the build |
| `libs` | String | No | Path to the libraries directory |
| `dependencies` | Array of String | No | Library dependencies |
| `env` | String | No | Environment variables applied during the project build (not applied to the built binaries) |
| `execute` | String | No | Arguments applied to the command during the project build |
| `buildOutName` | String | No | Name of the build output file |
| `buildOutPath` | String | No | Path to the build output file |
| `testOutName` | String | No | Name of the test build output file |
| `testOutPath` | String | No | Path to the test build output file |

**12.1.2.** Names not listed in **§12.1.1** are **custom** (see **§11.4**).

### 12.2. Required Parameters

**12.2.1.** The required parameters of `manifest.spc` are `name`, `version`, and `main`.

**12.2.2.** The parameter `authors` is required when the project is built with `build-lib`.

**12.2.3.** A `manifest.spc` file in which at least one required parameter is absent is invalid.

**12.2.4.** An empty `manifest.spc` file is invalid because it lacks all required parameters.

### 12.3. Type Fixation

**12.3.1.** For each reserved parameter listed in **§12.1.1**, the value type is fixed by the *Type* column of that table.

**12.3.2.** A value of a type different from the fixed type is invalid.

**12.3.3.** Examples of type violation:

- a) a reserved String parameter given an Array value;
- b) a reserved Array parameter given a String value.

**12.3.4.** For every parameter in **§12.1.1**, the parameter delimiters `[` and `]` are mandatory.

**12.3.5.** For the parameters `authors`, `target`, and `dependencies`, whose type is Array of String, the array delimiters `(` and `)` are also mandatory.

### 12.4. Format of the `env` Parameter

**12.4.1.** The value of the parameter `env` is a single String containing zero or more variable definitions.

**12.4.2.** A variable definition within the `env` String consists of a name, an Equal Sign, and a value:

```
VarDef ::= Identifier "=" VarValue
```

**12.4.3.** Variable definitions within the `env` String are separated by a Comma.

**12.4.4.** Whitespace characters immediately before or immediately after a Comma within the `env` String are insignificant.

**12.4.5.** The name of a variable within the `env` String is an identifier (see **§6.2**); it **SHALL NOT** begin with a digit.

**12.4.6.** The value of a variable within the `env` String consists of any printable ASCII characters **except** Comma.

**12.4.7.** A Comma character within the value of a variable definition is forbidden and cannot be escaped.

**12.4.8.** The first Equal Sign within a variable definition is the separator between the name and the value. Any subsequent Equal Sign is part of the value.

**12.4.9.** Whitespace characters within the value of a variable definition (after the first Equal Sign) are significant and are part of the value.

**12.4.10.** The absence of an escape sequence for Comma is **intentional**.

### 12.5. Format of the `execute` Parameter

**12.5.1.** The value of the parameter `execute` is a single String containing zero or more arguments.

**12.5.2.** Arguments within the `execute` String are separated by one or more whitespace characters (Space or Tab).

**12.5.3.** An argument within the `execute` String consists of one or more printable ASCII characters **except** Space and Tab.

**12.5.4.** The `execute` String **does not support** quoting. A Quote character within the `execute` String is a literal Quote and does not group characters into a single argument.

**12.5.5.** If the `execute` String is empty, the `execute` parameter contains zero arguments. A record in which the `execute` String is empty is valid.

**12.5.6.** The absence of quoting in the `execute` String is **intentional**.

### 12.6. Custom Parameters

See **§11.4**.

## 13. Errors and Conformance

### 13.1. Conformance

**13.1.1.** A `*.spc` file conforms to this standard if and only if all rules of this standard are satisfied.

### 13.2. Non-Conformance

**13.2.1.** A `*.spc` file that violates at least one rule of this standard does **not conform** to this standard.

**13.2.2.** A conforming implementation **SHALL** report every violation it detects.

**13.2.3.** The set of error conditions recognized by a conforming implementation **SHOULD** include at least:

- a) a character outside the permitted character set (see **§6.1.2**);
- b) a parameter name that is not an identifier (see **§6.2**);
- c) a missing or misplaced parameter delimiter (see **§10.2**);
- d) a missing or misplaced array delimiter (see **§10.3**);
- e) an incorrectly placed element separator (see **§10.5**);
- f) a nested Array value (see **§8.5.4**);
- g) a String value with an internal Quote (see **§8.2.4**);
- h) an unterminated String value (see **§8.2.6**);
- i) an unclosed interpolation sequence (see **§9.1.2**);
- j) an empty interpolation name (see **§9.1.3**);
- k) an interpolation referring to an undeclared parameter (see **§9.1.4**);
- l) an interpolation referring to an Array parameter (see **§9.1.5**);
- m) a nested interpolation (see **§9.1.7**);
- n) a Reference outside an Array value (see **§9.2.2**);
- o) a Reference to an undeclared parameter (see **§9.2.4**);
- p) a Reference to an Array parameter (see **§9.2.5**);
- q) two parameters with the same name (see **§11.1.4**);
- r) two parameters on the same line (see **§10.6.2**);
- s) for `manifest.spc`, the absence of a required parameter (see **§12.2**);
- t) for `manifest.spc`, a type mismatch on a reserved parameter (see **§12.3**).

### 13.3. Violation

**13.3.1.** A record that violates any rule of this standard is **invalid** and **does not conform** to this standard.

**13.3.2.** The local formulation of this consequence within individual rules is **informative** and does not create additional rules.

## 14. Grammar

### 14.1. Overview

**14.1.1.** This section provides an informative EBNF grammar for the SPC language.

**14.1.2.** Where this grammar and the textual rules of **§5–§13** disagree, the textual rules take precedence.

### 14.2. Grammar

```
File         ::= { Line }

Line         ::= { Whitespace }
                 ( Parameter | Comment | )
                 { Whitespace }
                 [ LineEnding ]

Parameter    ::= Identifier "[" Value "]"

Value        ::= String | Array

String       ::= '"' { StringChar | Interpolation } '"'

StringChar   ::= ? any printable ASCII except `"` and `{` ?

Interpolation ::= "{" Identifier "}"

Array        ::= "(" [ Element { "," Element } [ "," ] ] ")"

Element      ::= String | Reference

Reference    ::= "&" Identifier

Comment      ::= "#!" { ? any character except LineEnding ? }

Whitespace   ::= " " | "\t"

LineEnding   ::= "\n" | "\r\n" | "\r"

IdentifierStart ::= [A-Za-z_]
IdentifierPart  ::= IdentifierStart | [0-9]
Identifier      ::= IdentifierStart IdentifierPart*
```

### 14.3. Scope of the Grammar

**14.3.1.** The grammar of **§14.2** defines the **syntactic structure** of configuration files.

**14.3.2.** The **internal structure** of the `env` and `execute` String values is defined by **§12.4** and **§12.5** respectively and is **not** part of the grammar in **§14.2**.

## Appendix B — Examples of Valid Configurations

The following records conform to this standard:

```spc
name["MyProject"]
version["1.0.0"]
main["src/main.sk"]
buildOutName["myapp"]
buildOutPath["bin/"]
testOutName["myapp_test"]
testOutPath["test/"]
libs["libs/"]
authors[("Alice", "Bob")]
target[("linux", "windows", "macos")]
target[("linux")]
dependencies[("std", "math")]
dependencies[()]
env["PATH=/usr/bin,DEBUG=1"]
execute["--verbose --output=build"]
greeting["Hello, {name}!"]
label["{name}-{version}"]
alias[("&name", "custom")]
myCustomSetting["hello"]
buildFlags[("--release", "--strip")]
```

Additionally, the following files are valid:

- a file consisting of a single comment and no parameters;
- a file whose last Array parameter ends with a trailing Comma;
- a file ending with a comment that is not followed by a line ending.

In all cases above where `name`, `version`, or other referenced parameters appear inside interpolation sequences or References, those parameters are declared **above** the referencing parameter.

## Appendix C — Examples of Invalid Configurations

The following records do **not** conform to this standard:

- a parameter whose value is an Array but whose parameter delimiters are absent;
- a parameter whose value is an Array but whose array delimiters are placed outside the parameter delimiters;
- a parameter whose value is a String but whose array delimiters are present;
- a parameter whose Array value contains two consecutive Comma characters;
- a parameter whose Array value contains a leading Comma;
- a parameter whose Array value contains a nested Array;
- a parameter whose name contains a character outside `A–Z`, `a–z`, `0–9`, `_`;
- `1foo["bar"]` — custom name starting with a digit;
- `foo-bar["baz"]` — custom name containing a character outside the permitted set;
- `name[Hello]` — String value without Quote characters;
- `name["a"b"]` — internal Quote in a String value;
- `name["{undefined}-line"]` — Reference to an undeclared parameter via interpolation;
- `name["{target}-line"]` where `target` is an Array — interpolation of an Array;
- `name["{}"]` — empty interpolation name;
- `name["{name"]` — unclosed interpolation;
- `name["{a{b}"]` — nested interpolation;
- `name[(&authors)]` where `authors` is an Array — Reference to an Array;
- `name[(&undefined)]` — Reference to an undeclared parameter;
- `&name` outside an Array value;
- two parameters on the same line;
- a `manifest.spc` file in which at least one of the required parameters is absent;
- an empty `manifest.spc` file;
- a `manifest.spc` file where `target` is a String instead of an Array.
