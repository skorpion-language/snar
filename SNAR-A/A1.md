# SNAR-A1

## Skorpion Norms And Rules, A generation. Standard A1

This standard applies to Skorpion Project Configuration files with the `*.spc` extension.

---

## 1. Lexis

### 1.1. General Provisions

The SPC lexis is formed by the following characters:

| Character | Name |
|-----------|------|
| `[` | LBracket |
| `]` | RBracket |
| `"` | Quote |
| `'` | Apos |
| `\` | Backslash |
| `.` | Dot |
| `<` | Lt |
| `>` | Gt |
| `-` | Minus |
| `,` | Comma |
| Space | Space |
| Tab | Tab |
| LineFeed | LineFeed |
| CarriageReturn | CarriageReturn |

### 1.2. Rule of Lexical Closure

A character that is not listed in the table of Section 1.1 is **not part of the SPC lexis** and **does not conform to this standard**.

### 1.3. Rule of Value Types

The SPC lexer recognizes values of the following types: **String**, **Int**, **Float**, **Bool**, **Array**, and **Ident**.

### 1.4. Rule of Type Exclusivity

A single value belongs to exactly one of the types listed in Section 1.3. A value cannot belong to two or more types simultaneously.

### 1.5. Rule of Whitespace

Space, Tab, LineFeed, and CarriageReturn are whitespace characters.

#### 1.5.1. Rule of Whitespace Insignificance

Whitespace characters are **insignificant** outside String values. The lexer ignores them.

#### 1.5.2. Rule of Whitespace Permitted Positions

Whitespace characters may be placed:
- between a parameter and the next parameter;
- between a parameter and the end of file;
- between a parameter and a comment;
- between a comment and the next parameter;
- between a comment and the end of file.

#### 1.5.3. Rule of Whitespace Forbidden Positions

Whitespace characters are **forbidden**:
- between Param and LBracket;
- between LBracket and Value;
- between Value and RBracket;
- between LBracket and Lt;
- between Lt and the first element of an Array;
- between an element of an Array and Comma;
- between Comma and an element of an Array;
- between the last element of an Array and Gt;
- between Gt and RBracket.

#### 1.5.4. Rule of Whitespace Within String

Whitespace characters within a String value are **significant** and are part of the String value.

#### 1.5.5. Rule of Line Ending

A LineFeed character or a CarriageReturn followed by a LineFeed character is a line ending.

#### 1.5.6. Rule of Line Ending Equivalence

A LineFeed character and a CarriageReturn followed by a LineFeed character are **equivalent** as line endings.

#### 1.5.7. Rule of Lone CarriageReturn

A CarriageReturn character that is not followed by a LineFeed character is **whitespace**.

#### 1.5.8. Rule of Lone CarriageReturn as Line Ending

A CarriageReturn character that is not followed by a LineFeed character is **also treated as a line ending**.

#### 1.5.9. Rule of Line Ending Equivalence Extension

For the purposes of Section 1.6, a LineFeed character, a CarriageReturn followed by a LineFeed character, and a lone CarriageReturn character are **equivalent** as line endings.

---

### 1.6. Comments

#### 1.6.1. Rule of Comment Syntax

A comment starts with the sequence `#!` and ends with the end of line.

#### 1.6.2. Rule of Comment Content

The content of a comment is **insignificant** for SPC interpretation.

#### 1.6.3. Rule of Comment Position

A comment may be placed:
- at the beginning of a line;
- after a parameter on the same line;
- on a line without parameters.

#### 1.6.4. Rule of Comment Inside String

The sequence `#!` inside a String value is **not a comment**. It is part of the String value.

---

### 1.7. String

A **String** value is an arbitrary sequence of ASCII characters.

#### 1.7.1. Rule of String Length

The length of a String value is not limited by this standard.

#### 1.7.2. Rule of String Content

The permitted characters of a String value are determined by the specific parameter in which the value is used. The parameter may further restrict the permitted characters.

#### 1.7.3. Rule of String Enclosure

A String value is enclosed in a pair of:
- Quote — on both sides, or
- Apos — on both sides.

#### 1.7.4. Rule of String Enclosure Symmetry

The opening and closing characters of a String value must be identical. An opening Quote must be closed by Quote. An opening Apos must be closed by Apos.

#### 1.7.5. Rule of String Enclosure Uniformity

A String value must not be enclosed by different characters. A record with Quote on one side and Apos on the other side is **invalid** and **does not conform to this standard**.

#### 1.7.6. Rule of String Escape

The Backslash character is the escape character within a String value.

#### 1.7.7. Rule of String Escape Sequences

The following escape sequences are defined within a String value:

| Sequence | Meaning |
|----------|---------|
| `\"` | Quote |
| `\'` | Apos |
| `\\` | Backslash |
| `\n` | LineFeed |
| `\r` | CarriageReturn |
| `\t` | Tab |

#### 1.7.8. Rule of String Escape Closure

An escape sequence that is not listed in Section 1.7.7 is **invalid** and **does not conform to this standard**.

#### 1.7.9. Rule of String Escape Position

The Backslash character is placed immediately before the character it escapes. No other character may be placed between the Backslash and the escaped character.

#### 1.7.10. Rule of String Escape Uniqueness

A single escape sequence consists of exactly one Backslash and exactly one following character.

#### 1.7.11. Rule of String Escape Scope

An escape sequence affects only the character immediately following the Backslash. It has no effect on any other character.

---

### 1.8. Int

An **Int** value consists only of digits `0–9`.

#### 1.8.1. Rule of Int Sign

An Int value may optionally be preceded by a Minus character before the first digit.

#### 1.8.2. Rule of Int Sign Position

The Minus character is placed immediately before the first digit. No other character may be placed between the Minus and the first digit.

#### 1.8.3. Rule of Int Sign Singularity

A single Int value contains at most one Minus character.

#### 1.8.4. Rule of Int Content

An Int value contains only digits and at most one Minus character. Any other character within an Int value is **invalid** and **does not conform to this standard**.

#### 1.8.5. Rule of Int Leading Zeros

Leading zeros within an Int value are permitted. An Int value with leading zeros is interpreted as a decimal number.

---

### 1.9. Float

A **Float** value consists of digits `0–9` and a Dot character separating the integer and fractional parts.

#### 1.9.1. Rule of Float Sign

A Float value may optionally be preceded by a Minus character before the first digit.

#### 1.9.2. Rule of Float Sign Position

The Minus character is placed immediately before the first digit. No other character may be placed between the Minus and the first digit.

#### 1.9.3. Rule of Float Dot

A Float value contains exactly one Dot character.

#### 1.9.4. Rule of Float Dot Position

The Dot character is placed between the integer part and the fractional part. The Dot may not be the first character or the last character of a Float value.

#### 1.9.5. Rule of Float Content

A Float value contains only digits, exactly one Dot character, and at most one Minus character. Any other character within a Float value is **invalid** and **does not conform to this standard**.

---

### 1.10. Bool

A **Bool** value takes exactly one of two values: `true` or `false`.

#### 1.10.1. Rule of Bool Exclusivity

The Bool type has no other values. Any other value is **invalid** and **does not conform to this standard**.

#### 1.10.2. Rule of Bool Case

The values `true` and `false` are written in lowercase. A record in which these values are written in any other case is **invalid** and **does not conform to this standard**.

---

### 1.11. Array

An **Array** value is an ordered list of values of other types.

#### 1.11.1. Rule of Array Enclosure

An Array value is enclosed between Lt and Gt.

#### 1.11.2. Rule of Array Enclosure Symmetry

An opening Lt must be closed by Gt. A closing Gt must correspond to an opening Lt.

#### 1.11.3. Rule of Array Enclosure Pairing

Within a single Array value, the number of Lt characters equals the number of Gt characters.

This rule follows from Rule 1.11.3.3.

#### 1.11.3.1. Rule of Array Nesting Prohibition

An Array value **cannot** contain another Array value as an element.

A record in which an Array value is used as an element of another Array value is **invalid** and **does not conform to this standard**.

#### 1.11.3.2. Rule of Array Element Depth

Every element of an Array value is a value of a type other than Array.

#### 1.11.3.3. Rule of Array Enclosure Non-Nesting

Within a single Array value, the number of opening Lt characters is exactly one.

Within a single Array value, the number of closing Gt characters is exactly one.

A record in which an Array value contains more than one opening Lt or more than one closing Gt is **invalid** and **does not conform to this standard**.

#### 1.11.4. Rule of Array Elements

An Array value contains zero or more elements.

#### 1.11.5. Rule of Array Element Types

Each element of an Array value is a value of one of the types listed in Section 1.3.

#### 1.11.6. Rule of Array Element Type Exclusion

An Ident **cannot** be an Array value. A record in which an Ident is used as an Array value is **invalid** and **does not conform to this standard**.

#### 1.11.7. Rule of Array Separators

A Comma is required between adjacent Array elements.

#### 1.11.8. Rule of Array Trailing Separator

A Comma after the last element of an Array value is optional.

#### 1.11.9. Rule of Array Leading Separator

A Comma before the first element of an Array value is **forbidden**.

#### 1.11.10. Rule of Array Consecutive Separators

Two consecutive Comma characters within an Array value are **forbidden**.

#### 1.11.11. Rule of Array Empty

An Array value may contain no elements. An empty Array is written as Lt immediately followed by Gt.

---

### 1.12. Ident

An **Ident** value is written without brackets or quotes.

#### 1.12.1. Rule of Ident Content

An Ident value consists only of the characters `A–Z` and `a–z`.

#### 1.12.2. Rule of Ident Digit Exclusion

An Ident value contains no digits. A record in which an Ident value contains a digit is **invalid** and **does not conform to this standard**.

#### 1.12.3. Rule of Ident Underscore Exclusion

An Ident value contains no underscore characters. A record in which an Ident value contains an underscore is **invalid** and **does not conform to this standard**.

#### 1.12.4. Rule of Ident Enclosure Exclusion

An Ident value is not enclosed in brackets or quotes. A record in which an Ident value is enclosed in brackets or quotes is **invalid** and **does not conform to this standard**.

#### 1.12.5. Rule of Ident Case Sensitivity

Ident values are case-sensitive. `name` and `Name` are different Ident values.

#### 1.12.6. Rule of Ident Underscore and Digit Exclusion Rationale

The exclusion of digits and underscore characters from Ident values is **intentional**.

A record in which an Ident value contains a digit or an underscore character is **invalid** and **does not conform to this standard**.

The reserved parameter names listed in Section 4.1 are written in a form that does not violate Sections 1.12.2 and 1.12.3.

---

## 2. Syntax

### 2.1. Parameter

A configuration parameter is written according to the pattern:

Param, then LBracket, then Value, then RBracket.

where:
- Param — an identifier (Ident),
- LBracket — an opening square bracket,
- Value — a value of one of the permitted types,
- RBracket — a closing square bracket.

#### 2.1.1. Rule of Parameter Order

The elements of a parameter are written in the following order:

1. Param
2. LBracket
3. Value
4. RBracket

Any other order is **invalid** and **does not conform to this standard**.

#### 2.1.2. Rule of Parameter Adjacency

The elements of a parameter are written immediately one after another. No character may be placed between Param and LBracket, between LBracket and Value, between Value and RBracket.

#### 2.1.3. Rule of Parameter Single Value

A parameter contains exactly one Value.

#### 2.1.4. Rule of Parameter Single Parameter

A parameter contains exactly one Param.

---

### 2.2. Rule of Delimiters

The pair of LBracket and RBracket is **mandatory** for every parameter, regardless of the type of Value.

#### 2.2.1. Rule of Delimiter Independence

The type of Value does not affect the presence or absence of the parameter delimiters LBracket and RBracket.

#### 2.2.2. Rule of Delimiter Non-Value

The LBracket and RBracket delimiters are **not part of the value**. They delimit the parameter as a whole and are independent of the value contained within.

#### 2.2.3. Rule of Delimiter Presence

A record in which the parameter delimiters LBracket and RBracket are omitted for any value is **invalid** and **does not conform to this standard**.

---

### 2.3. Rule of Array Parameters

For a parameter whose value is of type **Array**:

- the parameter delimiters LBracket and RBracket are **mandatory**;
- the array delimiters Lt and Gt are **mandatory**;
- the array delimiters Lt and Gt are placed **inside** the parameter delimiters LBracket and RBracket.

#### 2.3.1. Rule of Array Parameter Order

The correct order of delimiters for an Array parameter is:

Param, then LBracket, then Lt, then elements, then Gt, then RBracket.

#### 2.3.2. Rule of Array Parameter Adjacency

The LBracket is placed immediately after Param. The Lt is placed immediately after LBracket. The Gt is placed immediately before RBracket. The RBracket is placed immediately after Gt.

#### 2.3.3. Rule of Array Parameter Omission

A record in which the parameter delimiters LBracket and RBracket are omitted for an Array value is **invalid** and **does not conform to this standard**.

#### 2.3.4. Rule of Array Parameter Displacement

A record in which the array delimiters Lt and Gt are placed outside the parameter delimiters LBracket and RBracket is **invalid** and **does not conform to this standard**.

---

### 2.4. Rule of Non-Array Parameters

For a parameter whose value is of a type other than **Array**:

- the parameter delimiters LBracket and RBracket are **mandatory**;
- the array delimiters Lt and Gt are **forbidden**.

#### 2.4.1. Rule of Non-Array Parameter Omission

A record in which the parameter delimiters LBracket and RBracket are omitted for a non-Array value is **invalid** and **does not conform to this standard**.

#### 2.4.2. Rule of Non-Array Parameter Displacement

A record in which the array delimiters Lt and Gt are used for a non-Array value is **invalid** and **does not conform to this standard**.

---

### 2.5. Rule of Element Separators

Within an Array value:

- a Comma is placed between each pair of adjacent elements;
- a Comma after the last element is optional;
- a Comma before the first element is **forbidden**;
- two consecutive Comma characters are **forbidden**;
- the presence of a Comma does not affect the requirement of the parameter delimiters LBracket and RBracket.

#### 2.5.1. Rule of Separator Count

The number of Comma characters within an Array value is either equal to the number of elements minus one, or equal to the number of elements.

#### 2.5.2. Rule of Separator Non-Value

A Comma character is **not part of any value**. It is a separator only.

---

### 2.6. Rule of File Structure

A `*.spc` file consists of zero or more parameters.

#### 2.6.1. Rule of File Beginning

The file begins with the first character of the first parameter or the first comment.

#### 2.6.2. Rule of File End

The file ends with the last character of the last parameter or the last comment.

#### 2.6.3. Rule of File Line Separators

Parameters are separated from each other by zero or more whitespace characters.

#### 2.6.4. Rule of File Comment Separators

Comments are separated from parameters by zero or more whitespace characters.

---

## 3. Semantics

### 3.1. Parameter

- Param acts as a **key**: it specifies the name of the configuration parameter.
- Value acts as a **value**: it contains the value required for the parameter with that name.

#### 3.1.1. Rule of Key Uniqueness

The name specified by Param is unique within a single `*.spc` file.

#### 3.1.2. Rule of Value Assignment

The Value is assigned to the parameter with the name specified by Param.

---

### 3.2. Array Parameter

- The value of an Array parameter is interpreted as an ordered list of elements.
- Each element is interpreted according to the rules of its own type.
- The order of elements is preserved.
- The parameter delimiters LBracket and RBracket are not elements of the Array and are not interpreted as values.

#### 3.2.1. Rule of Element Order

The order of elements within an Array value is preserved during interpretation.

#### 3.2.2. Rule of Element Type Interpretation

Each element of an Array value is interpreted according to the rules of its own type.

#### 3.2.3. Rule of Delimiter Non-Element

The parameter delimiters LBracket and RBracket are not elements of the Array.

#### 3.2.4. Rule of Array Delimiter Non-Element

The array delimiters Lt and Gt are not elements of the Array.

---

## 4. manifest.spc

manifest.spc is the Skorpion project configuration file.

### 4.1. Rule of Reserved Parameters

The standard defines 10 reserved parameters:

| Parameter | Type | Required | Purpose |
|-----------|------|----------|---------|
| name | String | Yes | Project name |
| version | String | Yes | Project version |
| main | String | Yes | Path to the main file |
| target | Array of String | No | Platform or platforms for the build |
| env | String | No | Environment variables applied during the build of this project (not applied to the built binary files) |
| execute | String | No | Arguments applied to the command during the project build |
| buildOutName | String | No | Name of the build output file |
| buildOutPath | String | No | Path to the build output file |
| testOutName | String | No | Name of the test build output file |
| testOutPath | String | No | Path to the test build output file |

#### 4.1.1. Rule of Required Parameters

The parameters name, version, and main are **required**.

#### 4.1.2. Rule of Required Parameter Absence

A manifest.spc file in which at least one of the required parameters is absent is **invalid** and **does not conform to this standard**.

#### 4.1.3. Rule of Parameter Delimiter Presence

For every parameter in the table, the parameter delimiters LBracket and RBracket are mandatory.

#### 4.1.4. Rule of Array Delimiter Presence

For the parameter target, whose type is Array of String, the array delimiters Lt and Gt are also mandatory.

#### 4.1.5. Rule of Type Fixation

For each reserved parameter of manifest.spc, the value type is fixed by this standard. A value of a different type is **invalid** and **does not conform to this standard**.

#### 4.1.6. Rule of Array Type Violation Example

A record in which a parameter declared as String (for example, buildOutPath) is given an Array value is **invalid** and **does not conform to this standard**.

---

### 4.2. Rule of env Format

The value of the parameter env is a single String.

#### 4.2.1. Rule of env Variable Definitions

The String contains zero or more variable definitions.

#### 4.2.2. Rule of env Variable Definition Form

A variable definition within the env String consists of a name, an equal sign, and a value.

#### 4.2.3. Rule of env Variable Separator

Variable definitions within the env String are separated by a Comma.

#### 4.2.4. Rule of env Variable Separator Insignificance

Whitespace characters immediately before or immediately after the Comma within the env String are **insignificant** for the purpose of separating variable definitions.

#### 4.2.5. Rule of env Variable Value Whitespace

Whitespace characters within the value of a variable definition (after the equal sign) are **significant** and are part of the value.

#### 4.2.6. Rule of env Variable Name

The name of a variable within the env String consists of characters permitted by the operating system environment.

#### 4.2.7. Rule of env Variable Value

The value of a variable within the env String consists of characters permitted by the operating system environment.

#### 4.2.8. Rule of env Separator Uniqueness

The first equal sign within a variable definition is the separator between the name and the value.

#### 4.2.9. Rule of env Value Equal Sign

Any equal sign that follows the first equal sign within a variable definition is **part of the value**.

---

### 4.3. Rule of execute Format

The value of the parameter execute is a single String.

#### 4.3.1. Rule of execute Arguments

The String contains zero or more arguments.

#### 4.3.2. Rule of execute Argument Separator

Arguments within the execute String are separated by Space.

#### 4.3.3. Rule of execute Argument Content

An argument within the execute String consists of characters permitted by the operating system command line.

#### 4.3.4. Rule of execute Quoting

An argument within the execute String may be enclosed in Quote or Apos.

#### 4.3.5. Rule of execute Quoting Purpose

The purpose of quoting within the execute String is to preserve Space characters as part of a single argument.

#### 4.3.6. Rule of execute Quoting Escape

A Quote or Apos character within a quoted argument is escaped by a Backslash.

#### 4.3.7. Rule of execute Argument Separation After Quoting

After a closing Quote or Apos, an argument is terminated by a Space or by the end of the execute String.

#### 4.3.8. Rule of execute Empty String

If the execute String is empty, the execute parameter contains zero arguments.

A record in which the execute String is empty is **valid** and **conforms to this standard**.

---

### 4.4. Rule of Unknown Parameters

A parameter that is not listed in the table of reserved parameters is **not defined by this standard**.

#### 4.4.1. Rule of Unknown Parameter Behavior

The behavior of an unknown parameter is not regulated by this standard.

#### 4.4.2. Rule of Unknown Parameter Validity

The presence of an unknown parameter does not by itself make a file invalid under this standard.

---

## 5. Conformance

### 5.1. Rule of Conformance

A `*.spc` file conforms to this standard if and only if all rules of this standard are satisfied.

### 5.2. Rule of Non-Conformance

A `*.spc` file that violates at least one rule of this standard does **not conform** to this standard.

### 5.3. Rule of Partial Conformance

Partial conformance is **not defined** by this standard. A file either conforms or does not conform.
