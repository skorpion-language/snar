# SNAR-A6

## Skorpion Norms And Rules — Generation A — Standard A6

### Diagnostic Codes of the Skorpion Language

---

## 1. Scope

**1.1.** This standard defines the **diagnostic codes** emitted by a conforming implementation of the Skorpion compiler — that is, every error and warning code that the implementation **SHALL** or **MAY** emit when processing a program.

**1.2.** This standard specifies:

- a) the classification of diagnostics into severity levels;
- b) the structure of a diagnostic record;
- c) the message format used to display diagnostics;
- d) the exit codes of the compiler driver;
- e) the normative meaning of each code emitted by the current reference implementation;
- f) the conditions under which each code is emitted;
- g) the current multivalency and overlap among codes (see §17).

**1.3.** This standard does **not** specify:

- a) the Skorpion language itself — see **SNAR-A2** through **SNAR-A4**;
- b) the SPC configuration language — see **SNAR-A1**;
- c) the `.sklib` format — see **SNAR-A5**;
- d) implementation details of any particular compiler;
- e) the presentation of diagnostics (color, layout, TUI) beyond the required structural elements.

**1.4.** Codes listed in §6–§16 are **normative**: a conforming implementation **SHALL** emit the code specified for each condition.

**1.5.** Codes not listed in this standard are **reserved**. A conforming implementation **SHALL NOT** emit a diagnostic code that is not listed here; new codes **SHALL** be introduced only by amendment to this standard.

**1.6.** This standard uses the keywords **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** as defined in RFC 2119.

---

## 2. Conformance

**2.1.** A conforming implementation **SHALL** emit every diagnostic required by §6–§16 for the corresponding condition.

**2.2.** A conforming implementation **SHALL** report each diagnostic with the structure defined in §5.2.

**2.3.** A conforming implementation **SHALL** preserve the exit-code semantics of §5.4.

**2.4.** A conforming implementation **MAY** suppress warnings (see §13) under conditions defined by the implementation, but **SHALL** still be able to emit them.

**2.5.** A conforming implementation **SHALL NOT** silently swallow errors: every error SHALL either be displayed or cause a nonzero exit.

## 4. Terms and Definitions

**Diagnostic** — a record produced by a conforming implementation reporting the existence of a condition in the source input that the implementation has identified as erroneous or noteworthy.

**Diagnostic code** — a four-digit decimal identifier (with three leading zeros where needed) that uniquely identifies a diagnostic class.

**Severity** — one of **error**, **fatal error**, or **warning**. See §5.1.

**Position** — the *(file, line, column)* triple identifying the location of the condition in the input. See §5.2.

**Message** — the human-readable text accompanying a diagnostic.

**Explanation** — additional human-readable context (description, tip, example) associated with a code. See §5.3.

**Trigger** — the precise condition that causes a diagnostic to be emitted.

**Multiplexed code** — a diagnostic code that is emitted for more than one distinct trigger. See §17.

**Required diagnostic** — a diagnostic that a conforming implementation **SHALL** emit when the corresponding condition is detected.

**Recommended diagnostic** — a diagnostic that a conforming implementation **SHOULD** emit when the corresponding condition is detected.

## 5. Diagnostic Model

### 5.1. Severity Levels

**5.1.1.** A diagnostic **SHALL** have one of the following severities:

- **error** — the input is invalid; the implementation **SHALL** produce no executable output for that input.
- **fatal error** — as error, but the implementation **SHALL** stop processing the current phase immediately without attempting further recovery.
- **warning** — the input is valid; the implementation **MAY** produce output. The implementation **SHOULD** display the warning.

**5.1.2.** The classification of each code into a severity is normative and is specified in §6–§16.

**5.1.3.** Whether warnings are promoted to errors is an **implementation-defined** diagnostic-level policy.

### 5.2. Diagnostic Record Structure

**5.2.1.** Every diagnostic **SHALL** include at least:

- a) the diagnostic code;
- b) the severity;
- c) the message;
- d) the position (file, line, column).

**5.2.2.** A diagnostic **SHOULD** additionally include, where relevant, an **end position** (end line, end column) describing a span of source text rather than a single point.

**5.2.3.** When the position is unknown (for example, a file-level condition before any line has been read), line and column **SHALL** be reported as `0`.

**5.2.4.** When the file is unknown (for example, an internal error before any file has been opened), the file **SHALL** be reported as `<unknown>` or as the empty string, consistently within a single compilation.

### 5.3. Message Format

**5.3.1.** The human-readable form of a diagnostic **SHALL** contain:

- a) the severity prefix (`Err+`, `Fatal:`, or `Warn+`);
- b) the diagnostic code;
- c) the position in the form `<file>:<line>:<column>`;
- d) the message.

**5.3.2.** A conforming implementation **SHALL** preserve the message text specified in §6–§16, except for the substitution of positional format arguments.

**5.3.3.** An implementation **MAY** add additional context (such as source-line snippets, hints, or examples). Such additions **SHALL NOT** alter the diagnostic code or the primary message.

**5.3.4.** Example of a conforming diagnostic output:

```
[2026-01-15T12:34:56 > Err+1507]: Type mismatch: cannot assign 'string' to 'int' (at src/main.sk:12:5)
```

### 5.4. Exit Codes

**5.4.1.** The compiler driver **SHALL** use the following exit codes:

| Exit Code | Meaning |
|-----------|---------|
| 0 | Compilation succeeded (no errors) |
| 1 | Compilation failed (at least one error or fatal error) |

**5.4.2.** The exit code **SHALL NOT** distinguish between different error codes. Diagnostics themselves carry that information.

**5.4.3.** Warnings **SHALL NOT** by themselves cause a non-zero exit code, unless the implementation applies a diagnostic-level policy that promotes warnings to errors.

### 5.5. Deduplication

**5.5.1.** A conforming implementation **SHOULD** deduplicate diagnostics with the same code, line, and column, displaying only the first occurrence.

**5.5.2.** Deduplication **SHALL NOT** change the exit code: a duplicate error still counts as an error.

### 5.6. Ordering

**5.6.1.** Diagnostics **SHOULD** be reported in source order, i.e., sorted by file, then by line, then by column.

**5.6.2.** An implementation **MAY** report errors before warnings. The relative order between errors and warnings **SHALL NOT** affect the meaning of the diagnostics.

## 16. Message Stability

**16.1.** A conforming implementation **SHALL** emit the message text specified in §6–§16 for the corresponding code, with placeholders substituted by values from the input.

**16.2.** An implementation **MAY** append an additional implementation-defined suffix to the message, prefixed by a separator such as ` — `, provided the normative prefix remains unchanged.

**16.3.** An implementation **MAY** translate messages to the user's language, provided that:

- a) the diagnostic code is preserved verbatim;
- b) the translation is unambiguous;
- c) a language-neutral representation remains recoverable.

**16.4.** When a message contains format placeholders (`<token>`, `<name>`, `<type>`, etc.), the implementation **SHALL** substitute the actual source text for the placeholder.

## 17. Multiplexed and Misplaced Codes

### 17.1. Purpose

**17.1.1.** This section documents cases where a single code is used for more than one trigger, or where a code's stated description in the reference code map does not match its actual emission.

**17.1.2.** A conforming implementation **SHALL NOT** rely on the specific trigger selected by the reference implementation; it **SHALL** emit the code specified in §6–§16 for the corresponding condition. Where a code is multiplexed, the implementation **SHALL** emit the code for each trigger listed.

### 17.2. Code 0590

**17.2.1.** The parser emits **0590** when `Error` is not followed by `{`. The message is `Expected '{' after 'Error'`.

**17.2.2.** The reference code map documents **0590** as `Expected 'new' or error type after '='`. No code path in the reference implementation emits **0590** with that message.

**17.2.3.** A conforming implementation **SHALL** treat the parser usage of **0590** as normative.

### 17.3. Code 0560

**17.3.1.** The parser emits **0560** when `void` appears as an array element type: message `Array element type cannot be 'void'`.

**17.3.2.** The semantic analyzer emits **0560** for two related conditions: a variadic parameter that is not the last parameter (`Variadic parameter must be the last one`) and a variadic parameter that is not unique (`Only one variadic parameter is allowed`).

**17.3.3.** A conforming implementation **SHALL** emit **0560** for all three triggers described above.

### 17.4. Codes 3100, 3101, 3103

**17.4.1.** The reference code map describes **3100**, **3101**, and **3103** as library errors (cannot read `.sklib`, library not found, library version mismatch).

**17.4.2.** The reference implementation uses these codes for **Zig toolchain setup failures**, with messages about Zig, not about libraries.

**17.4.3.** A conforming implementation **SHALL** treat the actual emission in the driver as normative for §12.

**17.4.4.** The library-related uses described in the code map for codes 3100, 3101, and 3103 are **not currently emitted**; they are **reserved** for future use, to be specified in a future amendment.

### 17.5. Code 2501

**17.5.1.** The reference implementation's code map registers the entry under the numeric key `"2501"` but sets its `Code` field to `"2500"`.

**17.5.2.** A conforming implementation **SHALL** emit **2501** (not 2500) when the condition in §10 (argument-expression type cannot be determined) is detected.

### 17.6. Code 0653

**17.6.1.** The parser emits **0653** when an assignment operator is missing after a field name in `x.field = value` (see §8.4).

**17.6.2.** The configuration parser emits **0653** as a catch-all for **configuration file syntax errors**, with message `Config error: <detail>`.

**17.6.3.** Both usages are fatal. A conforming implementation **SHALL** emit **0653** for both conditions. The two usages are distinguished by the source file (`manifest.spc` for configuration errors, a `.sk` file for parser errors) and by the message.

### 17.7. Code 0597

**17.7.1.** **0597** is emitted by the parser in two closely related cases:

- a) a keyword appears where a statement is expected (`Unexpected keyword in statement position`);
- b) an identifier is followed by a token that is not a valid postfix or assignment operator (`Unexpected token after identifier`).

**17.7.2.** A conforming implementation **SHALL** emit **0597** for both cases.

### 17.8. Code 1507

**17.8.1.** **1507** is emitted for three variants of type mismatch during declaration:

- a) a normal local variable declaration whose initializer type does not match the declared type;
- b) an async call assigned to a local variable whose declared type does not match the async function's return type;
- c) a global constant whose literal initializer type does not match the declared type.

**17.8.2.** A conforming implementation **SHALL** emit **1507** for all three cases.

### 17.9. Code 1539

**17.9.1.** **1539** is emitted for several closely related "not a valid operation for this symbol/type" conditions: calling a variable, indexing a non-array, accessing a field on a non-error type, accessing a non-existent field.

**17.9.2.** A conforming implementation **SHALL** emit **1539** for all of these triggers.

### 17.10. Code 0668

**17.10.1.** Code **0668** lies in the `06xx` range (normally parser diagnostics), but it is emitted during **IR pipeline generation**, not during parser or semantic analysis. In the reference implementation, it originates from `pipeline.go`, in the argument handling for the `isAsyncEnded` built-in.

**17.10.2.** Because this code is `error`-severity (not `fatal`), the pipeline reports it through `errors.NewError` and continues generating IR. The exit code is still affected because any error causes a non-zero exit.

**17.10.3.** A conforming implementation **SHALL** emit **0668** with error severity, from any phase that detects the condition described in §9.16. The numeric placement of the code in the `06xx` range is historical; it does not constrain the phase in which the code is emitted.

### 17.11. Codes 3106, 3107

**17.11.1.** Codes **3106** and **3107** are emitted during **IR pipeline generation** (the `processGlobalVar` stage), not during semantic analysis. They are `error`-severity, not `fatal`-severity.

**17.11.2.** **3106** is emitted when the initializer of a global constant is not a literal, or when the initializer is absent. **3107** is emitted when the initializer's element type (for a global `arr`) is not supported at file scope (e.g., `void`, `dict`, or a union type inside `arr[...]`).

**17.11.3.** A conforming implementation **SHALL** emit **3106** for the "not a literal" and "no initializer" triggers, and **3107** for the "unsupported element type" trigger. The phase in which they are emitted is a property of the reference implementation, not of this standard.

**17.11.4.** The code map documents **3107** as a `fatal` error under the name *Library dependency not imported*; that trigger is **not currently emitted** by any code path, and its use of the number 3107 conflicts with the pipeline's use. The pipeline's use of **3107** for "unsupported global array element type" is the only currently emitted use, and a conforming implementation **SHALL** treat it as normative. The library-dependency use is **reserved** for a future amendment.

A conforming implementation **MAY** emit 1502 if it detects a non-void `main` in a code path of its own; otherwise, it **SHALL NOT** emit it. This code is therefore classified as **conditionally reserved**.

## 19. Rationale (Informative)

**19.1.** Diagnostic codes are grouped by phase (lexer, parser, semantic, backend, builder, library) to make it easy to identify the source of a problem from the code alone. The leading digits of each code encode the phase.

**19.2.** The severity of a code is generally determined by the phase: lexer and parser errors are fatal because recovery would require substantial heuristics; semantic errors are non-fatal because the analyzer can continue to find more errors; warnings never invalidate the input.

**19.3.** Codes 2000–2099 are reserved for warnings. No warning currently shares a code with an error, except 1541, which is grouped under the semantic range for historical reasons.

**19.4.** The multiplexing documented in §17 is a consequence of the reference implementation's growth: as new conditions were added, some existing codes were reused rather than creating new codes. A future revision of this standard **MAY** split multiplexed codes into distinct codes; when that happens, the older codes **SHALL** remain as aliases for backward compatibility.

---

## 20. Amendment Procedure

**20.1.** New diagnostic codes **SHALL** be introduced only by amendment to this standard.

**20.2.** An amendment **SHALL** specify, for each new code:

- a) the numeric code;
- b) the phase (lexer, parser, semantic, backend, builder, library, pipeline);
- c) the severity;
- d) the trigger;
- e) the message template;
- f) an example of the condition.

**20.3.** The amendment **SHALL NOT** change the severity of an existing code, except where the original severity was demonstrably incorrect.

**20.4.** The amendment **MAY** reclassify a reserved code into a used code.

## Appendix B — Reference Message Format

For each message, the implementation **SHALL** substitute the following:

- `<token>` — the literal text of the offending token
- `<keyword>` — the keyword text
- `<name>` — the identifier text
- `<type>` — the type string (`int`, `arr[int]`, `T<int,string>`, etc.)
- `<op>` — the operator symbol (`+`, `&&`, etc.)
- `<hex>` — the hexadecimal codepoint digits
- `<n>`, `<m>`, `<i>` — numeric placeholders
- `<target>` — the build target (e.g., `linux`, `windows`)
- `<detail>` — an implementation-defined detail string (typically the underlying OS error)

## Appendix C — Complete Example

A program containing several of the diagnostic conditions:

```skorpion
const int MAX = "hello"       // Err+1507: type mismatch on global constant

void main(arr args) {
    int x = "hello"           // Err+1507: type mismatch
    const int Y = 10
    Y = 20                    // Err+1509: cannot assign to constant
    string s = "hi"
    s += 42                   // Err+1510: cannot apply '+=' to string and 'int'
    for (int n in 42) { }     // Err+0631: cannot iterate over 'int'
    case (x) {
        1 { }                 // Err+1525: pattern type mismatch
    }
}
```

The implementation **SHALL** emit diagnostics **1507**, **1509**, **1510**, **0631**, and **1525** at the corresponding source positions.
